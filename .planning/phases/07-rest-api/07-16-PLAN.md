Close gap 4 of 07-VERIFICATION.md (WR-03): a well-formed but foreign, emptied or hand-edited `cursor` answers 422 on all four list endpoints instead of 500, and the example cursor in the published documentation is one the API accepts.

Laravel's `Cursor::fromEncoded()` accepts any base64url JSON object that has `_pointsToNextItems`, so a cursor with missing keys throws `UnexpectedValueException`, and a wrong-typed value reaches a uuid or timestamptz column as a bound parameter (22P02 / 22007): both 500. The published example cursor is itself such a cursor.

Facts read while planning (vendor source of the installed Laravel):
- `Illuminate\Pagination\Cursor::fromEncoded()` decodes `str_replace(['-', '_'], ['+', '/'], $encoded)` with `base64_decode` and `json_decode(..., true)`; it returns null (first page, no error) for invalid JSON, a non-array or a missing `_pointsToNextItems`, and otherwise keeps every other key unchecked.
- `AbstractCursorPaginator::getParametersForItem()` reads each order column from the model (`$item[$column] ?? $item[afterLast('.')]`) and turns an object with `__toString` into a string, so a timestamp column is written as Carbon's string form `Y-m-d H:i:s` in UTC (the application timezone), and an id column as the uuid string. The keys are the order column names exactly as ordered: `started_at` or `created_at` (unqualified, from the query-builder sort) and `time_entries.id` (qualified, from the tiebreaker); for lookups `name` / `title` / `created_at` and `clients.id`, `projects.id`, `tasks.id`.
- Confirm both facts by decoding a real `meta.next_cursor` in the first RED test before writing the rule.

Decisions made in this plan (recorded, Claude's discretion):
- A cursor that the API did not issue is refused with 422, including one that Laravel would silently treat as "first page" (not decodable, not an object, no `_pointsToNextItems`). The docs already say an invalid cursor is 422.
- The decoded key set must equal exactly the sort column, the id column and `_pointsToNextItems`; extra keys are refused, so a cursor of another endpoint or another sort column can never pass.
- The kind of a sort column is declared in one place, `ApiCursor::kindOf()` (`started_at`, `created_at` are instants; `name`, `title` are text); an unknown column throws a LogicException, so a sort added later without a cursor kind fails its round-trip test instead of silently skipping validation.
- An instant cursor value is accepted only in the exact form the paginator writes (`Y-m-d H:i:s`, a real calendar date and time, year not 0000), so PostgreSQL never parses anything the validator did not.
- The rule fails with the same message as the other list parameters (`validation.regex` with the attribute), keyed `cursor`.
