Facts measured while planning (PHP 8.5 in DDEV, Carbon as installed):
- `0001-01-01` at Prague midnight is `0000-12-31 23:02:16+00:00` (historic local mean time, UTC year 0), so that day cannot be a filter bound; `0001-01-02` begins in UTC year 1.
- Re-parsing the text `10000-01-01` with `createFromFormat('!Y-m-d', ...)` throws `InvalidFormatException`; building the same midnight from the year, month and day components gives `9999-12-31 23:00:00+00:00` (CET), which PostgreSQL stores. So `9999-12-31` is a supported day once `midnight()` stops re-parsing a formatted string.
- `9999-12-31T23:59:59-12:00` is UTC year 10000; `0001-01-01T00:00:00+02:00` is UTC year 0.

Facts read while revising (code as of plan 07-13's delegation):
- `TimeEntryPayload::end()` computes the end of a `duration_seconds` entry as `$start?->addSeconds((int) $duration)` and only compares the span (07-13: `TimeEntryInput::assertDurationFits`); that end never passes `TimeEntryInput::instant()` or `normalised()` in the payload. `started_at` 9999-12-31T00:00:00Z with `duration_seconds` 2147483647 passes the span bound and yields an end in UTC year 10067, which is a 500 today.
- `CreateTimeEntry::handle()` and `UpdateTimeEntry::applyTimes()` pass the received `ended_at` through `TimeEntryInput::instant()` again (the CarbonInterface branch), so after step 3 of Task 1 the Action would also refuse that end. The payload must refuse it itself, so the answer comes before the Action runs (no transaction, no share locks) and the request layer does not lean on a check it does not own.

Decisions made in this plan (recorded, Claude's discretion):
- The envelope lives in `TimerClock` ("the single clock of every time write") as `isStorable(CarbonInterface $value): bool`: true when the instant's UTC year is between 1 and 9999. Both `TimeEntryInput` and `PragueDay` ask it, so the range is stated once.
- Tests assert year bounds and storability, not the exact historic local-mean-time seconds, so a tzdata update cannot break them.
- An out-of-range day in the panel's custom period filter is dropped like any other invalid day (the existing `PragueDay::day()` null path), with no new message.
- The computed end of `duration_seconds` is wrapped in `TimeEntryInput::instant(..., 'ended_at')` inside `TimeEntryPayload::end()`, not checked with a direct `TimerClock::isStorable()` call there: the range, the truncation and the `invalid_time` message then stay in `TimeEntryInput::normalised` only, and a named `ended_at` and a computed end take exactly the same path. The range check runs before the span bound of plan 07-13, as for a named `ended_at`.
