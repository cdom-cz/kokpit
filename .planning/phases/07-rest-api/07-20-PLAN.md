<objective>
Close gap G-07-3 (07-UAT.md test 3, major): the empty-state button "Nový API token" on the API token list does nothing.

Purpose: an Admin who has no token yet sees the empty state first, and its call to action is the UI-SPEC's primary way into the create modal (UI-SPEC: "The empty-state call to action is the same 'Nový API token' action"). Today the empty-state action newToken is a table action whose handler makes a nested mount of the page action createToken. Filament then resolves createToken as a modal child of newToken, which it is not. The resolution fails, the nested mount is dropped, and the finished newToken is unmounted, so nothing opens. During planning this was confirmed in DDEV: after mountTableAction('newToken') the page's mountedActions was []. With the handler switched to replaceMountedAction('createToken'), the stack was exactly [createToken] with an empty context, and a token with both abilities was created from that modal.

Output: a one-handler fix in ApiTokenResource (plus a guard and corrected comments), and regression tests in ApiTokenScreenTest. The tests cover the empty-state click end to end, the error and cancel paths on that route, a forged Partner call, and the empty-state action pinned by name and label.
</objective>

Gap source: 07-UAT.md `## Gaps` G-07-3. truth: "Admin creates a token with both abilities from the token screen; the create modal opens from the table empty state". root_cause: the empty-state action newToken nests a mount of createToken inside its handler. missing: (1) "Open createToken from the empty state without a nested action mount (replaceMountedAction or a wire click on mountAction)"; (2) "Livewire test that clicks the empty-state button and asserts the createToken modal is mounted".

Locked decisions carried in: D-01 (a Partner cannot create tokens), D-03 (Admin-only token screen with `#[AccessRule]`), D-04 (password and TOTP re-confirmation before a token is issued; the plain token is shown once). UI-SPEC: header and empty state share the one primary CTA "Nový API token".

Decisions made in this plan (Claude's discretion, recorded):
- Fix with replaceMountedAction('createToken') in the newToken handler, not with an Alpine click handler that calls the page's mount from the browser. Both options are in the gap's `missing` item. The server-side replacement can be driven by a Livewire test (`mountTableAction('newToken')`), which `missing` item 2 requires; a browser-only click handler cannot. It is also the pattern ListApiTokens::issueToken already uses to swap createToken for showToken. Filament's callMountedAction keeps a replaced stack: it compares the stack's names and contexts before and after the handler and does not unmount when they differ. Verified in DDEV during planning, as described in the objective.
- The newToken handler gets the same `abort_unless(self::canAccess(), 403)` first line as the revoke handler in this resource (defence in depth; the page-level AccessRule already refuses a Partner's Livewire calls).
- ListApiTokens.php does not change. createTokenAction(), issueToken() and failUnderModal() stay as they are, so the empty-state route goes through exactly the same identity confirmation, throttle and field errors as the header button.

Fictional data only (example.com, 'Example tool', runtime-generated passwords and TOTP secrets as in the file's beforeEach). Tests run in DDEV; the host has no database. Before every commit run `git status`, `git diff --staged` and `scripts/check-sensitive.sh`. Never bypass the hook.
