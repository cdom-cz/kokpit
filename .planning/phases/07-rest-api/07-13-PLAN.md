<objective>
Close gap 1 of 07-VERIFICATION.md (WR-01, open threat T-07-26): bound the interval of a time entry in the shared domain Actions, so a far-past or far-ahead start answers a clean 422 instead of an integer-overflow 500, on a finished and on a running entry, through the API and the panel alike.

Purpose: the 07-05 must-have "an interval longer than 2147483647 seconds answers 422, never the PostgreSQL integer overflow 500" holds today only for create and for PATCH of `ended_at` / `duration_seconds`. A PATCH of `started_at` alone gives 500 on a finished entry and silently stores an overflowing start on a running entry, which then breaks the Admin's own entry list. D-09 (the API refuses what the UI refuses) and the locked rule "the Actions are the single place for rules" put the fix in `TimeEntryInput` and the Actions, not in the HTTP layer.
Output: `TimeEntryInput::MAX_DURATION_SECONDS` and `TimeEntryInput::assertDurationFits()`, calls in `UpdateTimeEntry` and `CreateTimeEntry`, `TimeEntryPayload::end()` delegating, the Czech message moved to `kokpit.time.errors`, regression tests at the HTTP and the Action level.
</objective>

Decisions made in this plan (recorded, Claude's discretion):
- The bound is the magnitude of the interval, `abs(to - start) > 2147483647`, so a running entry is refused both for a start far in the past and for a start more than about 68 years ahead of now (both overflow the `::int` cast of the elapsed-seconds expression).
- The field key is the field the data changes: `ended_at` when the data names `ended_at` (and always on create), otherwise `started_at`. This keeps the existing 07-05 contract (overflow via `ended_at` / `duration_seconds` under `ended_at`) and gives the gap's required `started_at` key for a start-only edit.
- The Czech text stays exactly "Záznam je příliš dlouhý." and moves from `api.errors.duration_too_long` to `kokpit.time.errors.duration_too_long`, because the rule now lives in the domain and the panel shows it too. The API answer text is unchanged.
