<objective>
Close gap G-07-1 (07-UAT.md, major), which is 07-VERIFICATION.md truth 7 and 07-REVIEW.md WR-02. The SQL elapsed-seconds expression that the Admin screens read becomes overflow-proof, so no stored start of a running entry can ever take down the entry list or the time totals.

Purpose: plan 07-13 put a span guard on a running entry's start, but it only compares the start with now at the moment of the edit. The reader, `TimeEntry::scopeWithElapsedSeconds`, casts the epoch difference straight to a 32-bit integer every time the list is read. A start accepted a few seconds inside the limit therefore makes every later read fail with SQLSTATE 22003. That takes down the Admin entry list, the view and edit pages, the timesheet and the project entries tab, and nothing in the panel can repair it. The fix follows the gap's `missing` item: compute in bigint and clamp with GREATEST/LEAST to 2147483647. `TimeTotals` has two more copies of the same unsafe cast (task page, project stats row, project task tab). All three move to one shared expression.
Output: `TimeEntry::elapsedSecondsSql()`, the scope and `TimeTotals` on it, corrected docblocks that no longer claim the write guard keeps the list readable, and regression tests that reproduce the UAT failure through the API, the panel pages, the Action layer and the totals.
</objective>

The Phase 6/7 rule that the Actions are the single home of the write rules. 07-13 decision: the interval bound is `abs(to - start) <= 2147483647` in `TimeEntryInput::assertDurationFits`. That bound stays exactly as it is.

Decisions made in this plan (Claude's discretion, recorded):
- The fix is on the read side, as WR-02 asks: "remove the dependency on the margin rather than shrinking it". The write guard on a running start stays as a sanity bound. It still refuses a typo year more than about 68 years off, and its tests and messages do not change.
- One expression for every SQL reader: `TimeEntry::elapsedSecondsSql(string $alias): string`. It is a public static method on the model, typed `literal-string` in and out so `TimeTotals::taskSum()` keeps its `literal-string` contract, and it has exactly one `?` placeholder for the instant. Inside COALESCE the stored `duration_seconds` still comes first. The running value is the epoch difference cast to bigint, floored with GREATEST(0, ...), capped with LEAST at `TimeEntryInput::MAX_DURATION_SECONDS`, and the capped value is cast back to int. Each row therefore stays an int between 0 and 2147483647. The cast can never overflow, because a bigint holds every difference between UTC years 1 and 9999. Sums over the rows are bigint in PostgreSQL. Verified in DDEV PostgreSQL 18 during planning: year-1 start gives 2147483647, year-9999 start gives 0, `pg_typeof(SUM(int))` is bigint, the old direct cast raises "integer out of range".
- The ceiling is the same constant as the write bound (`TimeEntryInput::MAX_DURATION_SECONDS`), so the read clamp and the write bound cannot drift.
- PHP readouts are not changed. `ControlsTimer` (top bar and side panel) and `NotifyLongRunningTimers` compute elapsed time with 64-bit PHP integers and cannot overflow. A running entry past the limit will show a few more seconds there than the clamped list. That only happens to an entry that has run for 68 years and is accepted as is.
- No wire change: `app/Http` reads no elapsed seconds (checked with git grep during planning), and the API resource keeps `duration_seconds` null while an entry runs.
