Assumptions adopted from research (unattended run, recorded and easy to reverse):
- Research item 6 (Open Question 7): no global `UserResource`; the account list lives in the client detail (D-04). The single Admin is managed by the install and reset commands.
- Own decision (reason): D-04 requires a password reset sent from the client detail, and the mailed link needs a reset page; Filament provides it only through `->passwordReset()`, which also registers the public "forgot password" request page. It answers generically, is throttled, and its broker callback sends nothing when `canAccessPanel()` is false. Side effect: the documented gap "no password recovery path for the Admin" closes (Admin 2FA still applies after a reset); plan 04-21 updates the README line. Reversal: remove the call and the Admin action.
- Deactivation is stored in `users.deactivated_at` (plan 04-01, CONTEXT discretion), set only by these Actions with `forceFill`.
- Accounts are never hard-deleted: the accounts tab has no delete action and `client_invitations.accepted_user_id` references users with `ON DELETE RESTRICT`.

Fictional data only; `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
