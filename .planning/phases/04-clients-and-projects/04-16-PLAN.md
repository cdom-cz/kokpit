Design decisions carried in from research Pattern 3 (recorded here):
- State is derived from `accepted_at`, `revoked_at` and `expires_at`, never stored (research anti-pattern "storing invitation state as a column"); the derived `state()` lands in plan 04-17.
- The token is `bin2hex(random_bytes(32))`; only `hash('sha256', $token)` is stored and compared with `hash_equals`. SHA-256 is right for a 256-bit random token.
- `ClientInvitation` is not activity-logged: its own timestamps (`last_sent_at`, `send_count`, `accepted_at`, `revoked_at`) record the lifecycle, and the activity log must never see the token hash.
- Plan 04-17 adds the e-mail delivery to `InvitePartner` (the plain token leaves the Action only inside the signed URL); in this plan the Action stores the invitation and returns it.

Fictional data only: `exampleEmail()` invitees, `Example` names. `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
