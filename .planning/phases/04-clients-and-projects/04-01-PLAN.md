Assumptions adopted from research (unattended run; each is recorded here, visible and easy to reverse):
- Research item 8 (A1, A2): enum columns are `varchar` plus a `CHECK (col IN (...))` constraint, no native PostgreSQL enum; invoice languages are exactly `cs` and `en`.
- Column naming (own decision, reason): the Czech company ID (IČO) and tax ID (DIČ) are stored as `company_number` and `tax_number`, because schema rule R1 in `tests/Support/PgSchema.php` requires every column ending in `_id` to be uuid and the exempt map stays at its four framework entries.
- Foreign keys use `restrictOnDelete()`; PostgreSQL answers a hard delete of a referenced row with SQLSTATE 23001 (restrict_violation) and an insert with an unknown parent with 23503 (STATE.md, plan 02-07 finding). Tests assert exactly these codes.
- `User::canAccessPanel()` keeps no memo on the user instance: one primary-key `exists` query per call, so an archive or a deactivation takes effect on the next request even in long-lived processes and in tests that reuse one user object.
- Migration order: clients (`000100`), then the users foreign key (`000200`), then projects (`000300`, plan 04-02); each sorts after what it references.
