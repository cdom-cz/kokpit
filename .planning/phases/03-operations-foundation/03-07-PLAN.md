<objective>
Add bank accounts per currency to the settings page: a repeater whose format (Europe 1, Europe 2, World) decides the visible fields, an own IBAN rule, one account per currency in the form and at the data layer, uniform stored shape, and the lookup by currency that invoices will use (D-03, D-04).

Purpose: FND-07 bank accounts per currency. Phase 10 prints the account on invoices and builds the SPAYD QR from its IBAN, so an invalid IBAN or two accounts in one currency would surface only on an issued, immutable invoice.
Output: banking value objects and rules, `BankAccountSettings`, the bank tab, unit and feature tests.
</objective>

Uses from 03-03 to 03-06: `ValidatedSettings`, `SettingsMigration`, `SettingsPage` (SETTINGS list, tab methods, data-layer error key mapping), `Money::isoCurrencyCodes()` and `Money::isKnownCurrency()` (03-05).

Resolved decision (open question 3, not re-asked): an own IBAN validation (mod-97 plus a country length table covering Czech, Slovak and EU/EEA basics, plus CH and GB); `jschaedl/iban-validation` is not added, because its unverified provenance would force a blocking human checkpoint. Rating: reversible, the rule sits behind `IbanRule` and can later delegate to a library without touching callers.

The bank tab is the second tab (after supplier). Required fields per format (planner discretion, documented here): Europe 1 requires account number (`^(\d{1,6}-)?\d{2,10}$`), bank code (`^\d{4}$`) and IBAN, bank name optional; Europe 2 requires IBAN; World requires account number (up to 34 letters and digits), recipient name and bank name, bank address optional; BIC/SWIFT is optional for every format and, when given, must match `^[A-Z]{4}[A-Z]{2}[A-Z0-9]{2}([A-Z0-9]{3})?$` after upper-casing; label required (max 100); currency required and known.

All bank form cases (Livewire tests of the bank tab) live in `tests/Feature/Operations/BankAccountSettingsTest.php`; `tests/Feature/Operations/SettingsPageTest.php` is run as a regression check and not edited by this plan.

Hygiene (research "Fictional IBAN in tests"): compose IBANs at runtime with `Iban::compose(country, bban)` from digit fragments (for example a bank code fragment and a random account fragment); never write a complete IBAN, and never write an account number joined to a bank code by a slash. `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
