<objective>
Make the application deployable to Zerops without weakening the repository's guarantees: a secret-free `zerops.yml` with once-per-deploy migrations and a readiness gate (D-18), a deploy workflow that only a published release or a manual dispatch through the protected `production` environment can start, the proxy trust the balancer needs, the documented manual GitHub and Zerops settings, and a rehearsal checklist for what only a real Zerops project can prove (FND-15).

Purpose: FND-15. A deploy path that any push, tag or integration could trigger would bypass review; a migration that half-fails while traffic switches would corrupt production.
Output: `zerops.yml`, `kokpit:deploy:verify`, proxy trust, `.github/workflows/deploy.yml`, contract tests, documentation and the rehearsal checklist.
</objective>

Resolved decisions (not re-asked):
- Open question 4: the Zerops rehearsal is a non-blocking manual verification. It becomes `03-ZEROPS-REHEARSAL.md` plus a `<human-check>` here and a Manual-Only row in `03-VALIDATION.md`; nothing in this run waits for it.
- Open question 5: a separate `scheduler` setup running `schedule:work` (one container, set in the Zerops service settings), mirroring DDEV.
- Research A7 (`extends` with `null` overrides unverified): the three setups are written out in full without `extends`; the test asserts their build sections are identical, so they cannot drift. Rating: reversible.
- Readiness: `kokpit:deploy:verify` is the app readiness command, because the Zerops docs do not state what an `initCommand` failure does to the new container (research A4).
- `trustProxies(at: '*')`: the app containers are reachable only through the Zerops balancer; rehearsal item confirms https URLs.
- Redis eviction: Valkey `maxmemory-policy` `volatile-lru` (or `noeviction`) is a documented Zerops setting; the DDEV `redis.conf` stays as generated by its add-on (development only, 2 GB cap) and the difference is documented (research Pitfall 3).
- The native Zerops GitHub or GitLab integration must be disabled for every service; it is a checklist item and a documentation test (research Pitfall 11).
- zcli: pinned release asset `zcli-linux-amd64` by version and SHA-256 hard-coded in the workflow; obtain the digest with `gh api repos/zeropsio/zcli/releases/latest --jq '.assets[]|[.name,.digest]|@tsv'`, the same bump procedure as for gitleaks; the Zerops-provided action is not used (research Pattern 11). If `gh api` is unavailable to the executor, download the asset over HTTPS from the GitHub release page, compute its SHA-256 locally, compare it with the digest the release page shows when reachable, and record in the summary which source the pinned digest came from.
- Environment variable reference names of Zerops services (for example `${db_hostname}`, `${db_password}`, `${redis_hostname}`, object storage keys) are `[ASSUMED]` and are a rehearsal item; `APP_KEY` and mail credentials are project secrets set in the Zerops GUI and never appear in the file.

Hygiene: the scanners flag hosting hostnames (`*.zerops.app` and S3-provider endpoints) and a Zerops token assigned to a `ZEROPS_TOKEN`-style name; never write a hostname of a real project, and never write a literal value after a token or key name in tests or docs (use `${{ secrets.ZEROPS_TOKEN }}` in the workflow only). `scripts/check-sensitive.sh` before every commit; never bypass the hook.
