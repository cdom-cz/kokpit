Serialized after 03-01 and 03-02 only to keep application plans out of a parallel wave: every application plan runs Pest in the single DDEV project against the shared `kokpit_test` database (same rule as Phase 2). There is no content dependency on the spikes.

Resolved decision (open question 1, recorded here, not re-asked): `SettingsProperty` uses the Phase 2 `DeniesPartners` trait and overrides `constrainForPartner()` with a group allowlist (`PARTNER_VISIBLE_GROUPS`, empty now, so the behaviour equals deny-all); `settings.cache.enabled` is a literal `false` (a cached read would bypass the scope); jobs and console run in the system context (existing `runAsSystem` for commands, the job base in plan 03-13, the settings migration base here). Keeping the class on `DeniesPartners` is deliberate: the Phase 2 canary test expects zero rows for it, so adding a Partner-visible group later fails that test until the author swaps the trait and the fixture on purpose.

Verified before planning: the package binds each settings class with `scoped()` (fresh per request and per queue job), `save()` writes through an upsert (no global scope on insert), reads go through the model (scope applies), settings migrations live in `database/settings/` and run with `php artisan migrate`.

Settings classes are registered explicitly in `config('settings.settings')` and auto-discovery is off, so no discovery cache is needed in deploy; plans 03-05 to 03-08 add their classes to that list.

`SupplierSettings` extends the package `Settings` class in this plan. Plan 03-04 introduces `ValidatedSettings` (data-layer rules and form-state mapping) together with the settings page and moves `SupplierSettings` onto it.

Fictional data only: `Example s.r.o.`, company ID `12345678`, `exampleEmail()` addresses. Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
