## Decisions and residual risk

- **CR-01, timeout kill.** When the worker kills a job on timeout (`TimeoutExceededException`), the process exits right after `JobFailed` and no later hook runs, so that one alert is still delivered inline. It is bounded by the SMTP timeout, but in that path the alert still runs before the framework writes the `failed_jobs` row. Another mailer than SMTP is not bounded by `MAIL_TIMEOUT`; set the timeout of its client in `config/mail.php` if one is used.
- **CR-01, other failures.** A hanging transport in the deferred step can no longer cost the `failed_jobs` row (tests prove the row exists when the alert is sent and when every channel throws). The deferred send can still be cut by the job timeout alarm, which would lose only the alert, not the failure record.
- **WR-02.** The sanitising is best effort and errs on removing too much. The unfiltered message stays in `failed_jobs` and the log.
- **WR-04.** No `retryUntil`, deliberately: the worker marks an expired job as failed, which would write `failed_jobs` rows and raise Admin alerts after every worker outage. A lost unique lock (for example a cache flush) delays the next heartbeat by at most 900 s.
- **WR-03.** The `APP_URL` check refuses non-https URLs and `localhost`, loopback, `*.localhost` and `*.test` hosts. It does not try to recognise other private or development hosts.
- **WR-07.** `URL::forceRootUrl(config('app.url'))` from the review was not added; ignoring the forwarded host already removes the spoofing path, and `APP_URL` is now guaranteed in production.

## Deferred, with recommendations

- **WR-06 (number scope key versus pattern collisions).** Recommendation: add a unique constraint on the issued-number string per document kind in Phase 10, and make issuing check that the formatted number does not exist before the allocator increments, so a collision fails with a clear error. Until invoices exist there is nothing to collide with.

## WR-05 follow-up (security audit T-03-48) and UF-1

- **WR-05 (a), ref guard, implemented.** After the existing release checks (prerelease, tag type, `v*`), the `verify` step of `.github/workflows/deploy.yml` runs `case "${GITHUB_REF}" in refs/heads/main | refs/tags/v*) ;; *) exit 1`. It applies to every event, so a `workflow_dispatch` from a feature branch, a lookalike such as `main-evil` or `release/main`, a pull request ref or a foreign tag is refused. Event data still reaches scripts only through `env` (the runner variable `GITHUB_REF` is read like `GITHUB_SHA`), and no `${{ }}` appears in any `run:`.
- **WR-05 (b), green CI, implemented (chosen over documenting it as a maintainer control).** A second step of the secret-free `verify` job calls `gh api --paginate repos/${GITHUB_REPOSITORY}/commits/${GITHUB_SHA}/check-runs` with the job's own `GITHUB_TOKEN` (`GH_TOKEN: ${{ github.token }}`, in that step's `env` only) and a `--jq` filter that accepts only a run named `CI Passed`, from the app `github-actions`, with status `completed` and conclusion `success`. An empty result or an API error refuses the deploy (fail closed). The check-runs endpoint returns the latest run per name by default, so a later failed re-run supersedes an earlier green one. It could be done cleanly and testably because the filter is exercised with the real `jq` against canned answers (see below), the token needs only `checks: read`, and no extra action or secret is involved. `statuses: read` is not needed because `CI Passed` is a check run, not a commit status.
- **Permissions.** Top level stays `permissions: {}`. `verify` has `contents: read` and `checks: read` at job level (the second carries an inline comment, which keeps the `deploy.yml` clean under zizmor `--persona auditor`). `deploy` is unchanged (`contents: read`). `DeployWorkflowTest` now asserts exactly these sets, that no other job or step sees `GH_TOKEN`, and that the token comes from `github.token`.
- **Tests.** The test runs the real `verify` steps in a throwaway repository with a fake `gh` (never contacts GitHub) that applies the workflow's own `--jq` filter with the real `jq` to a canned answer, and records its arguments. Proven: six refused refs (message asserted, `gh` not even called), eight refused CI states (failed, cancelled, skipped, still running, other name, other app, no run, API error), the passing cases (release, dispatch from main, dispatch from a `v*` tag), and the exact endpoint for the deployed commit. The runner variables are set explicitly so a GitHub runner environment cannot leak in. The mutation self-check gained nine mutations (checks write, checks read in deploy, ref guard removed, CI gate removed, conclusion filter removed, app filter removed, empty-result check inverted, another token, job token in the deploy job). Tests that need `jq` skip themselves when it is not installed (it is preinstalled on the Ubuntu runners and in DDEV). Two manual mutations of the real workflow (ref guard widened, empty-result check inverted) were confirmed to fail the suite.
- **Residual risk, stated plainly.** The workflow file that runs is the one of the dispatched ref. Anyone who can push a branch can edit `verify` there, so these checks are defence in depth against mistakes and against a dispatch from a non-reviewed ref, not a boundary against a malicious writer. The boundary is the `production` environment: required reviewer, no admin bypass, and the deployment branch and tag policy (`v*` plus the default branch). `CONTRIBUTING.md` ("Deploy (maintainer, manual)") now says so, and those items remain unchecked maintainer tasks that cannot be verified from the repository.
- **Unverified against the live API.** Nothing here contacted GitHub. The filter assumes the documented shape of the check-runs answer (`name`, `status`, `conclusion`, `app.slug` of `github-actions`). If a first rehearsal deploy is refused although CI is green, check the shape first; the failure mode is a refusal, never an unintended deploy. Also note that `hygiene.yml` cancels an in-progress run on a newer push to `main`, so an older commit of `main` may have a cancelled `CI Passed` and will be refused until its checks are re-run.
- **UF-1.** Besides the cap, a cut line also redacts from any quote left without a partner (the partner may have been in the dropped part), so the start of a quoted value that closes beyond the cap is not shown; both behaviours have unit tests. Not changed, noted by the audit: `replace()` still falls back to the unredacted subject when a PCRE call returns `null`. With the cap that needs invalid UTF-8 passed straight to `sanitise()`; `firstLine()` already yields an empty line for invalid UTF-8. A fail-closed fallback would be a separate, small change.
