## Accomplishments

- `php artisan lang:add cs` generated `lang/cs.json` and six PHP files in `lang/cs/`: `actions.php`, `auth.php`, `http-statuses.php`, `pagination.php`, `passwords.php`, `validation.php`. No English files were published; nothing was hand-translated or edited.

- 20 new tests in `tests/Feature/Localisation` (full suite 213 passed, Pint and Larastan level 8 clean, `scripts/check-sensitive.sh` clean).
- ICU runtime in DDEV: ICU 76.1, PHP 8.5. `1234.5 CZK` comes out as `31 c2a0 323334 2c 3530 c2a0 4b c48d`, so the grouping space and the space before `Kč` are both **U+00A0** (not U+202F). The tests fold U+00A0 and U+202F to a plain space, so they also hold on an ICU build that emits U+202F.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] The local `.env` carries `APP_LOCALE=en`, so the suite ran in English**
- **Found during:** Task 1 (first test run)
- **Issue:** the git-ignored local `.env` (created by the Laravel installer before 02-02 added the keys to `.env.example`) has `APP_LOCALE=en`, `APP_FAKER_LOCALE` likewise; `.env` overrides the new config defaults, so `app()->getLocale()` was `en` and three tests failed. The plan's acceptance criterion greps only the config default.
- **Fix:** `phpunit.xml` pins `APP_LOCALE=cs`, `APP_FALLBACK_LOCALE=en`, `APP_FAKER_LOCALE=cs_CZ`; a subprocess test evaluates `config/app.php` with the variables removed, which proves the "environment omits APP_LOCALE" truth without relying on either file. The local `.env` itself was not touched (not part of the repository, and reading or editing it is out of bounds for the executor).
- **Files modified:** `phpunit.xml`, `tests/Feature/Localisation/LocalisationTest.php`
- **Verification:** `pest tests/Feature/Localisation` green; full suite 213 passed
- **Committed in:** `7616aea`

**2. [Rule 3 - Blocking] Pint failed on the generated lang files**
- **Found during:** Task 1
- **Issue:** `binary_operator_spaces` flags the aligned arrows laravel-lang writes in all six `lang/cs/*.php` files; the lint gate failed.
- **Fix:** `pint.json` `notPath` lists the six generated files by exact path (hand-written lang files stay linted). Reformatting them instead would produce a noisy diff on every `lang:update`.
- **Files modified:** `pint.json`
- **Committed in:** `7616aea`

**3. [Rule 1 - Bug] Date-time picker default contains seconds**
- **Found during:** Task 2
- **Issue:** `DateTimePicker` shows seconds by default, so it reads the `...WithSeconds` default (`M j, Y H:i:s`), not the plain date-time default the plan's provider spec configures. Pickers would have shown the English month format.
- **Fix:** the provider also sets `defaultDateTimeWithSecondsDisplayFormat('j. n. Y H:i:s')` and `defaultTimeWithSecondsDisplayFormat('H:i:s')`; tests cover both the with- and without-seconds forms.
- **Files modified:** `app/Providers/LocalisationServiceProvider.php`, `tests/Feature/Localisation/FormatsTest.php`
- **Committed in:** `7bf4f31`

**4. [Plan adaptation] Picker configuration through default formats**
- **Issue:** the plan's artifact table says "display `j. n. Y H:i`" for `DateTimePicker` and "display `j. n. Y`" for `DatePicker` (that is `displayFormat()`). Since `DatePicker` extends `DateTimePicker`, a `displayFormat()` set on the parent would also apply to date-only pickers depending on configuration order.
- **Fix:** default-format setters on one `DateTimePicker::configureUsing`; same visible result for the three picker kinds, without the ordering hazard. Recorded as a key decision.

**5. [Rule 2 - Missing critical] A passing fixture enum**
- **Issue:** with the only fixture failing, a checker that reports everything would pass the plan's tests. Added `TranslatedFixtureEnum` (labels from the generated `pagination` keys) and a test that expects no problems for it.
- **Files modified:** `tests/Support/Fixtures/TranslatedFixtureEnum.php`, `tests/Feature/Localisation/EnumLabelsTest.php`
- **Committed in:** `7bf4f31`

**6. [Plan adaptation] The empty-login test sits in `LocalisationTest.php`**
- The plan lists no test file for the Livewire login case in Task 2; it was added to `LocalisationTest.php` next to the login page test from Task 1. The checker additionally flags a label equal to a backed enum's raw value, a stricter rule than the plan's "empty, `enums.`-prefixed or key-like".
