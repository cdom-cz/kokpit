Rulings made in this plan (recorded):
- R-17-05-1 (tasks): `TaskResource::getGlobalSearchEloquentQuery()` keeps its `whereNull(deleted_at)` and `with(['project' ...])` and appends `->orderByRaw('('.$status.' = ?) ASC', [ProjectStatus::Done->value])` with `$status = (new Task)->qualifyColumn('status')` (false sorts before true in PostgreSQL, so active rows come first), then `->orderByDesc((new Task)->qualifyColumn('created_at'))->orderByDesc((new Task)->qualifyColumn('id'))`. Tasks had no order at all before; newest first is the deterministic order inside each part (ruling, flagged in the SUMMARY). The raw call carries `// @phpstan-ignore argument.type (the column is qualified by the model, the value is bound)`, the precedent of `TaskColumns::orderByPriority()` and the TaskResource default sort; if PHPStan reports the ignore as unmatched, drop the comment.
- R-17-05-2 (projects): `ProjectResource::getGlobalSearchEloquentQuery()` gets the same done-last `orderByRaw` (status of `Project`) inserted BEFORE its existing `->orderBy((new Project)->qualifyColumn('key'))`, which stays as the order inside each part; same ignore comment rule.
- R-17-05-3 (placement): both keys live in the base query that Filament's `getGlobalSearchResults()` narrows with the search constraints and limits to 50 (`$globalSearchResultsLimit`), so the order decides which rows survive the limit (research Pitfall 7). `ClientResource` is not touched: clients have another status vocabulary and D-10 names tasks and projects.
