Decisions carried in (locked, not re-asked):
- D-02: starting stops the running timer and keeps its entry, no confirmation; a start needs only a client.
- TI-07 (requirement): at most one running timer per user, enforced in the database.
- Scope guard (ROADMAP mapping note): Phase 6 stores no money on a time entry; the TI-08 rate and amount snapshot is Phase 10. TI-08 here means exact seconds (this plan) and the effective-rate resolution (plan 06-05).

Decisions made in this plan (research recommendations adopted, recorded):
- Open Question 5 / A1: the database CHECK is `ended_at IS NULL OR ended_at >= started_at`, so zero length is allowed. A start in the same second as the running entry stops it at the same instant and KEEPS the zero-length entry (D-02 says the stopped entry is kept). Manual entries (plan 06-04) require Konec strictly after Začátek; only an auto-stop can produce zero length.
- One migration file adds the two composite unique keys the foreign keys need (`projects_id_client_unique (id, client_id)`, `tasks_id_project_unique (id, project_id)`; `tasks_ident_unique` is `(id, project_id, depth)` and does not fit) and then creates `time_entries`, because the keys exist only for this table.
- The per-user advisory lock is taken inline in `StartTimer` in this plan; plan 06-03 moves it into a swappable `TimerLock` service for the concurrency mutation run.
- `BillingState` is a storage enum (`unbilled`, `billed`) without a label; plan 06-07 adds the display enum `BillingBadge` with the three UI-SPEC labels.
- The `TimeEntry` relations to client, project and task include archived rows (`withTrashed()`), because archiving never stops a running timer (research A13, Pitfall 5).

Fictional data only: descriptions assembled at runtime (`Example work ` plus a random suffix), `exampleEmail()` addresses. Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
