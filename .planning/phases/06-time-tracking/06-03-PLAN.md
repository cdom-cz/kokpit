Prove with real parallel processes that concurrent starts never leave two running timers for one user, and give a lost race a typed, Czech error.

Purpose: roadmap success criterion 1 says "concurrent starts never leave two running timers for one user". The partial unique index is the authority and the advisory lock keeps the race out of the normal case; only a real multi-process run, with a mutation run that removes the lock, shows both.
Output: `TimerLock` (extracted from the two Actions), `TimerRaceLost`, the worker script, the concurrency test and the test-only `UnlockedTimerLock`.
</objective>

Decisions carried in: TI-07 (one running timer per user, DB-enforced), D-02 (concurrent starts must never leave two running timers).

Decisions made in this plan (recorded):
- `TimerLock` is a plain `class`, not `final`, resolved from the container, so the test double `UnlockedTimerLock` extends it (the `TaskBoard` / `UnlockedTaskBoard` precedent). The production classes (`TimerLock`, `StartTimer`) get no test hook.
- Deterministic interleaving, test-only: the mutation run does not rely on natural timing (a timing-dependent `raced > 0` would be flaky). `UnlockedTimerLock`, when the worker passes a rendezvous directory and a party count, registers a listener on the Eloquent `creating` event of `TimeEntry`. That event fires inside `StartTimer` after the user's running row was read under `lockForUpdate()` and before the INSERT; `lock()` arms a one-shot wait for the current call and the listener waits until every party has arrived. Each round starts with no running entry of the user, so no party blocks on a row lock before the rendezvous; all parties have read "nothing running" before any of them inserts, the partial unique index lets exactly one insert win, and every other party gets the unique violation, translated to `TimerRaceLost`. The rendezvous must never be combined with the real `TimerLock` (the second party would wait on the advisory lock and never arrive), so the worker refuses that combination. This replaces the sleep-based widening of the `task-worker.php` precedent with an arrival barrier.
- The worker cleanup deletes the activity rows of the created entries as well (`subject_type = 'time_entry'`), so the test stays green once plan 06-05 adds the activity allowlist to `TimeEntry`.

Fictional data only (worker client name assembled at runtime). Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
