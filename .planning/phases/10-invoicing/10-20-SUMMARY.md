# Phase 10 Plan 20: PDF stored at issue and atomic rollback Summary

**Issuing now renders the PDF from the frozen snapshots, stores it through the hardened upload path as an invoice-owned, Admin-only document and links it from `invoice_admin.pdf_document_id`; any failure rolls back the number, the state, the billing, the document row and the stored object.**

## Accomplishments

- `invoice` is a document owner kind (not shareable, label "Doklad", resolver branch with a shared row lock). The visible-flag CHECK and `constrainForPartner` already exclude it, and `ARCHIVABLE_OWNER_TYPES` leaves it out, so the PDF stays findable for the Admin when the client is archived.
- `StoreGeneratedDocument` writes the bytes to a temp file, wraps it as an `UploadedFile` and goes through `AttachDocuments` (policy, resolver, content MIME detection, limits, object naming). It registers `DB::afterRollBack()` before the upload and removes the objects when the open transaction rolls back; the temp file is removed in every case.
- `DocumentIssuer` has the PDF as its last step: `InvoicePdf::render()`, `StoreGeneratedDocument`, then `pdf_document_id` saved on the document's `InvoiceAdmin` row. The `invoices` row takes no write after the state flip (D-13).
- `IssueContext` carries the Admin; `IssueDocument` passes its actor.
- `IssueRollbackTest` (10 tests): stored document and link, file names by kind and language, Partner invisibility, archived client, and four rollback cases with an empty-disk, empty-media, unchanged-counter and still-reserved-entries assertion each.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical functionality] AttachDocuments leaked an object when a media-library listener failed after the write**
- **Found during:** Task 2 (test "storage fails after the object was written")
- **Issue:** `MediaHasBeenAddedEvent` fires after the object is written but before `AttachDocuments` records the media in its cleanup list, so a failing listener left an orphan object that neither `AttachDocuments` nor the rollback hook knew about.
- **Fix:** `AttachDocuments::store` catches a failure of `toMediaCollection`, records the media row of the document (still readable inside the transaction) in the cleanup list and rethrows. Uses the document's `media()` relation (the app `Media` model has UUID keys; the package base model would cast the key to an integer and compute a wrong path).
- **Files modified:** app/Domain/Documents/Actions/AttachDocuments.php
- **Commit:** febc12b

**2. [Rule 1 - Bug] Existing suites assumed that issuing creates no document**
- **Found during:** full suite
- **Issue:** `PaymentTransactionLockTest` counted all `documents` rows as receipts; `InvoiceIssueConcurrencyTest` cleanup could not delete its client because committed PDF documents referenced it; `DocumentOwnerDeletionTest` and `DocumentsRelationManagerTest` enumerate the owner kinds.
- **Fix:** the lock test counts `transaction` owner receipts only; the concurrency cleanup deletes the PDF document, media row and stored object; the two enumeration tests list the new kind (`invoice` is `immutable`, label "Doklad").
- **Commits:** 759e71c, 341df40

**3. [Scope] StoreGeneratedDocument could not be wrapped by a container binding**
- The plan's rollback behavior 2 ("StoreGeneratedDocument wrapped by a binding that stores and then throws") needs a non-final class. The classes stay `final` (project convention); the failure after the write is injected through the `MediaHasBeenAddedEvent` listener instead, which also found deviation 1. The render failure is injected with a `View::composer` on `pdf.invoice` for the same reason.

**4. [Scope] IssueContext::today() added**
- `IssueDocument::expectedNumber()` and `RecordPayment` used `IssueContext::now()` only for the day. With the actor required they use the new static `IssueContext::today()`.

**Total deviations:** 4 (1 Rule 2, 1 Rule 1, 2 scope). **Impact:** none on the contract of the plan.
