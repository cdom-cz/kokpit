<objective>
The Admin-only half of the invoicing schema, the three links into earlier modules (time entries, transactions, and the stored PDF in documents), with every lifecycle rule enforced by the database and proven with raw SQL.

Purpose: IN-02 and IN-10 (reservation and release are a single column with a lifecycle guard), IN-03 (side data frozen), IN-04 (the PDF link, ruling R-06-6), IN-05 and FI-03 (payments and their income link, both locked as D-19 requires), TI-08 (billed snapshot); D-03, D-04, D-05, D-12 to D-15, D-17, D-19, D-21 and D-23 (the PDF link lives here so the issued invoice row takes no write, plan 10-04 R-04-6); research Pattern 1, 2, 4, 6, 7, Pitfall 2.
Output: three migrations, three schema test files.

Owner confirmation point (ruling R-06-1): a recorded payment and the income booked from it are permanent. Correcting a mistaken payment by deleting it (research Open Question 7) is not adopted because it would delete an income whose amount, currency and invoice link D-19 locks; the application therefore offers no way to undo a saved payment, and the payment modal warns before saving (plan 10-30). The owner confirms this behaviour or decides on a compensating correction instead.
</objective>

Rulings made in this plan (recorded):
- R-06-1 (research Open Question 7, not adopted, to conform to D-19; owner confirmation point in the objective): there is no payment deletion. `kokpit_guard_invoice_payment()` refuses every UPDATE and every DELETE of `invoice_payments`, whatever session setting is present; INSERT is allowed only for an issued invoice or proforma. Payments therefore stay as recorded, and the income booked from them stays tied to them (R-06-5).
- R-06-5 (D-19 "amount, currency and invoice link are locked afterwards", Phase 9 D-14): `kokpit_guard_payment_income()` on `transactions` (BEFORE UPDATE OR DELETE) refuses with KP001, for a row whose OLD `invoice_payment_id` is set: DELETE; and an UPDATE that changes anything other than `transaction_date`, `category_id`, `czk_minor`, `czk_source`, `exchange_rate`, `exchange_unit_amount`, `exchange_rate_date` (the CZK figure follows the date by the Phase 9 rule), `description`, `counterparty`, `document_number` and `updated_at`. For any other row it refuses an UPDATE that sets `invoice_payment_id`, so payment income is created only at insert by `RecordPayment`. This is the finance-side lock every writer meets, including the Transactions API of Phase 09.1; plan 10-19 adds the matching refusals with Czech messages in `UpdateTransaction` and `DeleteTransaction`.
- R-06-2 (research Open Question 9, adopted): rate and amount of a billed entry are snapshotted on billing (manual and invoice billing); entries billed before this phase keep null snapshots and the report falls back to the current rate for them (plan 10-34).
- R-06-3 The reservation state is `invoice_id IS NOT NULL AND billing_state = 'unbilled'`; reserved time counts as unbilled in every existing unbilled query and is only excluded from the picker of other drafts (D-04 "must be explicit"; research Pattern 2). Plans 10-13, 10-34 and 10-40 test the counting.
- R-06-6 (D-21, D-23; moved here from `invoices` by plan 10-04 R-04-6, so the issued invoice row takes no write) The PDF link is `invoice_admin.pdf_document_id` (uuid, nullable, unique, FK `invoice_admin_pdf_document_fk` to `documents` ON DELETE SET NULL). The stored PDF is a rendering of the frozen snapshot, not document data, and D-21 requires that an issued PDF can be deleted after an explicit confirmation and D-23 that it can be regenerated, so the link must change after issue; it changes only in these two ways. `kokpit_guard_invoice_pdf_link()` (trigger `invoice_admin_pdf_link_guard`, BEFORE INSERT OR UPDATE) refuses with KP001: a non-null link while the parent invoice is not issued; a non-null link to a document whose `owner_type` is not `invoice` or whose `owner_id` is not this row's `invoice_id`; a change from one document to another (a regeneration links only when the link is null, plan 10-36 R-36-2); clearing the link while its document still exists (only the FK action after the confirmed deletion clears it). The child guard of `invoice_admin` lists `internal_note`, `internal_note_updated_at`, `pdf_document_id` and `updated_at` as always-mutable (no implied `updated_at`, plan 10-04 R-04-4). Readers reach the link only through `InvoiceAdmin::pdfDocument()` (plan 10-08); a Partner reaches the PDF bytes only through the route of plan 10-38, which reads the link as system after authorising the invoice.
- R-06-4 Transaction link: `invoice_id` and `invoice_payment_id` with composite keys `transactions_invoice_client_fk (invoice_id, client_id) -> invoices (id, client_id)` and `transactions_invoice_payment_fk (invoice_payment_id, invoice_id) -> invoice_payments (id, invoice_id)`, the partial unique index `transactions_invoice_payment_unique` on `invoice_payment_id`, and CHECKs `transactions_invoice_income_check` (a linked transaction is an income with a client) and `transactions_invoice_payment_link_check` (a payment link needs an invoice link).
