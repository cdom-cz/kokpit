## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Plan premise wrong] The unlocked twin does not break the commit-order invariant of R-10.1-10-2**
- **Found during:** Task 1 (the RED run of the mutation)
- **Issue:** The plan expects the queue without the explicit row lock to commit before an edit that is still open. It cannot: the queued row has a foreign key to the invoice, and the key check takes `FOR KEY SHARE`, which the `FOR UPDATE` of the edit blocks until the edit commits. In six mutation rounds the edit always committed first and the queue followed, with or without the explicit read lock. The database already orders the commits, so a harness that judged only the commit order could never fail and would prove nothing.
- **Fix:** What the explicit lock adds is the freshness of the read: without it the Action reads the committed row before it waits at the insert and decides on a document that the edit then changes. The worker therefore also reports the total the queue first read after the barrier (`Invoice::retrieved` listener), and the test requires that figure to equal the total the document was left with. The real Action satisfies it in every round, the twin fails in the first mutation round. The commit-order invariant of the plan is kept as well. The file docblock records the foreign key finding.
- **Files modified:** `tests/Concurrency/invoice-edit-worker.php`, `tests/Concurrency/InvoiceEditSendConcurrencyTest.php`
- **Commit:** `d0bd2ca`

**2. [Rule 3 - Blocking] The queue of the test environment is synchronous**
- **Found during:** Task 1
- **Issue:** `QUEUE_CONNECTION=sync` would run `SendInvoiceEmail` inside the queue process after its commit, send the mail and lock the invoice, which changes the subject of the test.
- **Fix:** the queue role calls `Bus::fake()`; only the queued row is the subject.
- **Files modified:** `tests/Concurrency/invoice-edit-worker.php`
- **Commit:** `d0bd2ca`

**3. [Rule 1 - Test expectation] Assertions of the Partner sweep adjusted to what the pages really print**
- **Found during:** Task 2
- **Issue:** the unit price of an edited line is unchanged (only the quantity doubles), so "the old amount is absent" was wrong for the detail; the invoice number of another client may equal a number of the Partner's own list (the file already documents that).
- **Fix:** the old figure and the shared number are no longer asserted absent; the old line text, the reason and the history are.
- **Files modified:** `tests/Isolation/InvoiceLeakTest.php`
- **Commit:** `a16d10d`
