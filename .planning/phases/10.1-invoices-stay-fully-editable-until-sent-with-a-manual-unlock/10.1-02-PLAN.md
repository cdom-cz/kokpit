Decisions carried in (locked): D-02 (no manual mark-as-sent), D-03 (unlock with a mandatory reason, audited, no auto-relock), D-13 (every unlock and lock audited with who, when, before/after and the reason). Claude's Discretion: names, placement of the unlock action, Czech wording.

Assumptions adopted as the planned default (owner to confirm before execution):
- A1: a credit note is never unlocked.
- A3: a cancelled invoice and a proforma that already has its invoice are not editable even when unlocked, so the unlock refuses them instead of opening a document nobody can edit.
- A12: the audit rows live in the Admin-only activity log; the unlock reason is free text written there on purpose (D-13 overrides the "free text is never logged" precedent T-10-30 for this case).

Rulings made in this plan (recorded):
- R-10.1-02-1 (`UnlockInvoice`): `final readonly class App\Domain\Invoicing\Actions\UnlockInvoice`, `handle(User $actor, Invoice $invoice, string $reason): Invoice`, analog `DeletePayment`. Order: `Gate::forUser($actor)->authorize('update', $invoice)`; the reason trimmed, 10 to 500 characters, else `ValidationException` under `reason` with `invoices.errors.unlock_reason_length`; `DB::transaction`: lock the invoice `lockForUpdate()`; refusals under the key `unlock`: not issued or a credit note `invoices.errors.credit_note_locked` (a draft gets `invoices.errors.not_locked`), not locked `invoices.errors.not_locked`, cancelled `invoices.errors.cancelled_not_editable`, a proforma with `invoiceFromProforma` `invoices.errors.converted_not_editable`; `DB::select("select set_config('kokpit.invoice_unlock', ?, true)", [$locked->id])`; `forceFill(['lock_state' => InvoiceLockState::Open])->save()` (a model save, never a bulk query update); `DB::select("select set_config('kokpit.invoice_unlock', '', true)")`; `InvoiceAudit::unlocked()`; return the refreshed invoice. Docblock with numbered steps and the lock order, as in `DeletePayment`.
- R-10.1-02-2 (`InvoiceAudit`): `final readonly class App\Domain\Invoicing\Support\InvoiceAudit` with static `locked(Invoice $invoice, ?User $causer): void` and `unlocked(Invoice $invoice, User $actor, string $reason): void`; each writes exactly one row through `activity('invoice')->performedOn($invoice)` (+ `causedBy` when a user is known) `->event(...)->withChanges(['attributes' => [...], 'old' => [...]])->log(...)`: event `invoice_locked` with attributes `lock_state` `locked`, old `open`; event `invoice_unlocked` with attributes `lock_state` `open` and `unlock_reason` (the trimmed reason), old `lock_state` `locked`. Nothing else goes into the payload: no token, no e-mail address, no body. Plan 10.1-12 adds `snapshot()`, `everSent()` and `edited()`.
- R-10.1-02-3 (lock audit): the lock step of `SendInvoiceEmail` (plan 10.1-01, R-10.1-01-7) calls `InvoiceAudit::locked($invoice, $row->sender)` (the `InvoiceEmail::sender()` relation over `created_by`) in the same transaction, only when it actually moved the document from open to locked.
- R-10.1-02-4 (detail page, UI copy): in `ViewInvoice::getHeading()` an invoice or proforma that is issued gets a third badge with the label of its `lock_state` (color `gray` when `isLocked()`, `info` otherwise; page code asks `isLocked()` and never names the enum case, see the architecture test of Task 2); `banners()` gains, after the overdue callout: an info callout `invoices.detail.banners.open_for_edits` "Doklad lze upravit, dokud nebude úspěšně odeslán e-mailem." for an issued, open, not cancelled invoice or proforma, and a warning callout `invoices.detail.banners.locked` "Doklad byl odeslán e-mailem a je uzamčen.
