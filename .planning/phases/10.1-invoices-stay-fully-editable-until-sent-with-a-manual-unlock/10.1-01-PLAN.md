<objective>
Move the freeze criterion of an issued document from `state = 'issued'` to a send-driven lock: an issued invoice or proforma stays open until a successfully sent document e-mail locks it, a credit note is locked at issue, and the database enforces both against every writer. This is the tracer of the phase: issue -> open -> send -> locked, through the migration, the issue pipeline and the e-mail job.

Purpose: IN-03 (amended) and IN-11; D-01, D-02, D-08, D-12; the database half of the D-06 owner ruling for credit notes (IN-13); research guard inventory G1 to G6, G13, Pitfalls 1, 7, 10, 11; Runtime State Inventory (backfill).
Output: one migration, the lock enum, the issue and send changes, the lock fixtures, the raw-SQL guard matrix and the migrated frozen-state tests. The amended contract documents (PROJECT.md, REQUIREMENTS.md, .claude/CLAUDE.md) are plan 10.1-11, in the same wave.
</objective>

Settled by owner ruling (locked): D-06 amendment of 2026-10-23 recorded in CONTEXT.md: the currency of a document that already has a payment or a credit note cannot change. D-12 asks the database to hold that invariant for every writer. The payment half is already held by the kept key `invoice_payments_invoice_currency_fk` (plan 10.1-03 keeps it); the credit-note half has no key, because `invoices_credited_client_fk` is on `(credited_invoice_id, client_id)` and a credit note copies its invoice's currency only in PHP, so this plan adds it to `kokpit_guard_invoice_row()` (R-10.1-01-2). Plan 10.1-08 refuses the same change in the Action first, with its own message.

Assumptions adopted as the planned default (owner to confirm before execution; none is dropped):
- A1: a credit note is locked at issue and can never be unlocked or edited.
- A2: backfill: an issued credit note, and an issued invoice or proforma with at least one `invoice_emails` row in state `sent`, becomes `locked`; every other issued document becomes `open`; drafts are `open`.
- A10: the new column `lock_state` on the Partner-readable `invoices` table is acceptable (it carries no reason, sender or time); the unlock reason and the lock history live only in the Admin-only activity log (plans 10.1-02, 10.1-05).
- A11 (requirement ids IN-11 to IN-15 and the IN-03 rewording) is carried by plan 10.1-11 together with the contract documents it changes.
- A13: only the document e-mail job `SendInvoiceEmail` locks; a later e-mail kind (Phase 13 payment confirmation) must not reuse its lock step.

Rulings made in this plan (recorded):
- R-10.1-01-1 (column and checks): `invoices.lock_state varchar(8) NOT NULL DEFAULT 'open'`; `invoices_lock_state_check CHECK (lock_state IN ('open', 'locked'))`; `invoices_lock_state_issued_check CHECK (state = 'issued' OR lock_state = 'open')`; `invoices_credit_note_locked_check CHECK (kind <> 'credit_note' OR state = 'draft' OR lock_state = 'locked')`. A text lifecycle column, not a timestamp, so the existing child guard function compares it unchanged (research Pattern 1).
- R-10.1-01-2 (invoice row guard): new function `kokpit_guard_invoice_row()` behind trigger `invoices_row_guard BEFORE INSERT OR UPDATE OR DELETE ON invoices FOR EACH ROW`, replacing `invoices_frozen_guard`; every refusal `RAISE EXCEPTION ... USING ERRCODE = 'KP001'`, style of `2026_10_17_000500_link_time_entries_to_invoices.php`. INSERT: a row inserted as an issued credit note gets `NEW.lock_state := 'locked'`. DELETE: refused unless `OLD.state = 'draft'` ('an issued document is never deleted'). UPDATE, checked first, whatever the state and lock: when `NEW.currency IS DISTINCT FROM OLD.currency` and `EXISTS (SELECT 1 FROM invoices c WHERE c.credited_invoice_id = OLD.id)` (a credit note, draft or issued, names the row) the write is refused ('the currency of a document named by a credit note never changes'; owner ruling of D-06, 2026-10-23); the lookup runs only when the currency changes, and because a plpgsql function is volatile it sees a credit note committed while the update waited for the row (the credit note's `invoices_credited_client_fk` check takes a key-share lock on the invoice row, which a currency update conflicts with because `currency` belongs to `invoices_id_currency_unique`). UPDATE from a draft: allowed; the flip of a credit note to issued sets `NEW.lock_state := 'locked'`. UPDATE of an issued row: `NEW.state` must stay `issued` and `(to_jsonb(NEW) - open_columns) IS NOT DISTINCT FROM (to_jsonb(OLD) - open_columns)` where the open list is exactly `currency, language, issue_date, taxable_supply_date, due_date, subtotal_minor, vat_minor, total_minor, note, supplier_snapshot, customer_snapshot, bank_snapshot, lock_state, updated_at` (anything else, a future column included, is always-on frozen: 'the number, kind and identity of an issued document never change'). When `OLD.lock_state = 'locked'`: with `NEW.lock_state = 'locked'` any difference at all is refused ('a locked document accepts no write', a timestamp-only write included); with `NEW.lock_state = 'open'` nothing but `lock_state` and `updated_at` may differ, `OLD.kind` must not be `credit_note`, and `current_setting('kokpit.invoice_unlock', true)` must equal `OLD.id::text` ('a document is unlocked only by the sanctioned unlock'). An open row moves to locked freely (locking is always safe).
- R-10.1-01-3 (child guards): drop and re-create `invoice_items_parent_guard` and `invoice_item_sources_parent_guard` through `Immutability::childGuardTriggerSql(<table>, 'invoice_id', 'invoices', 'lock_state', 'open')` and `invoice_admin_parent_guard` with the unchanged mutable list `['internal_note', 'internal_note_updated_at', 'pdf_document_id', 'updated_at']`. The function `kokpit_guard_child_of_frozen_parent()` is not changed; a draft is always open by `invoices_lock_state_issued_check`, so drafts behave exactly as before.
- R-10.1-01-4 (Admin-only row of an issued document): new function `kokpit_guard_invoice_admin_issued()` behind trigger `invoice_admin_issued_guard BEFORE UPDATE OR DELETE ON invoice_admin`: it reads the parent state `FOR SHARE`; when the parent is `issued`, a DELETE is refused and an UPDATE that changes `invoice_id`, `pay_token` or `card_payment_enabled` is refused (the token is printed in the PDF and the e-mail). The `ON DELETE SET NULL` of `pdf_document_id` stays allowed.
- R-10.1-01-5 (migration order, Pitfall 10): drop `invoices_frozen_guard` (it would refuse the backfill) and the three child guards -> `ALTER TABLE invoices ADD COLUMN lock_state` -> backfill per A2 with one raw UPDATE that does not touch `updated_at` -> the three CHECKs -> the two functions and triggers -> the re-keyed child guards. `invoices_truncate_guard` and every other guard stay. `down()` drops both new triggers and functions, the CHECKs and the column, and re-creates `invoices_frozen_guard` through `Immutability::guardTriggerSql('invoices', 'state', 'draft', [], withUpdatedAt: false)` and the three child guards keyed on `state` / `draft` with their Phase 10 lists, which restores the frozen-at-issue model.
- R-10.1-01-5b (no new `Immutability` builder): the research offered a validated builder for the new row guard; it is not added, because `kokpit_guard_invoice_row()` is one dedicated function with fixed identifiers written once in this migration (no caller-supplied identifier reaches SQL text), the child guards keep using the validated `Immutability` builders, and the D-12 coverage requirement is met by the raw-SQL matrix through `RawSql` in `InvoiceLockGuardTest`. `tests/Unit/Database/ImmutabilityTest.php` stays unchanged.
- R-10.1-01-6 (domain): enum `App\Domain\Invoicing\Enums\InvoiceLockState: string implements HasLabel` with `Open = 'open'`, `Locked = 'locked'`, labels `enums.invoice_lock_state.open` "Lze upravit" and `enums.invoice_lock_state.locked` "Uzamčeno"; `Invoice` casts `lock_state` to it and gains `isLocked(): bool`; `lock_state` is not added to `#[LoggedAttributes]` (lock and unlock are written as explicit audit rows in plan 10.1-02). `DocumentIssuer::issue()` writes `lock_state` in the flip: `Locked` for a credit note, `Open` otherwise.
- R-10.1-01-7 (lock step): in `SendInvoiceEmail::handle()` the bare sent update after `Mail::to(...)->send(...)` becomes one `DB::transaction` that first locks the invoice row (`Invoice::query()->whereKey($row->invoice_id)->lockForUpdate()->firstOrFail()`, the same lock order as every edit: invoice first), then runs the existing conditional sent update, then, only when that update changed one row and the document is issued, carries payment (`kind->carriesPayment()`) and is not locked yet, saves `lock_state = Locked` through the model (never a bulk query update). A failure inside keeps the existing catch: the row goes back to `queued` and the retry may send again (the documented at-least-once guarantee).
