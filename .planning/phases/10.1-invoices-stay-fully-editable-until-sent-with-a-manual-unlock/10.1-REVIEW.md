# Phase 10.1: Code Review Report

**Reviewed:** 2026-10-23T12:00:00Z
**Depth:** standard
**Files Reviewed:** 67
**Status:** issues_found

## Summary

The production code (migrations, the `Invoicing` Actions and Support classes, `SendInvoiceEmail`, the two Filament pages and the entries relation manager) was read in full; the test and language files were scanned for hygiene, weak assertions and fictional-data compliance (`scripts/check-sensitive.sh --all` is clean). The core of the design holds up: the lock order is consistent (invoice row first, then children, e-mail rows, payment links); `UpdateIssuedDocument`, `QueueInvoiceEmail` and `SendInvoiceEmail::markSentAndLock` all serialise on `invoices ... FOR UPDATE`; the unlock setting is transaction-local and cleared; the row guard `kokpit_guard_invoice_row()` refuses frozen-column changes, deletes and non-sanctioned unlocks; Partner policies stay read-only and the Filament pages abort for non-Admins on every Livewire request.

The defects below are at the seams the phase created with code it did not edit. The most serious one is a money-handling hole: the phase relaxed the pin between a payment link and its document's currency, but the card-payment webhook still compares the paid currency only with the link, so a late payment through an old link can be booked in the wrong currency. The rest are a self-inflicted permanent edit block (a queued e-mail that never ages out), an audit gap for post-send bank-account changes, DB-level guard coverage that stops short of cancelled and converted documents, and a send job that can mail a document more than once when the new lock step fails.

## Critical Issues

### CR-01: A late card payment through an old payment link is booked in the document's new currency

**File:** `app/Domain/Payments/Actions/RecordCardPayment.php:113-119` (outside the reviewed list, caused by `database/migrations/2026_10_22_000300_relax_payment_link_currency_key.php` and `app/Domain/Invoicing/Support/IssuedEditFinisher.php:100-127`), booking at `RecordCardPayment.php:165`
**Issue:** Before this phase `payment_links_invoice_currency_fk (invoice_id, currency) -> invoices (id, currency)` guaranteed that a link and its document always share a currency. Migration 000300 removes that key so an open document can change currency, and `PaymentLinks::reconcile()` only deactivates the link locally; the Stripe side is switched off asynchronously and does not cancel a Checkout session the payer already has open. The webhook handler still decides "currency matches" by comparing the event with the link (`$event->currency !== $link->currency`), not with the document, and never looks at the link state. The next check, `$event->amountMinor === $link->amount_minor === $remaining`, is numerically satisfied whenever the edit changed the currency but kept the figure, which is exactly what D-06 and the editor warning promise for typed prices and fixed amounts ("keep their figure"). Example: a 1 000.00 CZK invoice with a manual line is switched to EUR (still 1 000.00); the payer completes the old CZK session (100000 minor CZK); the event matches, and `Money::ofMinor((int) $event->amountMinor, $locked->currency)` books 1 000.00 EUR, marks the invoice paid and records the income in EUR. The `invoice_payments_invoice_currency_fk` key does not help because the payment is created in the document's currency, not the paid one. No test exercises this (`PaymentLinkRecordTest` covers the insert guard only).
**Fix:**
```php
// RecordCardPayment::handle(), step 5: the paid currency must be the link's AND the document's.
if ($event->currency !== $link->currency || $link->currency !== $locked->currency) {
    return $this->record($event, $link, $locked, CardPaymentType::Unmatched, CardPaymentReason::Currency);
}
```
Add a webhook test: open link in CZK, change the document to EUR with the same minor amount, deliver a paid CZK session, expect an `unmatched` / `currency` record and no `invoice_payments` row.

## Warnings

### WR-01: A `queued` e-mail row that never leaves the queue blocks every edit of the document forever

**File:** `app/Domain/Invoicing/Support/IssuedDocumentRules.php:308-321` (read by `editBlocker()` at line 67)
**Issue:** `emailInFlight()` treats every `queued` row as in flight regardless of age, while a `sending` row ages out after `unsent_invoice_email_stale_after`. A queued row whose job was lost (the `afterCommit` dispatch failed, the queue was flushed, the job record was pruned) stays `queued` forever. From then on `editBlocker()` returns `email_in_flight`: "Upravit" disappears, `UpdateIssuedDocument`, `AddEntriesToDraft`, `ReleaseEntries` and `AddFixedAmount` refuse, and nothing in the UI recovers it: the e-mail log offers "resend" only for an effective `failed` row (`InvoiceEmailsRelationManager::effectiveState()` ages out `sending` only), a resend creates a second queued row, and unlocking does not help because the block is independent of the lock. The document is also not locked (nothing was sent), so it is in limbo until someone edits the database. Before this phase a stuck queued row was only a health warning.
**Fix:** Apply the same staleness rule to `queued` (age from `updated_at`/`created_at`) in `emailInFlight()`, `InvoiceEmailsRelationManager::effectiveState()` and the health indicator, so an old queued row counts as failed and can be re-sent, or give the Admin a "mark as failed" action. Minimal change:
```php
$query->where(fn ($q) => $q->whereIn('state', [Queued->value, Sending->value])->where('updated_at', '>', $staleBefore))
```
(a claimed `sending` row refreshes `updated_at`, a `queued` row keeps `created_at`/`updated_at` from insert or from the retry requeue).

### WR-02: A post-send change of the bank account (or the exchange rate) leaves no audit row at all

**File:** `app/Domain/Invoicing/Support/InvoiceAudit.php:89-123` and `175`, `app/Domain/Invoicing/Actions/UpdateIssuedDocument.php:171-176`
**Issue:** D-13 requires every change to a sent document to be audited. `snapshot()` deliberately excludes `bank_snapshot` (T-10.1-18, no bank data in the log), and `UpdateIssuedDocument` silences the model history for an ever-sent document because "the explicit row replaces it". An edit that only sets `reload_bank` (or any bank change that is not accompanied by a currency, date, line or party change) therefore passes through `edited()` with `$new === []`, returns early, and writes nothing: the model history is off and no `invoice_edited` row exists, while the PDF that tells the customer where to pay has been replaced. The destination account of an already-sent invoice is the most fraud-relevant field to change silently. `InvoiceEditAuditTest` asserts only that no bank key appears in a payload, not that a bank-only edit is recorded.
**Fix:** Add a non-sensitive marker to the snapshot that changes when the account changes without logging the account itself, for example `'bank_fingerprint' => $invoice->bank_snapshot === null ? null : substr(hash('sha256', json_encode($invoice->bank_snapshot)), 0, 12)`, with a label in `kokpit.activity.attributes.invoice`. Add a test: ever-sent open document, change the settings account, `reload_bank => true` alone, expect one `invoice_edited` row.

### WR-03: Cancelled invoices and converted proformas stay `open` in the database, so the guards no longer protect them

**File:** `database/migrations/2026_10_22_000100_add_lock_state_to_invoices.php:111-141` (guard), with `IssueCreditNote` (storno) and `ConvertProforma` not touching `lock_state`
**Issue:** Phase 10 froze every issued row, so a storno-cancelled invoice and a converted proforma were immutable at the database level. Now the guard keys only on `lock_state`, and neither the storno nor the conversion locks the document. A cancelled invoice that was never sent, or was unlocked and then cancelled, and every converted proforma that was never sent, remain `open`: their lines, items' sources, dates, parties, currency and totals accept any writer (a future page, a console command, raw SQL) with no `KP001`. The app-level refusals (`cancelled_not_editable`, `converted_not_editable`) and the time-link helper `kokpit_invoice_accepts_time_changes()` compensate only in PHP and for time. D-12 says the guards stay and are "conditional on the lock", and the phase's own premise is that application code is not the only guard (CONTRIBUTING). `InvoiceLockGuardTest` does not cover this case.
**Fix:** Lock the document in the same transaction as the event that makes it uneditable (the open to locked move is always allowed by the row guard): in `IssueCreditNote::storno()` set `lock_state` to `Locked` on the original after the credit note is issued, and in `ConvertProforma` on the proforma. `UnlockInvoice::refuse()` already rejects both, so nothing else changes. Alternatively extend `kokpit_guard_invoice_row()` and the child guard with the storno and conversion predicates. Add a raw-SQL test per case.

### WR-04: The document e-mail is sent before the lock transaction, so a failure of the new lock or audit step re-queues an already delivered mail

**File:** `app/Domain/Invoicing/Jobs/SendInvoiceEmail.php:106-129` (send at 115, lock at 117, requeue at 120-123)
**Issue:** `Mail::to(...)->send(...)` runs first, then `markSentAndLock()` (invoice row lock, sent mark, model save of `lock_state`, `InvoiceAudit::locked()` through the activity log). Any `Throwable` from the lock step, including the new ones this phase added (the row guard, the activity-log insert, a deadlock or lock timeout on the invoice row held by a long edit transaction), is caught by the same `catch`, the row goes back to `queued`, and the retry mails the customer again. The class comment accepts one repeat after a "mark sent" failure, but the lock and audit make that step materially more likely to fail and fail deterministically (for example if the audit write throws), which multiplies into every retry the queue allows. Customers receiving the same invoice several times is a user-visible defect.
**Fix:** Make the post-send step failure-tolerant and idempotent: after the transport succeeded, mark the row `sent` in its own minimal transaction first (conditional update, no invoice lock), then lock the document and write the audit in a second transaction whose failure is logged and retried by a separate small job (or by the next lookup) without ever re-sending. At minimum, catch failures of `markSentAndLock()` separately, do not requeue the row, and report the exception.

## Info

### IN-01: Class comment of the editor still says currency and dates are read-only

**File:** `app/Filament/Resources/InvoiceResource/Pages/EditInvoice.php:92-98`
**Issue:** The docblock says that in issued mode "the currency, the language and the dates are read-only, and 'Uložit změny' hands only the lines and the notes to UpdateIssuedDocument". The code makes all of them editable and also hands over parties, currency and the bank refill flag (`issuedValues()`, `documentSection()`).
**Fix:** Update the paragraph to the current behaviour (D-06) so the next reader does not "restore" the old restriction.

### IN-02: The payer-only taxable-supply path is unreachable from the editor

**File:** `app/Filament/Resources/InvoiceResource/Pages/EditInvoice.php:953-957`, `app/Domain/Invoicing/Actions/UpdateIssuedDocument.php:288-303`
**Issue:** D-06 lists the taxable supply date as editable, but the editor renders it `disabled()->dehydrated(false)` and `DocumentIssuer` always issues with `taxable_supply_date = null`; the payer mode is blocked at issue (`vat_payer_unsupported`). `taxableSupplyDate()` and its payer branch are therefore dead code until VAT payer support exists.
**Fix:** Note the dependency in the method comment, or remove the branch until the payer mode lands, so a half-wired date does not get relied on.

### IN-03: The history shows prices and totals as raw minor units

**File:** `lang/cs/kokpit.php` (`activity.attributes.invoice.item_fields.unit_price_minor`, `line_total_minor`), `app/Domain/Invoicing/Support/InvoiceAudit.php:98,116-117`
**Issue:** The audit payload stores `total_minor`, `items.N.unit_price_minor` and `items.N.line_total_minor` as integers and the label only says "(v nejmenších jednotkách měny)". An Admin reading "150000 -> 120000" cannot tell the currency without opening the document, and the currency can itself be among the changed keys.
**Fix:** Format money in `ActivityPresenter` for keys ending in `_minor` using the `currency` of the same row (new value if changed, otherwise the stored one), or add a `currency` entry to every `invoice_edited` payload.

### IN-04: The relation-manager toast claims the PDF was re-created even when nothing was released or added

**File:** `app/Filament/Resources/InvoiceResource/RelationManagers/InvoiceEntriesRelationManager.php:289-302`
**Issue:** `successToast()` always appends `edit_issued.saved` ("Změny jsou uložené. PDF bylo vytvořeno znovu, doklad nebyl odeslán.") for an issued document. `ReleaseEntries` returns 0 early and `AddEntriesToDraft::addToIssued()` returns `['entries' => 0, ...]` before the finisher when no entry was claimed, so in those cases nothing was saved and no PDF was made.
**Fix:** Branch on the returned count: for 0 entries show a neutral "nothing changed" notice and skip the body and the `invoice-payment-saved` dispatch.

### IN-05: `reload_bank` is judged against the old currency when the same save changes the currency

**File:** `app/Domain/Invoicing/Actions/UpdateIssuedDocument.php:265-275` and `153-155`
**Issue:** `header()` resolves the refill with `$this->snapshots->bank($locked->currency)` before the model carries the new currency. If the old currency has no account in the settings (an account removed since issue) but the new one does, a save with both `reload_bank` and `currency` fails with `bank_missing` for the old currency, although `$change['bank']` would overwrite the snapshot anyway at line 154.
**Fix:** In `header()` skip the `reload_bank` lookup when `array_key_exists('currency', $data)` resolves to a different currency (or move the refill after `currencyChange()` and use the effective currency).

### IN-06: Test harness weaknesses

**File:** `tests/Concurrency/InvoiceEditSendConcurrencyTest.php:365-408`, `tests/Arch/InvoiceUnlockPathTest.php:20,57-63`
**Issue:** (a) Both concurrency tests depend on wall-clock windows (a 5 s barrier, 0.35 s queue offsets, a 0.6 s `pg_sleep`, `expect($queuedAfterEdit)->toBeGreaterThan(0)` and a mutation run that may find no defect in 6 rounds); on a loaded CI runner they can flake in either direction. (b) The arch test confines the lock write by the literal token `InvoiceLockState::Locked`; a writer using the string `'locked'` or an alias import bypasses the scan, and nothing scans for writers of `lock_state` by column name.
**Fix:** (a) Replace the sleeps with a deterministic handshake (the edit worker signals through a file or an advisory lock once it holds the row, the queue worker starts only then) and keep the mutation run as the proof the harness can fail. (b) Also scan `app` for `lock_state` and `'locked'` assignments and allowlist the same three files.
