Rulings made in this plan (recorded):
- R-16-01-1 (column): migration `2026_10_28_000100_add_document_emails_enabled_to_clients_table.php` adds, with `Schema::table('clients', ...)`, `$table->boolean('document_emails_enabled')->default(true)` (NOT NULL by default). The default alone enables every existing row; there is no UPDATE. `down()` drops the column. The header comment names D-01 and D-05, says why no backfill is needed and that the column is Admin-only (the `clients` table is `DeniesPartners`). Fictional data only.
- R-16-01-2 (model): `Client` gains `@property bool $document_emails_enabled`, the name `'document_emails_enabled'` right after `'online_payment_enabled'` in both `#[Fillable([...])]` and `#[LoggedAttributes([...])]`, and the cast `'document_emails_enabled' => 'boolean'`. The allowlist entry is the whole audit (P16-02): `LogsAllowlistedActivity` writes one `updated` row with the old and new boolean, the causer and the time; no new writer.
- R-16-01-3 (input): `ClientInput::attributes()` adds `document_emails_enabled` only when `array_key_exists('document_emails_enabled', $data)` and the value is not null, as a `(bool)` cast; otherwise the key is left out of the returned attributes, so `UpdateClient` keeps the stored value (research Pitfall 1: the online-payment idiom that reads a missing key as false must not be copied). `CreateClient::withDefaults()` sets `document_emails_enabled` to true when the key is absent or null, beside the `online_payment_enabled` default; the `ClientData` phpstan type gains `document_emails_enabled?: bool|null`. `ClientResource::actionData()` maps the form value as `(bool) ($data['document_emails_enabled'] ?? true)`.
- R-16-01-4 (gate): new `App\Domain\Invoicing\Support\ClientDocumentEmails`, `final readonly class` with three static methods:
  `enabledFor(string $clientId): bool` reads `Client::query()->withTrashed()->whereKey($clientId)->value('document_emails_enabled')` on every call and answers true only for `true`;
  `enabledForInvoice(string $invoiceId): bool` reads the `client_id` of the invoice fresh (`Invoice::query()->whereKey($invoiceId)->value('client_id')`) and then `enabledFor()`; a missing invoice answers false;
  `allows(?Client $client): bool` answers `$client !== null && $client->document_emails_enabled === true` for a model that was just read from the database with the column (an eager-loaded list relation, or the client `QueuePaymentConfirmation` reads in the payment transaction).
  Fail-closed (research assumption A4, decided here): a row that cannot be read answers false, "do not send", the same outcome `QueuePaymentConfirmation` already gives (a `skipped` row) when it cannot read the client; the restrict foreign key of `invoices.client_id` makes a missing row impossible in practice. The class never enters the system context itself: its callers are Admin requests and `KokpitJob` jobs, which already run in it. The class docblock names D-01 (only the document e-mail and payment confirmation paths ask it; invitation, password reset and task notifications never do), D-06, D-07, the fresh read (the switch may change inside the grace window of a confirmation) and the fail-closed ruling.
- R-16-01-5 (form and detail): in `ClientResource::form()` a `Toggle::make('document_emails_enabled')` directly after the `invoice_email` TextInput, label `kokpit.clients.fields.document_emails_enabled` ("Odesílat doklady e-mailem"), helper `kokpit.clients.hints.document_emails_enabled` (says that off means invoices, proformas, credit notes and payment confirmations with the cash receipt are not e-mailed and are handed over by hand, while invitations, password resets and task notifications of the client's users still go out), `->default(true)`, `->columnSpanFull()`. In the "terms" infolist section an `IconEntry::make('document_emails_enabled')->label(...)->boolean()` right after the `invoice_email` TextEntry. On `ViewClient` a `getHeading()` override: when the record's switch is off it returns an `HtmlString` of the escaped parent heading text followed by a Blade-rendered `<x-filament::badge color="warning">` with `kokpit.clients.badges.document_emails_off` ("E-maily s doklady vypnuté"), the shape `ViewInvoice::getHeading()` uses; when on it returns `parent::getHeading()` unchanged. No table column (D-05).
- R-16-01-6 (copy): `lang/cs/kokpit.php` gains `clients.fields.document_emails_enabled`, `clients.hints.document_emails_enabled`, a new group `clients.badges` with `document_emails_off`, and `activity.attributes.client.document_emails_enabled` = "Odesílání dokladů e-mailem" (the presenter prints booleans as `ano`/`ne`).
- R-16-01-7 (factory): `ClientFactory::definition()` gains `'document_emails_enabled' => true`, and a state `withoutDocumentEmails(): static` sets it to false, so in-memory models carry the value. Later plans use `InvoiceFixtures::client(['document_emails_enabled' => false])` or this state.
