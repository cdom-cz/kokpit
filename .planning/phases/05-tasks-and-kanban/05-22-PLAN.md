UUID v7 ordering assumption, checked in code during planning:
- `app/Domain/Shared/Models/Activity.php` uses `HasUuids`; `Illuminate\Database\Eloquent\Concerns\HasUuids::newUniqueId()` returns `Str::uuid7()`; `Str::uuid7()` calls the factory set by `Str::createUuidsUsing(static fn () => Uuid::uuid7())` in `app/Providers/ModelConventionsServiceProvider.php`. The database default `uuidv7()` of `activity_log.id` is not used for these rows.
- `vendor/ramsey/uuid/src/Generator/UnixTimeGenerator.php` (ramsey/uuid 4.9.4): when the millisecond is not later than the last one, `generate()` calls `increment()` instead of re-randomising, so ids built by one PHP process are strictly increasing. PostgreSQL compares `uuid` values bytewise, which is that order.
- Pest runs these tests in one process (no parallel option in `phpunit.xml` or `tests/Pest.php`) with the sync queue, so every activity row of a test is written by the same process. Across processes the ids are only millisecond-ordered; nothing here relies on that.
