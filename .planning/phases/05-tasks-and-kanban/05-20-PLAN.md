Serialized after 05-19: every application plan runs Pest in the single DDEV project against the shared `kokpit_test` database, so no two plans of this phase run in parallel.

Interpretation of "where applicable" (Claude's discretion, stated so the owner can narrow it later in one place, `TaskPolicy::editDescription`): every task the Partner may open, whatever its status (D-01: statuses switch freely, nothing else is locked by status), its requester or its assignee, subtasks included. An archived task stays read-only for everybody (A9), and the Admin keeps editing through the existing edit page.

Lock order: `UpdateTaskDescription` takes only the row lock of the task (`lockForUpdate` through the scoped query). It writes neither status nor position, so the board lock rule of CONTRIBUTING ("Board") does not apply, and it never waits for the board lock while holding the row, so it cannot deadlock with `UpdateTask` (board lock, then row).

History: the Task model never logs the description (`#[LoggedAttributes]` leaves it out, and `LogsAllowlistedActivity` writes no row for a save that changes only unlisted attributes). The change is recorded as one manual activity row through the package logger with the event `description_changed` and no properties; `KokpitLogActivityAction` sets the source on manual rows as on model events (see `tests/Feature/Operations/ActivitySourceTest.php`).

Fictional data only (public AGPL repository): names come from `Canary` and the factories, texts are assembled at runtime from fragments (no line of a test file may look like a payload constant or a real value), e-mail addresses only under example.com. Run `scripts/check-sensitive.sh` before every commit; never bypass the lefthook hook. Everything written in `.planning/` stays in English; Czech appears only in `lang/cs`.
