Rendering facts, measured by the planner in the DDEV container (read-only probe, nothing written) and to be relied on:
- Mail. `MailMessage::render()` echoes each line through Blade inside `Illuminate\Mail\Markdown::render`, which HTML-encodes it (`EncodedHtmlString`), and then parses the result as Markdown. Raw HTML in a value is therefore already inert in the mail; the live vector is Markdown syntax: a value holding a Markdown link and a Markdown image produced two live attributes pointing at the probe host. The current `escapeMarkdown()` neutralises that, but because it also puts a backslash in front of `<` and `>`, the mail then shows the literal text "&lt;" for a "<" (a backslash before the renderer's entity escapes its ampersand). The same escaper without `<` and `>` in its character set gave zero live attributes and the exact text "A < B & C". Do not apply `e()` to mail lines: it double-encodes ("A & B" would read "A &amp; B").
- Bell. Filament renders the stored title and body with `str(...)->sanitizeHtml()` and its permissive global config (`vendor/filament/notifications/src/Notification.php`, `toEmbeddedHtml`), so an unescaped anchor, image and styled span stayed live (four live attributes, two style attributes). Wrapped in `e()` they rendered as exact visible text with no live attribute. `TaskChangedNotification::bellBody` already does this and is the pattern.
- Subject. The subject is a header, never rendered as markup; it stays the raw title (existing tests pin `$mail->subject` against the raw translation).
- Substring checks are not enough: after the CSS inliner re-serialises the mail, inert text can contain the substring `href="https://...`. Inspect the parsed DOM (PHP 8.5 `Dom\HTMLDocument::createFromString`) and look at element attributes and element names, not at the HTML string.

Accepted cosmetic effect, for the SUMMARY's "For the owner": the plain-text alternative of a notification mail shows a backslash before an escaped Markdown character of a value (for example "\(" in a title with brackets), as it already does today for excerpts and change lines. The HTML part, which mail clients show, reads exactly as written.

Flagged assumption (spec-less edge TA-04, unclassified by the probe): comment bodies stay as stored (sanitised HTML through `RichText`); this plan treats only the plain-text excerpt derived from them (`TaskNotifier::excerpt`) as notification text and escapes it per channel. Comment storage, comment rendering on the task pages and the internal flag do not change.
