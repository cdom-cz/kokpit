Rulings made in this plan (recorded):
- R-20-10-1 (`ReasonText`, final, static, Actions/): `length(mixed $reason, int $max, string $requiredKey, string $tooLongKey): int` refuses a string holding NUL with `knowledge.errors.nul_character`, an empty or whitespace-only value (or a non-string) with `$requiredKey`, and a trimmed length above `$max` with `$tooLongKey` and `['max' => $max]`, each as `ValidationException::withMessages(['reason' => ...])`; it returns the trimmed length and never the text. `RedactVersion::reasonLength()` becomes a one-line delegation with its `knowledge.redact.errors.*` keys and `MAX_REASON_LENGTH`; its behaviour is unchanged (RedactVersionTest stays green).
- R-20-10-2 (`DeleteImageForGood::handle(User $actor, KnowledgeArticleImage $image, mixed $reason): void`, `MAX_REASON_LENGTH = 500`): 1 a pending image (article_id null) is not deletable here (ModelNotFoundException: the Obrázky table lists bound images only, the cleanup removes pending ones); 2 the article is read `withTrashed()` and `Gate::forUser($actor)->authorize('update', $article)`; 3 `ReasonText::length($reason, self::MAX_REASON_LENGTH, 'knowledge.images.delete.errors.reason_required', 'knowledge.images.delete.errors.reason_too_long')`, then the local reason variable is set to null; 4 one `DB::transaction`: lock the article row (`withTrashed()->lockForUpdate()`, the lock order of SaveArticle), lock the image row (`whereKey()->where('article_id', ...)->lockForUpdate()->firstOrFail()`), delete its reference rows (query builder on `KnowledgeArticleVersionImage`), delete the image row (query builder), delete the object at `storagePath()` from `Storage::disk()` (a false result throws a RuntimeException inside the transaction, so the rows are rolled back and the image stays complete), write `activity()->useLog($article->getMorphClass())->performedOn($article)->causedBy($actor)->event('image_deleted')->withProperties(['reason_recorded' => true])->log('image_deleted')`; 5 a PDOException or the storage RuntimeException after the rollback surfaces as `ArticleWriteFailed` (SQLSTATE, or the fixed code `storage`), never with the original message. The object is deleted inside the transaction on purpose: for a leaked secret the object must be gone before the success is reported; if the commit itself fails afterwards, the row remains without its object, the route answers 404 and a retry completes (accepted residual, written into the docblock).
- R-20-10-3 (label) `lang/cs/kokpit.php`, `activity.events`: `'image_deleted' => 'Obrázek smazán navždy'` after `'version_redacted'`.
- R-20-10-4 (seam) `KNOWLEDGE_SEAM_IMAGE_REFERENCE_WRITERS` (20-06) gains `app/Domain/Knowledge/Actions/DeleteImageForGood.php`; the test "persists no reason text of a redaction (OD-1)" also asserts that DeleteImageForGood contains `'reason_recorded' =>` (its scan already covers every knowledge file).
