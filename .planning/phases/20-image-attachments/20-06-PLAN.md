<objective>
Bind and index images where the body is written: SaveArticle locks the images its body references, refuses a foreign one, binds the Admin's pending ones to the article and writes one reference row per image for the new version; RedactVersion deletes the reference rows its rewrite removed. An Arch rule keeps every other file away from the reference table.

Purpose: IMG-03 (the cleanup decides from the reference index, never from Markdown, D-16, D-17) and D-04 (no cross-article reuse). A restore is a save, so it indexes the same way and survives deleted images (D-18).
Output: one new Action, two changed Actions, the Arch rule, Feature tests.
</objective>

Rulings made in this plan (recorded):
- R-20-06-1 (`BindArticleImages`, final, Actions/): `lockReferenced(string $body, ?KnowledgeArticle $article, User $actor): list<KnowledgeArticleImage>` reads `ImageReferences::in($body)`; for an empty list it returns []; otherwise it loads those rows with `KnowledgeArticleImage::query()->whereIn('id', $ids)->orderBy('id')->lockForUpdate()->get()` (ids that find no row are skipped: unknown or deleted, D-18); a row is accepted when its article_id equals the article's key, or when its article_id is null and its uploaded_by equals the actor's key; any other row throws `ValidationException::withMessages(['body' => __('knowledge.images.errors.foreign_reference')])` (D-04). On create the article is null, so every bound image is foreign. `bindAndIndex(KnowledgeArticle $article, KnowledgeArticleVersion $version, array $images): void` sets article_id on each accepted pending row with a query-builder update constrained by `whereNull('article_id')` and checks that one row changed (LogicException otherwise: the row is locked); clears `orphaned_at` on every accepted row that has one; inserts one row per accepted image into the reference table through the query builder (version_id, image_id, article_id; id and created_at come from the column defaults). The docblock states the lock order (the caller holds the article row; image rows follow in id order), the superset rule of `ImageReferences::in()` (a uuid inside a code block also binds and indexes) and that nothing is logged.
- R-20-06-2 (`SaveArticle`): constructor gains `private readonly BindArticleImages $images`; `writeVersion()` returns the saved `KnowledgeArticleVersion`; in `create()` the call `$images = $this->images->lockReferenced($body, null, $actor)` follows `acknowledgedRules()`, and `$this->images->bindAndIndex($article, $version, $images)` follows `writeVersion()`; in `update()` the same two calls sit in the content-changing branch only (after `acknowledgedRules()`, with `$locked`, and after `writeVersion()`); the no-op, classification-only and sensitivity-only branches write no version and call neither. The class docblock keeps its text about the fixed order of the existing steps and adds one paragraph beginning "Phase 20 appends" that names the new step: after the guard decision the referenced image rows are locked and a foreign one refuses the save; after the version row the Admin's pending images are bound and every referenced image is indexed for that version (D-02, D-04, D-16).
- R-20-06-3 (`RedactVersion`): inside its existing transaction, right after the two body updates and before the setting is switched off, delete the reference rows of `$version` whose image_id is not in `ImageReferences::in($new)` (query builder, `whereNotIn`; an empty list deletes every row of that version, which is correct for a whole-scope redaction). It does not touch `orphaned_at`: the cleanup stamps it (20-09). The class docblock gains one sentence on the resync.
- R-20-06-4 (seam) `tests/Arch/KnowledgeSeamTest.php`: constant `KNOWLEDGE_SEAM_IMAGE_REFERENCE_WRITERS = ['app/Domain/Knowledge/Actions/BindArticleImages.php', 'app/Domain/Knowledge/Actions/RedactVersion.php']`; function `knowledgeSeamImageReferenceWrites(string $source): list<string>` reports each statement (the tokens up to the next semicolon) that names `KnowledgeArticleVersionImage` (last segment) or the string `'knowledge_article_version_images'` and contains one of the method names `insert`, `insertOrIgnore`, `upsert`, `update`, `delete`, `forceDelete`, `save`, `forceFill`, `create` or `truncate` right after `->` or `::`; tests: no app file outside the list writes the table, every listed writer still writes it, and a synthetic source with an insert, a delete and a forceFill is reported while a read (`::query()->where(...)->exists()`), a comment and a string mention are not.
