Rulings made in this plan (recorded):
- R-20-09-1 (`PruneImages`, final, Actions/): `PENDING_HOURS = 24`, `ORPHAN_GRACE_DAYS = 7`, `CHUNK = 100`; `run(): array{pending: int, stamped: int, cleared: int, deleted: int}` in four passes. Pass 1 (pending): rows with article_id null and created_at older than PENDING_HOURS, by `chunkById`; per row a transaction that re-reads it with `whereNull('article_id')->lockForUpdate()` (a save may have bound it meanwhile: then skip), deletes the object, then the row. Pass 2 (clear): rows with orphaned_at set that `whereHas('references')` get orphaned_at null. Pass 3 (stamp): bound rows with orphaned_at null that `whereDoesntHave('references')` get orphaned_at now. Pass 4 (delete): rows whose orphaned_at is older than ORPHAN_GRACE_DAYS, by `chunkById`; per row a transaction that re-reads it with the same conditions and `lockForUpdate()`, rechecks `references()->exists()` (true: clear the stamp and skip), deletes the object, then the row. Object first, then row; a missing object is no error. Every statement uses the `references` relation, never the reference table name or its model, so the Arch rule of 20-06 sees no write (this Action deletes no reference row; RESTRICT forbids deleting a referenced image anyway). Nothing is logged; the counts are the only output.
- R-20-09-2 (concurrency reasoning, written into the docblock): a save holds the article row and then the image rows `FOR UPDATE` in id order while it binds and indexes (20-06); the cleanup locks one image row at a time and rechecks after the lock, so a save that indexed first makes the recheck see the reference and keep the image, and a cleanup that deleted first makes the save's locked read find no row and skip the reference (D-18). The stamp pass can at worst stamp an image whose reference commits in the same instant; the next run's clear pass and the recheck of pass 4 make that harmless.
- R-20-09-3 (job) `App\Domain\Knowledge\Jobs\PruneKnowledgeImages extends KokpitJob` with `#[Idempotent(how: 'deletes id-derived objects and their rows only after rechecking them under a row lock; a second run finds nothing to delete and a missing object is skipped')]` and `handle(PruneImages $prune): void`. KokpitJob runs it in the system context (the image model denies Partners and a worker has no user). The docblock states the effective delays: pending 24 to 25 hours, orphans 7 to 8 days.
- R-20-09-4 (schedule) `routes/console.php` after the document archive prune: `Schedule::job(new PruneKnowledgeImages)->daily()->name('kokpit-knowledge-image-prune')->onOneServer()` with a comment in the style of the neighbours (what it deletes, D-02 and D-17, runs as system). `tests/Arch/JobContractTest.php`: `PruneKnowledgeImages::class` appended to `EXPECTED_APPLICATION_JOBS`.
