Rulings made in this plan (recorded):
- R-20-05-1 (transport, research Pattern 5 and Alternatives): the browser uploads through a Livewire temporary upload (`$wire.upload('imageUpload', ...)`, the existing private-bucket path with its CORS and one-day expiry rules and the `max:10240` rule pinned by UploadConfigTest) and then calls `storeImageUpload()`. Filament's own MarkdownEditor attachment flow stays off (`fileAttachments(false)`): it inserts a link for a URL without an image extension, stores publicly and exposes a storing method (research, verified in vendor). The pages already use Livewire's WithFileUploads through Filament's InteractsWithSchemas, so the trait does not add it.
- R-20-05-2 (`StoreArticleImage::handle(User $actor, UploadedFile $file): StoredImage`, constructor-injected `ImagePipeline`): 1 `Gate::forUser($actor)->authorize('create', KnowledgeArticleImage::class)`; 2 `$file->getSize()` above `ImagePipeline::MAX_UPLOAD_BYTES` throws `ImageRefused(ImageRefusal::TooLarge)` before reading; 3 `$file->get()` (a false or null read is Failed); 4 `$processed = $this->pipeline->process($bytes)`, then the original string is dropped; 5 id = lowercase `Str::uuid7()`; 6 a new `KnowledgeArticleImage` forceFilled with id, article_id null, uploaded_by the actor, file_name `ImageNames::fileName($file->getClientOriginalName(), $processed->format)`, mime type, width, height, size and sha256 of the processed image; 7 `Storage::disk()->put($image->storagePath(), $processed->bytes)` (default disk, the private s3 disk in production; a false result is Failed); 8 the row is saved; a PDOException deletes the object again and throws `ArticleWriteFailed` with the SQLSTATE only (object first, then row: a row never exists without its object); 9 returns `StoredImage`. The file name and the client MIME type are never used for any decision (D-07). Nothing is logged.
- R-20-05-3 (`StoredImage`, final readonly, Actions/): `id`, `altText`, `width`, `height`, `reference` (= `ImageReferences::markdown($id, $altText)`).
- R-20-05-4 (`ImageNames`, final, static, Images/): `altText(string $clientName): string` takes the base name, drops the last extension, removes every character of the Unicode classes Cc and Cf (controls, bidi overrides, zero-width), removes `[`, `]`, `(`, `)` and the backslash, collapses whitespace to single spaces, trims, normalises to NFC when the intl Normalizer exists, and cuts to 120 characters; it may return an empty string (an empty alt is allowed, D-03). `fileName(string $clientName, ImageFormat $format): string` takes the base name, removes Cc and Cf characters, normalises to NFC, trims and cuts to 255 characters; an empty result becomes `image.` plus the format's extension. The stored file name is shown only in the Obrázky table (20-11) and is never logged.
- R-20-05-5 (page concern) trait `HandlesImageUploads` (Concerns/) with `public mixed $imageUpload = null`, `public bool $imageNoticeVisible = false`, `showsImageNotice(): bool` and `storeImageUpload(): array`; interface `ImageUploadForm` (Concerns/) declares `showsImageNotice(): bool`; both `CreateKnowledgeArticle` and `EditKnowledgeArticle` use the trait and implement the interface. `storeImageUpload()`: takes the property and sets it to null; anything but a `TemporaryUploadedFile` answers the Failed refusal; otherwise calls `StoreArticleImage::handle()` inside `try`, maps `ImageRefused` to its refusal, maps `ArticleWriteFailed` and `League\Flysystem\FilesystemException` to Failed after `report()`, lets `AuthorizationException` pass, and deletes the temporary file in `finally`. Success sets `imageNoticeVisible` to true and answers `['ok' => true, 'id' => ..., 'reference' => ..., 'alt' => ..., 'width' => ..., 'height' => ...]`; a refusal answers `['ok' => false, 'title' => __('knowledge.images.errors.title'), 'body' => __($refusal->messageKey())]`. The method is not renderless: its response re-renders the form so the notice of 20-08 appears and stays across later morphs (a script-unhidden element would be reset by the next morph, research Pattern 5). The trait docblock states Pitfall 8 and that the Partner refusal comes from the page mount and the Action gate.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> Livewire temporary upload (private bucket) | the original file, including its metadata, sits in livewire-tmp until deleted |
| Livewire page -> StoreArticleImage | the page method is callable by any session that reaches the component |
| client file name -> stored row and inserted Markdown | the name is attacker-controlled text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-15 | Elevation of privilege | `storeImageUpload` called by a Partner session or a forged Livewire request | high | mitigate | page mount aborts 403 for a Partner; the Action authorises `create` on the admin-only image policy; Feature tests for both |
| T-20-16 | Information disclosure | the original upload with EXIF left in livewire-tmp | medium | mitigate | the temporary file is deleted in `finally` on every path (tests assert it); a crash in between is bounded by the documented one-day bucket expiry rule (Pitfall 8, accepted residual) |

| T-20-18 | Tampering | inconsistent storage (row without object or object without row) after a failure | medium | mitigate | object first, then row; a failed row insert deletes the object again; the failure surfaces as ArticleWriteFailed without content |
</threat_model>
