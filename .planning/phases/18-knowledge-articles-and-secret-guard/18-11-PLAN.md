Rulings made in this plan (recorded):
- R-18-11-1 (prefix tolerance, CR-01): `PEM_PRIVATE_KEY` keeps its header grammar and its two proven base64 lines. It gains (a) after the closing dashes of the header, optional spaces or tabs and an optional escaped line break (the literal characters backslash and n, or backslash r backslash n) before the real line break; (b) before each of the up to four header-field lines, the optional blank line and each of the two proven base64 lines, a possessive run of up to 40 spaces, tabs and `>` characters; (c) after each proven base64 run, optional spaces or tabs and an optional escaped line break before the real line break or the end of the text. The header itself was never anchored, which is why only the body lines failed. `isBase64Line()` strips the same leading run (spaces, tabs, `>`), a trailing escaped line break and trailing spaces and tabs before its `strspn` check, so the key lines after the two proven ones are covered the same way.
- R-18-11-2 (escaped single-line form, CR-01): new constant `PEM_PRIVATE_KEY_ESCAPED`, reported as `SecretRule::PemPrivateKey` (Blocking): the same header grammar, then an escaped line break, up to four escaped header-field segments (a field name, colon, space, a value without a backslash, an escaped line break), an optional second escaped line break, then exactly sixteen units, each a base64 character or a JSON-escaped slash (a backslash followed by a slash). Fixed count, no unbounded repetition. It runs per line inside `scanPrivateKeys()` on every view, after a cheap `str_contains($line, '-----BEGIN ')` pre-check; a matching line gets one `pem_private_key` finding and is marked covered, so the further escaped base64 chunks on that line give no second finding.
- R-18-11-3 (invisible strip, WR-01): the narrow zero-width class is replaced by a constant `INVISIBLE`, the Unicode Default_Ignorable_Code_Point set written as explicit ranges: U+00AD, U+034F, U+061C, U+115F-U+1160, U+17B4-U+17B5, U+180B-U+180F, U+200B-U+200F, U+202A-U+202E, U+2060-U+206F, U+3164, U+FE00-U+FE0F, U+FEFF, U+FFA0, U+FFF0-U+FFF8, U+1BCA0-U+1BCA3, U+1D173-U+1D17A, U+E0000-U+E0FFF. Explicit ranges, not a Unicode property escape, because the PCRE2 build in DDEV or CI may not know Boolean properties. A private method `fold(string $line): string` strips `INVISIBLE`, applies NFKC and strips `INVISIBLE` again (a compatibility mapping can produce a default-ignorable character: U+FFA0 maps to U+1160); a false from `Normalizer::normalize()` still throws the RuntimeException that becomes `scan_failed`.
- R-18-11-4 (rendered-equivalent view, WR-01): per line the raw view is `fold(line)` as today. The rendered view is derived from the raw view: a backslash before an ASCII punctuation character is removed (the CommonMark escapable set, constant `MARKDOWN_ESCAPE`), then `html_entity_decode()` with `ENT_QUOTES | ENT_HTML5` and UTF-8 decodes decimal, hex and HTML5 named entities, then every line break the decoding produced is replaced by the two literal characters backslash and n (so each view keeps exactly one entry per editor line, and an entity-encoded key is still seen by the escaped PEM rule), then `fold()` again. A raw line with no backslash and no ampersand may skip this work (its rendered view equals the raw one). When no line differs, only the raw view is scanned. Otherwise both private key passes run on each view (the multi-line rule over the view joined by LF, the escaped rule per line), the covered lines are the union of both views, the line rules run on the raw view for every uncovered line and on the rendered view for every uncovered line that differs from its raw view, and findings stay keyed by rule and line. Union, never replacement: no fold may remove a finding the raw view produced (fail closed), at the accepted cost that an Ambiguous raw-view finding can stand next to a Blocking rendered-view finding on the same line. Views are local variables only: the scanner keeps no state and gains no property (`KnowledgeSeamTest` proves no guard class property).
- R-18-11-5 (fixtures, D-05): new static methods on `Tests\Support\SecretFixtures`, every value assembled at runtime from the existing samples and fragments:
  - `prefixedLines(string $text, string $prefix): string`, every line of the text with the prefix
  - `pemPrivateKeyJsonEscaped(bool $escapeSlashes = false): string`, one line: a fictional service-account style object (a `type` key and a `private_key` key holding `pemPrivateKey()` plus a final LF) produced by `json_encode`, with `JSON_UNESCAPED_SLASHES` unless `$escapeSlashes`, so both JSON spellings come from the encoder, never typed
  - `pemPrivateKeyShapes(): array<string, array{string, int}>`, shape name to text and the 0-based offset of the header line inside the text: `plain` (0); `yaml block scalar` (a `tls_key: |` line, then the key with a two-space prefix; 1); `blockquote` (`> ` prefix; 0); `nested blockquote` (`> > `; 0); `list item fence` (`- Example step`, a three-space-indented fence line, the key with a three-space prefix, the closing fence line; 2); `tab indent` (0); `json escaped` (0); `json escaped slashes` (0); `yaml double quoted` (a `tls_key: "` line carrying the header, header and base64 lines ending in a literal backslash-n, continuation lines indented by two spaces, a closing quote after the footer; 0); `markdown escaped header` (a backslash before the header; 0)
  - `markdownEscaped(string $secret): string`, every underscore preceded by a backslash (what rich-text-to-Markdown converters such as league/html-to-markdown emit)
  - `entityEncoded(string $secret, string $entity = '&#95;'): string`, every underscore replaced by the entity
  - `withInserted(string $secret, string $insert, int $offset = 4): string`, the insert placed at the byte offset
  - `secretEvasionShapes(): array<string, array{string, string}>`, shape name to text and expected rule key: Stripe live secret, GitHub token and fine-grained GitHub token, each with Markdown-escaped underscores; Stripe live secret with `&#95;`, `&#x5F;` and `&lowbar;`; AWS access key with U+00AD, U+034F, U+061C, U+200E, U+202E, U+2062, U+2066, U+FE0F and U+E0041 inserted after the four-character prefix, and with the `&shy;` entity there
  Invisible characters are written as `\u{...}` escapes in double-quoted PHP strings, never as raw bytes.
- R-18-11-6 (Ambiguous tier, IN-01): two silent passes of the Ambiguous tier become Ambiguous findings. D-01 already names long random strings and `password=...` as ambiguous, so this implements a locked decision instead of opening a new one, and no Blocking rule changes: both findings stay overridable with one acknowledgment (D-03), and a flag set by that acknowledgment can be cleared by hand (D-04).
  - (a) Long runs: the 256-character run cap of `SecretScanner` (line 84, used at line 319) becomes the window length, constant `RUN_WINDOW_LENGTH` with the value 256. A run of 32 to 256 characters is checked exactly as today. A longer run is checked in consecutive windows of that length from offset 0, plus one final window holding the last 256 characters of the run, so no tail escapes; it is one `high_entropy_string` finding when any window passes the existing hex/UUID exclusion, the three-class mix and the 4.2 bits entropy floor. The loop stops at the first passing window, so the work stays linear in the run length (one `count_chars` per window); the `RUN` pattern stays possessive and unchanged.
  - (b) Quoted values: the value part of `PASSWORD_ASSIGNMENT` becomes a branch-reset group `(?|...)`, so capture group 1 stays the value that `isPlaceholder()` checks and `candidateGroups()` needs no change: a double-quoted value (6 to 128 characters other than the double quote and LF, possessive, then the closing double quote), a single-quoted value (the same with the single quote), or the existing unquoted form (optional opening quote, 6 to 128 characters without whitespace or quotes). The optional `bearer`/`basic` prefix stays in front of the value in every branch. A quoted value with spaces is then one `password_assignment` finding; a quoted placeholder (`<...>`, `${...}`, `{{...}}`, `changeme` and the rest of the existing list) and a quoted value under six characters stay quiet.
  - Accepted cost, recorded: a long base64 blob on one line (an RSA public key, a base64 data URI) and a quoted prose value after a secret-like name now give an Ambiguous finding. The scanner already treats a 64-character certificate line and an unquoted first word of six or more characters after a secret-like name the same way, so the false-positive class does not change; only the silent pass ends. No exemption for `data:` URIs is added, because any exemption would be a place to hide a credential.
  - Fixtures (D-05): `SecretFixtures::longRandomRun(int $length = 336): string`, the first `$length` characters of `base64_encode()` over fresh `random_bytes()` (a new random value on every call, never a literal); `SecretFixtures::quotedPasswordAssignment(string $quote = '"'): string`, the name `db password`, ` = `, the quote, a phrase of short words assembled from fragments whose first word has fewer than six characters, and the closing quote (at HEAD this shape gives no finding, because the unquoted form stops at the first short word).
