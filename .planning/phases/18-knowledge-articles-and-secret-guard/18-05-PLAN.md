- R-18-05-4 (SaveArticle): `final class SaveArticle` with `__construct(private readonly MarkdownNormaliser $normaliser, private readonly SecretScanner $scanner)`.
  - `create(User $actor, ArticleInput $input, bool $acknowledge = false): SaveResult`: `Gate::forUser($actor)->authorize('create', KnowledgeArticle::class)`; in `DB::transaction`: normalise the body, scan it and apply R-18-05-5, then forceFill a new article (kind `ArticleKind::General`, title, body_md, sensitive = input flag or the acknowledgment, version_no 1, edited_at now), save, and forceFill and save the version 1 row (article_id, version_no 1, title, body_md, author_id = actor); the acknowledgment row of R-18-05-5 when applied; returns `Created`.
  - `update(User $actor, KnowledgeArticle $article, ArticleInput $input, int $expectedVersion, bool $acknowledge = false): SaveResult` (the expected version has no default, so no caller can skip the check): `Gate::forUser($actor)->authorize('update', $article)`; in `DB::transaction`: `KnowledgeArticle::query()->whereKey($article->getKey())->lockForUpdate()->firstOrFail()` (the scoped query: an archived article is a `ModelNotFoundException`); authorise again on the locked row; `$locked->version_no !== $expectedVersion` throws `StaleArticle($locked->version_no)` before anything else; normalise; when title and normalised body equal the stored ones: if the flag that R-18-05-5 derives from the input (mark sets it, the manual clear clears it, otherwise the stored flag stays) differs from the stored flag, forceFill only `sensitive` and save (no version, edited_at unchanged) and return `SensitivityChanged`, else return `Unchanged` without any write; otherwise scan and apply R-18-05-5, then forceFill title, body_md, the derived sensitive flag, `version_no` + 1 and edited_at now, save, insert the version row with the new number and author_id = actor, write the acknowledgment row when applied, return `Updated`. Version numbers come from the locked row, never from `SequenceAllocator` or a max() query; `UNIQUE (article_id, version_no)` is the backstop.
  - The caller's instance is refreshed after the transaction (as `UpdateTaskDescription` does). The class docblock states the order, the lock, what is logged, that the title is never scanned (D-02) and that a database failure surfaces as `ArticleWriteFailed`.
  - Write failure (R-18-05-8): the `DB::transaction` call of `create()` and of `update()` runs inside `try { ... } catch (PDOException $e) { throw new ArticleWriteFailed((string) $e->getCode()); }` with `use PDOException;` imported (Laravel's `QueryException` and `UniqueConstraintViolationException` extend `PDOException`, so does the `DeadlockException` that `ManagesTransactions` raises with the original message when a concurrency error hits a nested transaction, and a failing commit throws a bare `PDOException`); the catch sits around the transaction call, so the rollback (or the savepoint rollback inside an outer transaction) has already happened when `ArticleWriteFailed` is thrown, and it never passes `$e` on. Every other exception (`StaleArticle`, `SecretGuardRefused`, `ModelNotFoundException`, `AuthorizationException`, `ValidationException`) passes through unchanged. A private helper that wraps both transaction calls is allowed.
- R-18-05-5 (guard decision): with findings F of the normalised body: any Blocking finding throws `SecretGuardRefused(F, hash)` whatever `$acknowledge` says (D-01); else any Ambiguous finding without `$acknowledge` throws `SecretGuardRefused(F, hash)`; else with `$acknowledge` and at least one Ambiguous finding the save goes ahead with sensitive true and `markedSensitive` true, and writes `activity()->useLog($article->getMorphClass())->performedOn($article)->causedBy($actor)->event('secret_acknowledged')->withProperties(['rules' => sorted unique rule values of the Ambiguous findings, 'version_no' => new version number])->log('secret_acknowledged')` (rule keys only, SEC-03, D-03); `$acknowledge` without any Ambiguous finding changes nothing. Sensitive flag derivation (D-04 fail closed, checker info 4): on `create()` the flag is `sensitive || acknowledged`; on `update()` it is true when this save acknowledges an Ambiguous finding (the acknowledgment wins over a clear request), else false only when `clearSensitive` is true, else true when `sensitive` is true, else the stored flag. So `sensitive` false without the manual clear never clears a stored flag, on a content save and on a save without content change alike; a later save without findings never clears it either. The screens send the manual clear only when the Admin turned the shown toggle off (18-10 R-18-10-1).
