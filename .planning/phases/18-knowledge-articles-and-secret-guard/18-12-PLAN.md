<objective>
Resolve code review finding IN-04, which `18-VERIFICATION.md` names as one of the two review items most relevant to the gap closure: a database failure (`ArticleWriteFailed`) or an article archived in another tab (`ModelNotFoundException`) must reach the Admin as a notice that keeps the typed text and says why, never as Livewire's generic error overlay. Close the related silent data loss found while planning: a NUL byte in a title or body is cut off by the PostgreSQL driver instead of being refused.

Purpose: D-09 promises that a refused save keeps every typed character and explains itself; KB-08 promises that a concurrent change is never handled silently; KB-01 promises that the article stored is the one the Admin typed. The two pages already do this for the stale save and the secret guard, but not for these three cases.
Output: a small `RefusesFailedSaves` trait, two extra catch branches on the edit page, one on the create page, a NUL check in `ArticleInput::from()`, five Czech strings, and Feature proof on both screens.
</objective>

Gap source: code review finding IN-04 (info, disposition `open`), named in `18-VERIFICATION.md` "Gaps Summary" as one of the two review items most relevant to a closure plan. It is not a failed verification truth, so it closes alongside the two gaps in 18-11.

Planner probe (read-only, DDEV, 2026-11-25): a bound text parameter that holds a NUL byte reaches PostgreSQL cut off at the NUL (`select length(?::text)` with a three-byte value whose middle byte is NUL returned 1). The review assumed PostgreSQL refuses such a body with an error; it does not, so the body and its version row would be stored truncated with no message at all.

Decisions carried in (locked): D-09 (a refused save keeps the typed text and offers the current article in a new tab; no overwrite, no merge), D-10 with the owner ruling on A3 (no byte inside code is changed), D-03 (no message carries content). UI-SPEC: the stale save is a persistent warning notification, refused saves keep the user on the edit screen with every typed character, there is no permanent delete in this phase. Claude's Discretion used here: Czech wording, notice status per case.

Rulings made in this plan (recorded):
- R-18-12-1 (shared refusal): new trait `App\Filament\Resources\KnowledgeArticleResource\Concerns\RefusesFailedSaves` with one method `protected function refuseWriteFailure(ArticleWriteFailed $failed): never`. It calls `report($failed)` (the message is fixed and holds only the SQLSTATE, 18-05, so the log keeps the diagnostic the default handler wrote while the exception was uncaught), sends a persistent danger notification with title `knowledge.notifications.write_failed_title` and body `knowledge.notifications.write_failed_body`, and throws `Filament\Support\Exceptions\Halt`. It never puts `$failed->getMessage()` into the notice. It is protected, so the Livewire endpoint gains no callable method.
- R-18-12-2 (edit screen): `handleRecordUpdate()` gains a `ModelNotFoundException` branch and an `ArticleWriteFailed` branch next to the existing `StaleArticle` one. Inside that try only the scoped re-read of `SaveArticle::update()` raises a not-found, and archiving is the only way an article leaves the scope in this phase (no permanent delete exists, UI-SPEC), so the branch means "archived in another tab": a persistent warning notification with title `knowledge.notifications.archived_meanwhile_title`, body `knowledge.notifications.archived_meanwhile_body` and one action `load_current` (label `knowledge.actions.load_current`, the view URL of the record, `shouldOpenInNewTab: true`, exactly like the stale notice; the view screen opens an archived article and offers Restore), then `Halt`. Warning, not danger: it is the stale notice's family (UI-SPEC colour table: stale save = warning). The starting version stays locked and unrefreshed, so a second press is refused the same way. The catch location is fixed by R-18-12-6, not left to the test run.
- R-18-12-3 (create screen): `handleRecordCreation()` catches `ArticleWriteFailed` around the existing `runGuarded()` call and calls `refuseWriteFailure()`. It does not catch `ModelNotFoundException`: `SaveArticle::create()` looks up no record, so a not-found there would be a programming error that must stay loud. This narrows the review's "in both pages" wording on purpose.
- R-18-12-4 (NUL): `ArticleInput::from()` refuses a title or a body that contains chr(0), with a `ValidationException` keyed `title` or `body` and the message `knowledge.errors.nul_character`, after the existing trim and type checks and before the length checks return. Refuse, never strip or replace: changing the byte would alter code content against the owner's ruling on A3 (D-10 applied literally) and would break the hash binding of `GuardsSecrets::saveAnyway()`, which hashes the normalised form body as typed.
- R-18-12-5 (Czech copy, NFC): `notifications.write_failed_title` "Článek se nepodařilo uložit"; `notifications.write_failed_body` "Váš text zůstal v editoru, aby ho šlo zkopírovat. Zkuste článek uložit znovu."; `notifications.archived_meanwhile_title` "Článek byl mezitím archivován"; `notifications.archived_meanwhile_body` "Váš text zůstal v editoru, aby ho šlo zkopírovat. Článek nejprve obnovte a změny pak uložte znovu."; `errors.nul_character` "Text obsahuje neplatný znak (NUL). Odstraňte ho a uložte znovu."
- R-18-12-6 (catch location, located before execution): for the Admin, the not-found of a concurrent archive is raised in `SaveArticle::update()` and at no earlier point of the request, so `handleRecordUpdate()` is the one place that handles it, and no hydration-level or record-resolution override is added to the page. Located by the planner reading the installed sources read-only (livewire/livewire v4.4.9 and filament/filament v5.12.0 as locked in `composer.lock` at b1c6d43):
  1. `vendor/livewire/livewire/src/Features/SupportModels/ModelSynth.php` `hydrate()` restores the `#[Locked]` `$record` with `newQueryForRestoration()`, which Laravel defines as `newQueryWithoutScopes()->whereKey()`: neither the soft-delete scope nor the Partner scope applies, so an archived row restores.
  2. `vendor/filament/filament/src/Livewire/ScopedModelPropertiesComponentHook.php` runs `Resources/Pages/Page::resolveScopedModelProperties()` on every hydrate and before every call. It re-reads the record through `resolveRecord()`, `KnowledgeArticleResource::resolveRecordRouteBinding()` and `getRecordRouteBindingEloquentQuery()`, which removes `SoftDeletingScope` (`KnowledgeArticleResource.php` lines 110-115). The archived article resolves, so the `abort(404)` that `resolveScopedModelProperties()` raises on a `ModelNotFoundException` does not fire.
  3. `EditRecord::hydrate()` and `EditRecord::save()` call `authorizeAccess()`, which is `KnowledgeArticleResource::authorizeEdit()`, and `InteractsWithRecord::hydrateCanAuthorizeAccess()` calls `canAccess()`. The policy is `AdminOnlyPolicy`, and its base `KokpitPolicy::before()` returns true for the Admin for every ability, trashed record or not.
  4. The `abort_if($article->trashed(), 404)` of `EditKnowledgeArticle::mount()` runs on the first request only.
  A test pins this instead of a fallback. The Task 2 test "keeps an open edit screen hydrating after another tab archived its article, so only the save is refused" fails as soon as step 1, 2 or 3 starts to refuse an archived record (for example a later change to the route-binding query or to the policy). The archived-meanwhile test asserts status 200 on every save press, so a not-found that escapes `handleRecordUpdate()` fails it too: in a Livewire test both an escaped `ModelNotFoundException` and a hydration `abort(404)` come back as a 404 response, because the test request broker keeps exception handling for `HttpException` and `ModelNotFoundException` (`vendor/livewire/livewire/src/Features/SupportTesting/RequestBroker.php`). If the hydration pin fails after the merge, the executor stops and reports the failing step as a blocker in the SUMMARY. It does not move the catch, add an override or weaken either test without a new planning round.
