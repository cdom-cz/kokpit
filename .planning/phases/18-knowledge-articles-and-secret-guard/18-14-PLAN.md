Rulings made in this plan (recorded):
- R-18-14-1 (key header line): the multi-line private key pattern constant and the constant of the three allowed prefix characters are removed. New constant `PEM_PRIVATE_KEY_HEADER`: the unchanged header grammar (the text `-----BEGIN `, up to five words of 1 to 20 capitals each followed by one space, `PRIVATE KEY`, an optional ` BLOCK`, five dashes), anchored with `\G`. A line is a key header line when it contains `-----BEGIN ` (cheap pre-check), the pattern matches at the last occurrence of `-----BEGIN ` in the line (`strrpos()`, then `preg_match()` with that offset through `checked()`), and the rest of the line after the match has an empty core (R-18-14-2). So `tls_key: "` plus the header plus an escaped line break, `# ` plus the header, the header in quotes with a comma or a concatenation suffix, and the header with a trailing backslash all qualify, while a sentence that continues after the header does not. The header is still not anchored at the line start, as before; a later public-key header on the same line ends the candidacy, which is correct because the private key header then has text after it.
- R-18-14-2 (core of a line): constant `KEY_EDGE`, every byte that is not an ASCII letter or digit, written as a `trim()` range list (the bytes 0x00 to 0x2F, 0x3A to 0x40, 0x5B to 0x60 and 0x7B to 0xFF). Private method `keyCore(string $line): string`: right-trim `KEY_EDGE`; when the result ends in the two characters backslash and n, drop them and right-trim again; when it then ends in backslash and r, drop them and right-trim again; finally left-trim `KEY_EDGE`. The right side is processed first because the letter n of an escaped line break is alphanumeric. A line is blank when its core is empty (an empty line, or only decoration such as a quote marker, a hash, a dash, two slashes, quotes, a comma, an escaped line break). `isBase64Line()` becomes: core not empty and made only of `BASE64` characters. Every byte of a multi-byte UTF-8 character is 0x80 or higher and in `KEY_EDGE`, so trimming never splits a character. Trimming also removes a plus, slash or equals sign at either end of a real base64 line, which only shortens it by a few characters.
- R-18-14-3 (bounded look-ahead): constants `KEY_LOOKAHEAD` (8), `KEY_FIELD_LINES` (4), `KEY_LINE_MIN_LENGTH` (16), `KEY_SINGLE_LINE_MIN_LENGTH` (40) and `PEM_HEADER_FIELD` (a possessive run of at most 40 non-alphanumeric characters at the start, then a field name of a letter and up to 30 letters or dashes, a colon and a space; anchored at the start). Private method `keyBodyEnd(array $folded, int $header): ?int` looks at most `KEY_LOOKAHEAD` lines after the header line, in order: a blank line is skipped, but a second consecutive blank line ends the look-ahead without a key; before the first body line, up to `KEY_FIELD_LINES` lines matching `PEM_HEADER_FIELD` are skipped as header fields; any other line is a body line when its core is at least `KEY_LINE_MIN_LENGTH` characters long and made only of `BASE64` characters, otherwise the look-ahead ends without a key. The key is proven at the first body line when its core has at least `KEY_SINGLE_LINE_MIN_LENGTH` characters, otherwise at the second body line; write the condition as "this is the second body line, or this line's core has at least `KEY_SINGLE_LINE_MIN_LENGTH` characters" (PHPStan level 8 flags an explicit first-line comparison as always true). The method returns the 0-based index of the proving line, or null.
- R-18-14-4 (cover and report): `scanPrivateKeys()` keeps its signature and return type and no longer joins the view into one text. For every line of the view that is a key header line (R-18-14-1) with a proven body (R-18-14-3), the covered range runs from the header line to the proving line and is extended over each following line for which `isBase64Line()` holds and over one blank line that is directly followed by such a line; every line of the range is covered, and one `pem_private_key` finding is recorded on the header line (1-based), keyed by rule and line as today. The per-line escaped rule (`PEM_PRIVATE_KEY_ESCAPED`, R-18-11-2) stays exactly as it is. The work per view is linear: one header match per line, at most eight look-ahead lines per header, and each extension run belongs to one header because a header line is never a base64 line.
- R-18-14-5 (fixtures, D-05): new static methods on `Tests\Support\SecretFixtures`: `pemPrivateKeySingleLine(int $bytes = 48): string` (the PKCS#8 header with the kind assembled from fragments as in `pemPrivateKey()`, LF, `base64_encode(random_bytes($bytes))` on one line, LF, the footer; 48 bytes give the 64-character Ed25519 body, 1200 bytes a 1600-character body, neither has padding); `wrappedLines(string $text, string $before, string $after): string` (every line of the text between the two decorations, the style of `prefixedLines()`); `base64Line(int $length): string` (a fresh random line of exactly that length made of base64 letters and digits only: the encoding of enough random bytes with the plus and slash mapped to letters, cut to the length before any padding, so the key check trims nothing from it and a boundary test cannot flake). New entries of `pemPrivateKeyShapes()` with the offset of the header line: `ed25519 single line` (0); `ed25519 fenced` (a fence line of three backticks from `str_repeat()`, the key, the closing fence; 1); `ed25519 yaml block scalar` (a `tls_key: |` line, then the key with a two-space prefix; 1); `single long line` (`pemPrivateKeySingleLine(1200)`; 0); `hash comment`, `double slash comment` and `list item` (the RSA-shaped `pemPrivateKey()` with the prefix `# `, `// ` or `- ` on every line; 0); `quoted lines with trailing comma` (every line wrapped in a double quote and a double quote plus comma; 0); `string concatenation` (every line wrapped in a double quote and a literal backslash-n, double quote, space, plus; 0); `backslash continuation` (every line of `pemPrivateKey()` except the last ending in one backslash; 0); `blank line between base64 lines` (the four lines of one `pemPrivateKey()` with an empty line inserted between the two base64 lines; 0). Every key is a fresh runtime value; no line of the file may form a complete header (keep the kind fragments).
- R-18-14-6 (control characters, WR-03): `INVISIBLE` gains the ranges U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F and U+007F to U+009F in front of its existing ranges, written as `\x{...}` escapes like the others. Tab (U+0009) stays because the indent shapes and the patterns use it; LF and CR never reach a line because the body is split before folding, so line numbers cannot shift. NUL is refused earlier by `ArticleInput`; folding it here is defence in depth only. The docblock of `INVISIBLE` names the controls next to the Default_Ignorable set. `secretEvasionShapes()` gains `start of heading` (U+0001), `backspace` (U+0008), `delete` (U+007F), `next line` (U+0085) and `operating system command` (U+009D), each inserted into the AWS-shaped key id like the existing invisible characters and written as `\u{...}` escapes in double-quoted strings, never as raw bytes.
