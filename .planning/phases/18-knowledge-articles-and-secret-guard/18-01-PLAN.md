No DEFERRABLE foreign key from the article to its current version row (planner's call): it would fire only at commit, so the RefreshDatabase Feature tests could never observe it, and `SaveArticle` writes both rows in one transaction under the row lock (proved by 18-05).
- R-18-01-6 (folders): `knowledge_folders` with `id uuid primary key default uuidv7()`, `parent_id uuid null`, `name text not null`, `timestampsTz()`; `knowledge_folders_parent_fk` REFERENCES knowledge_folders (id) ON DELETE RESTRICT; `knowledge_folders_name_check` CHECK (name ~ '[^[:space:]]'); unique index `knowledge_folders_sibling_name_unique` ON knowledge_folders (parent_id, lower(name)) NULLS NOT DISTINCT. Function `kokpit_guard_knowledge_folder_tree()` with trigger `knowledge_folders_tree_guard` BEFORE INSERT OR UPDATE OF parent_id FOR EACH ROW: first `PERFORM pg_advisory_xact_lock(hashtext('knowledge_folders_tree'))`; a `NEW.parent_id = NEW.id` raises 'a knowledge folder cannot be its own parent' (KP003); a recursive CTE walks the ancestors of `NEW.parent_id` and raises 'a knowledge folder cannot move into its own subtree' (KP003) when `NEW.id` is among them; the parent depth is the number of those ancestors (a root parent is level 1, no parent is 0); a second recursive CTE downward from `NEW.id` (bounded by the cap plus one) gives the subtree height (1 for an insert or a leaf); when parent depth plus subtree height exceeds the cap it raises 'knowledge folders nest at most N levels' (KP003). The cap is interpolated into the SQL from `KnowledgeFolder::MAX_DEPTH` (6); KP003 is a new SQLSTATE next to KP001 (frozen rows) and KP002 (project key). The same migration adds `knowledge_articles_folder_fk` (folder_id) REFERENCES knowledge_folders (id) ON DELETE RESTRICT on the articles table; its `down()` drops that FK first.
- R-18-01-7 (models): all three extend `App\Domain\Shared\Models\KokpitModel` and are `final`. `KnowledgeArticle` uses `SoftDeletes` and `LogsAllowlistedActivity` with `#[LoggedAttributes(['kind', 'folder_id', 'client_id', 'project_id', 'client_visible', 'sensitive', 'version_no'])]` (never the title or the body; the class docblock says so and why); no `#[Fillable]` (every content write is a `forceFill` inside the Knowledge Actions); casts `kind` => ArticleKind, `sensitive` and `client_visible` => bool, `version_no` => int, `edited_at` => immutable_datetime; relations `versions(): HasMany` (article_id, ordered by version_no), `folder(): BelongsTo` KnowledgeFolder, `parent(): BelongsTo` self, `client(): BelongsTo` Client, `project(): BelongsTo` Project. `KnowledgeArticleVersion` sets `const UPDATED_AT = null;`, casts `version_no` => int and `created_at` => immutable_datetime, relations `article(): BelongsTo` KnowledgeArticle and `author(): BelongsTo` User. `KnowledgeFolder` has `public const int MAX_DEPTH = 6;` and relations `parent()`, `children()`, `articles()`. The isolation declaration (`PartnerIsolated` with `DeniesPartners`) is part of each class in this plan; the policy registration and the test-side declarations are 18-02. Each class carries an `@property` docblock in the style of `TaskBilling`.
- R-18-01-8 (morph aliases): `MorphMap::MAP` gains `'knowledge_folder' => KnowledgeFolder::class`, `'knowledge_article' => KnowledgeArticle::class`, `'knowledge_article_version' => KnowledgeArticleVersion::class` with their `use` lines in alphabetical position, following the convention in the MorphMap docblock (short singular snake_case table nouns).
