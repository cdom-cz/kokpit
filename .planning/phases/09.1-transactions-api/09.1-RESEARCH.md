## User Constraints (from CONTEXT.md)

### Locked Decisions

Carried forward, not re-opened: Phase 7 API conventions (`/api/v1`, Sanctum bearer tokens of an active Admin, `abilities:` middleware per route group, per-token rate limits `throttle:api-read` / `throttle:api-write`, optional `Idempotency-Key` on create routes through `EnsureIdempotency` with replay/422/409 semantics, cursor pagination default 50 / max 200, `spatie/laravel-query-builder` filters and sorting, Scribe documentation with fictional examples only, errors in Laravel's JSON validation shape with Czech messages); the domain actions are the single place for rules and the API adds no parallel rule set (`RecordTransaction`, `UpdateTransaction`, `DeleteTransaction`, input checked by `TransactionInput`); money is bigint minor units plus ISO 4217 currency; the CZK amount and its CNB snapshot rules (Phase 9 D-12, D-13); transactions are Admin-only and a Partner never reaches finance data (Policies, `DeniesPartners`, canary harness extended with API lines); UUID v7 keys; Phase 7 D-13 reference style (UUID or key, never names).

**Token abilities**
- **D-01:** Two new abilities `finance:read` and `finance:write` are added to `ApiAbility` and offered on the token creation screen next to `time:*`. Transaction and category GET routes need `finance:read`; POST, PATCH, DELETE need `finance:write`. A token with only `time:*` abilities gets 403 on finance routes, and a finance token gets 403 on time routes. - **Reversibility:** costly - ability strings are stored on issued tokens and named in the published API contract.

**Endpoint scope**
- **D-02:** Transactions: list, detail, create, bulk create, PATCH, DELETE, each going through `RecordTransaction`, `UpdateTransaction` and `DeleteTransaction`. Transaction categories: read-only list and detail so a client can discover the UUIDs; category management stays in the UI. Deleting a transaction through the API follows the Phase 9 delete rules (its receipt files are removed with it, as in D-14/D-21 of Phase 9). Receipts and other files are not exposed.
- **D-03:** Client and project are optional on a transaction; a project requires a client and must belong to it (DB CHECK and composite FK from Phase 9). The API refuses a project without a client or of another client with the same field error as the UI.

**Bulk create**
- **D-04:** Bulk create is partial-success, the same contract as time entry batch (Phase 7 D-14): every valid item is saved in its own DB transaction through `RecordTransaction`, invalid items are skipped, the response lists only failed items (item index plus errors) with counts of saved and failed items. It carries `Idempotency-Key` like the single create and counts as one write against the rate limit. Exact status codes (201 all saved, 207 mixed, 422 none saved, as in Phase 7) and response layout follow the Phase 7 batch endpoint. - **Reversibility:** costly - importers rely on the partial-success contract.
- **D-05:** The maximum batch size is **500** items (value in `config/kokpit.php`, separate from the 100 limit of time entry batches); more returns 422.

**Amounts and CZK conversion**
- **D-06 (owner decision during discussion):** The caller can set the exchange rate and the currency directly on the transaction; it is a rate of that one transaction, not a general rate. The client sends `amount_minor` and `currency` plus either (a) an own rate `exchange_rate` (with `exchange_unit_amount`, default 1), from which the CZK amount is computed and the rate stored as the transaction's snapshot with a new `czk_source = custom`; or (b) `czk_amount_minor`, the real bank figure (`czk_source = manual`, no rate stored); or (c) neither, and the CZK amount is computed from the CNB rate of the transaction date (`ExchangeRateConverter`, `czk_source = cnb`; `identity` for CZK). Supplying more than one of (a) and (b) is a 422. A currency without any stored CNB row is accepted when (a) or (b) is given; without either it fails with 422 (nothing is saved without a CZK figure, so the CHECK constraints stay intact). The UI keeps its current behaviour. This needs a migration widening `transactions_czk_source_check`, `transactions_identity_check` and `transactions_snapshot_check` to the new `custom` source (snapshot columns required, date of the rate defaults to the transaction date) and a change to `RecordTransaction` / `UpdateTransaction` / `TransactionInput` so the UI and the API share one rule set. - **Reversibility:** costly - a new `czk_source` value touches the DB CHECKs, the actions, the finance overview labels and the published API contract.
- **D-07:** The transaction response returns `type`, `transaction_date`, `category_id`, `amount_minor`, `currency`, `czk_minor`, `czk_source`, `exchange_rate`, `exchange_unit_amount`, `exchange_rate_date`, `description`, `counterparty`, `document_number`, `client_id`, `project_id`, `created_at`, `updated_at`. It carries no receipt data. The snapshot is shown so the caller can verify what was booked. - **Reversibility:** one-way - published response contract once n8n depends on it.

**References**
- **D-08:** The category is referenced by UUID only (the category list gives the IDs). Client and project are referenced by UUID or by key, resolved by the same resolver as the time entry API (Phase 7 D-13); names are never accepted. A category that is archived, or of another type than the transaction, is refused with the same error as the UI.

**Listing**
- **D-09:** The list uses cursor pagination (default 50, max 200), default sort by transaction date, newest first. Filters mirror the Admin screen: `filter[type]`, `filter[category]` (a parent category includes its children), `filter[client]`, `filter[project]`, `filter[date_from]` / `filter[date_to]`, `filter[currency]`, `filter[czk_source]`. Sorting by date and amount (`sort`). The category list returns the tree data needed to use it (id, parent, name, type, archived flag).

## Summary

Phase 9.1 is almost entirely a second instance of the Phase 7 API pattern, wired to the Phase 9 Actions, plus one real domain change: a new `custom` CZK source. Everything the planner needs for the API shell exists and was read in this session: two route groups per ability in `routes/api.php`, `ApiAbility` (an enum whose cases feed the token form, the `abilities:` middleware and the label/description lang keys), `EnsureIdempotency`, `ApiCursor`, `TimeEntryBatchController` (the partial-success contract), `ReferenceResolver`, Scribe attributes plus fixed example constants, and a test harness (`ApiAccessTest` route walk, `ApiDocumentationTest` pins, canary registry) that is derived from the route table, so new routes fail the existing tests until they are wired correctly. About 8 existing assertions are hard-pinned to "the time API" and must be edited in the same plan that adds the routes (list in Pitfall 1).

The one place that is not mechanical is D-06. Two of the three constraints named in CONTEXT need widening (`transactions_czk_source_check`, `transactions_snapshot_check`); `transactions_identity_check` already excludes `custom` for CZK and allows it for foreign currencies without any change, so it can stay as is (verified by reading it, see D-06 section). The Actions currently take the amount as a major-unit *string* (`amount`, `czk_amount`) and the UI/API field names differ from the error keys the Actions throw (`amount`, `czk_amount`), so the API layer needs a thin mapping in both directions: request `amount_minor` to Action `amount` via `Money::ofMinor()->toMajor()` (exact, no Action change), and error keys `amount` to `amount_minor`, `czk_amount` to `czk_amount_minor`. The `custom` rate is a third branch in `TransactionCzk::resolve()`, reusing `Money::convert()` (the single rounding point), with a new optional `exchange_rate` / `exchange_unit_amount` pair on `TransactionInput`. `UpdateTransaction` needs an explicit rule for what a `custom` transaction does when the amount, date or currency changes, and for how a PATCH switches back to CNB; this research recommends a rule (Pattern 4) and flags it for owner confirmation because it becomes published API behaviour.

Phase 10 is already planned (28 plans, untracked in the working tree) and its plans 10-16 and 10-19 modify `RecordTransaction`, `UpdateTransaction` and `DeleteTransaction`. 9.1 must keep the Action data keys additive (new optional keys only) so those plans stay valid; Phase 10's payment-income refusals will surface through the API as the 409/422 answers this phase documents, which is the natural meaning of the "409" the docs test requires on PATCH and DELETE.

**Primary recommendation:** Build the API as a mirror of the time-entry controllers (thin controller, `TransactionPayload` mapping class, allow-listed Action data, Scribe attributes with fixed example constants), add `custom` as a third branch of `TransactionCzk` with one migration (`2026_10_16_000600_...`), keep the Action data keys additive, and update the pinned API tests (route list, ability map, idempotency list, per_page count, intro limits) in the same plan as the routes.

### Pattern 1: Route groups per ability (extend `routes/api.php`)
**What:** Two new groups, same middleware shape as the time groups, so `ApiAccessTest` keeps passing once its limits map knows the new abilities.
**Existing shape** [VERIFIED: routes/api.php:21-22 and :46]:
```php
Route::middleware(['auth:sanctum', 'abilities:'.ApiAbility::TimeRead->value, 'throttle:api-read'])->group(function (): void {
Route::middleware(['auth:sanctum', 'abilities:'.ApiAbility::TimeWrite->value, 'throttle:api-write'])->group(function (): void {
```
**New:**
```php
Route::middleware(['auth:sanctum', 'abilities:'.ApiAbility::FinanceRead->value, 'throttle:api-read'])->group(function (): void {
    Route::get('transactions', [TransactionController::class, 'index'])->name('api.v1.transactions.index');
    Route::get('transactions/{transaction}', [TransactionController::class, 'show'])->whereUuid('transaction')->name('api.v1.transactions.show');
    Route::get('transaction-categories', [TransactionCategoryController::class, 'index'])->name('api.v1.transaction-categories.index');
    Route::get('transaction-categories/{category}', [TransactionCategoryController::class, 'show'])->whereUuid('category')->name('api.v1.transaction-categories.show');
});
Route::middleware(['auth:sanctum', 'abilities:'.ApiAbility::FinanceWrite->value, 'throttle:api-write'])->group(function (): void {
    Route::post('transactions', [TransactionController::class, 'store'])->middleware(EnsureIdempotency::class)->name('api.v1.transactions.store');
    Route::post('transactions/batch', TransactionBatchController::class)->middleware(EnsureIdempotency::class)->name('api.v1.transactions.batch');
    Route::patch('transactions/{transaction}', [TransactionController::class, 'update'])->whereUuid('transaction')->name('api.v1.transactions.update');
    Route::delete('transactions/{transaction}', [TransactionController::class, 'destroy'])->whereUuid('transaction')->name('api.v1.transactions.destroy');
});
```
The route walk requires exactly one `abilities:` middleware per route and the matching throttle, so never put a finance route into a time group.

### Pattern 2: Thin controller + payload mapping class (copy of `TimeEntryController` / `TimeEntryPayload`)
- Route parameters are plain strings; a private `find()` does `Transaction::query()->whereKey($id)->first()` and `abort(404, __('api.errors.not_found'))` [VERIFIED: TimeEntryController.php `find()`].
- `actor()` reads `$request->user()` and `abort(401)` when it is not a `User`.
- Create answers 201 + `Location: route('api.v1.transactions.show', $id)`; PATCH answers 200 with the resource; DELETE answers `response()->noContent()`.
- The mapping class builds only allow-listed Action keys (`type`, `transaction_date`, `category_id`, `amount`, `currency`, `czk_amount`, `czk_manual`, `exchange_rate`, `exchange_unit_amount`, `description`, `counterparty`, `document_number`, `client_id`, `project_id`), so a smuggled `id`, `created_at`, `czk_source` or `czk_minor` never reaches an Action. (`Transaction` additionally only fills `description`, `counterparty`, `document_number` by mass assignment [VERIFIED: Transaction.php `#[Fillable(['description', 'counterparty', 'document_number'])]`].)
- Mapping details (all in `TransactionPayload`):
  - `amount` = `Money::ofMinor((int) $amount_minor, $currency)->toMajor()` after the currency has been checked with `Money::isKnownCurrency()` (an unknown or lower-case code makes `Money::ofMinor` throw `InvalidArgumentException`; validate `^[A-Z]{3}$` in the rules and raise the Action's `currency` error otherwise). On PATCH without `currency`, use the stored `amount_currency`. `toMajor()` output (`"1250.50"`, `"1500"` for JPY) is accepted by `TransactionInput::decimal()` (a string with a dot passes `Money::fromMajor`'s regex) [VERIFIED: Money.php `fromMajor` regex `'/^-?\d+([.,]\d+)?$/D'`].
  - `czk_amount` = `Money::ofMinor((int) $czk_amount_minor, 'CZK')->toMajor()` and `czk_manual` is left absent (a typed `czk_amount` makes the figure manual, per the `RecordTransaction` docblock).
  - `project_id` = `$refs->writeProject($value)` (UUID or key; an unknown key passes through unchanged so the Action refuses it with its own `project_unavailable`). `client_id` is a UUID only: the resolver says "A client is referenced by UUID only; there is no key." [VERIFIED: ReferenceResolver.php `clientId()` docblock]. D-08 says "UUID or by key" for client and project; for clients the only key is the UUID. State this in the docs.
  - Absent key means "keep stored value" on PATCH (`TransactionInput` uses `array_key_exists`), `null` clears `description`, `counterparty`, `document_number`, `client_id`, `project_id`. Pass a key to the Action only when the request body named it (use `array_key_exists` on the validated array, as `TimeEntryPayload::forUpdate` does).
  - `ConvertEmptyStringsToNull` turns `""` into `null`, so an empty string clears a text field. Document it.

### Pattern 3: Cursor pagination on a `date` and an integer column
`ApiCursor::kindOf()` throws `LogicException` for any column it does not know, and `hasKind()` returns false for a non-string value [VERIFIED: ApiCursor.php, `kindOf` match and `hasKind` first line `if (! is_string($value))`]. The transaction list sorts by a `date` column and by `czk_minor` (integer). Required `ApiCursor` changes:
- add kind `DATE` for `transaction_date`: Laravel writes a cursor value as `(string) $carbon`, i.e. `Y-m-d 00:00:00` for an `immutable_date` cast [CITED: vendor/laravel/framework/src/Illuminate/Pagination/AbstractCursorPaginator.php `ensureParameterIsPrimitive`]; accept `Y-m-d` and `Y-m-d H:i:s` with a zero time; PostgreSQL accepts the latter against a `date` column [VERIFIED: `psql` in ddev: `(date '2026-10-14' = '2026-10-14 00:00:00')` returned `t`, `<` returned `f`];
- add kind `INTEGER` for `czk_minor`: the cursor holds a JSON integer, so the check must accept `is_int` (and reject numeric strings that would be bound as text);
- `ListTransactionsRequest::cursorColumns()` must use the internal ORDER BY column names as cursor keys. If the public sort name is an alias (`amount` mapped to `czk_minor` with `AllowedSort::field('amount', 'czk_minor')`), keep a `SORT_COLUMNS` map in the controller so the request builds `['czk_minor' => INTEGER, 'transactions.id' => UUID]` for `sort=amount`.
- Tiebreaker: `->orderBy('transactions.id', $descending ? 'desc' : 'asc')`, exactly as `TimeEntryController` does (`ID_COLUMN = 'time_entries.id'`). The default order `-transaction_date, -id` is served by `transactions_transaction_date_id_index` [VERIFIED: create_transactions_table.php index `['transaction_date', 'id']`].
- Recommended public sort names: `transaction_date` (default `-transaction_date`), `amount` (internal `czk_minor`, documented as "by the CZK figure so currencies compare"; sorting by `amount_minor` across currencies is meaningless), `created_at`. A sort by `amount_minor` is not recommended. [ASSUMED] naming, see A6.

### Pattern 4: `custom` CZK source in the shared Actions (the D-06 core)
Current state, read this session:
- `TransactionCzk::resolve(Money $amount, string $day, ?Money $manualCzk)` handles CZK (identity), then the manual figure, then the CNB lookup [VERIFIED: TransactionCzk.php].
- `CzkSource` has exactly `Identity = 'identity'`, `Cnb = 'cnb'`, `Manual = 'manual'` [VERIFIED: CzkSource.php:18-20].
- DB constraints today [VERIFIED: create_transactions_table.php:76-78]:
  - `CHECK (czk_source IN ('identity', 'cnb', 'manual'))`
  - `CHECK ((amount_currency = 'CZK') = (czk_source = 'identity') AND (czk_source <> 'identity' OR czk_minor = amount_minor))`
  - `CHECK (CASE WHEN czk_source = 'cnb' THEN exchange_rate IS NOT NULL AND exchange_unit_amount IS NOT NULL AND exchange_rate_date IS NOT NULL AND exchange_rate > 0 AND exchange_unit_amount > 0 ELSE exchange_rate IS NULL AND exchange_unit_amount IS NULL AND exchange_rate_date IS NULL END)`

**Which constraints actually need widening.** CONTEXT lists three; reading them shows two:
1. `transactions_czk_source_check`: add `'custom'`. Needed.
2. `transactions_snapshot_check`: change `czk_source = 'cnb'` to `czk_source IN ('cnb', 'custom')`. Needed.
3. `transactions_identity_check`: `(amount_currency = 'CZK') = (czk_source = 'identity')` already refuses `custom` on a CZK row (true = false) and accepts it on a foreign row (false = false); the second conjunct only concerns `identity`. It needs **no change**. The planner should leave it alone and add a schema test that pins it: custom + CZK rejected (23514), custom + EUR accepted. If the plan keeps the line "widen identity_check" it risks a needless drop/re-add; either is correct, an unchanged constraint plus a test is smaller. [VERIFIED by reading the clause; the test proves it.]

Migration (new file after `2026_10_16_000500_create_document_archives_table.php`; Phase 10 uses `2026_10_17_000400_link_transactions_to_invoices.php` per its plan 10-06, so a `2026_10_16_000600_*` name sorts before it):
```php
DB::statement('ALTER TABLE transactions DROP CONSTRAINT transactions_czk_source_check');
DB::statement("ALTER TABLE transactions ADD CONSTRAINT transactions_czk_source_check CHECK (czk_source IN ('identity', 'cnb', 'manual', 'custom'))");
DB::statement('ALTER TABLE transactions DROP CONSTRAINT transactions_snapshot_check');
DB::statement("ALTER TABLE transactions ADD CONSTRAINT transactions_snapshot_check CHECK (CASE WHEN czk_source IN ('cnb', 'custom') THEN exchange_rate IS NOT NULL AND exchange_unit_amount IS NOT NULL AND exchange_rate_date IS NOT NULL AND exchange_rate > 0 AND exchange_unit_amount > 0 ELSE exchange_rate IS NULL AND exchange_unit_amount IS NULL AND exchange_rate_date IS NULL END)");
```
`down()`: first `UPDATE transactions SET czk_source = 'manual', exchange_rate = NULL, exchange_unit_amount = NULL, exchange_rate_date = NULL WHERE czk_source = 'custom'` (lossless for `czk_minor`), then restore the two original constraints. The activity-log migration `2026_10_14_000200_add_api_to_activity_log_source_check.php` is the precedent for replacing a CHECK by name (it has no `down()`; a reversible one is better here because rows can carry the new value).

`TransactionCzk` change: add a fourth optional parameter (a small readonly value object, e.g. `CustomRate {string $rate, int $unitAmount}`, or an array) and branch order: CZK amount first (identity, any rate ignored); then `manualCzk`; then `custom`; then CNB. For `custom`: `$amount->convert($rate, 'CZK', $unit)` and result `(czk, CzkSource::Custom, $rate, $unit, $day)`, the rate date being the transaction date (D-06). `Money::convert()` throws `InvalidArgumentException` for a rate that is not `^\d+(\.\d{1,10})?$` or is zero and for a unit below 1, and `OverflowException` when the product does not fit [VERIFIED: Money.php `validConversion` and `convert` docblock]. Map the first to a field error on `exchange_rate` and the second to `amount` (as the CNB branch already does).

`TransactionInput` change (additive; existing keys keep working):
- new optional data keys `exchange_rate` (string|null) and `exchange_unit_amount` (int|null, default 1 when a rate is given). Parse in one place with the Czech `finance.transactions.errors.*` message style.
- Hard bounds that the regexes in `Money` do not give: the column is `decimal(20,10)`, so at most 10 integer digits; a larger rate passes `Money::convert()` and then fails in PostgreSQL with 22003 (numeric overflow) = a 500. Validate `^\d{1,10}(\.\d{1,10})?$` and non-zero. `exchange_unit_amount` is a PostgreSQL `integer`: validate `1..2147483647` [VERIFIED: create_transactions_table.php `$table->integer('exchange_unit_amount')` and `$table->decimal('exchange_rate', 20, 10)`].
- conflict: a rate together with a typed CZK figure (`czk_amount` while `czk_manual` is not false) is a field error (D-06: "Supplying more than one of (a) and (b) is a 422"). Enforce it in `TransactionInput` so every caller shares it, and ALSO as a request rule in the API (Laravel `prohibits:` on both fields) so the message points at the API field names.
- currency rule: today `currency()` throws `currency_unknown` when the code is not `CZK` and has no stored CNB row [VERIFIED: TransactionInput.php `currency()`]. D-06 wants a known ISO code accepted when (a) or (b) is given. Compute `czkAmount` and the custom rate first, then call `currency($data, $current, $allowWithoutList)`. Keep the error key `currency` when neither is given and no CNB row exists, so the existing assertion in `TransactionCzkTest` ("refuses an unknown currency and a known code without any CNB row", `toHaveKey('currency')`) still passes unchanged and the UI behaviour is untouched. `Money::isKnownCurrency()` remains the floor for the relaxed case.
- A CZK amount with a rate or a bank figure: the Action silently ignores a figure for CZK ("A CZK transaction needs no rate: it is identity whatever was typed or kept"). For the API contract, reject `exchange_rate`, `exchange_unit_amount` and `czk_amount_minor` when `currency` is `CZK` with a 422 in the request layer (a shape/combination rule), instead of silently ignoring input. The UI already unsets them for CZK (`TransactionResource::actionData`). [ASSUMED] preference, see A5.

`UpdateTransaction::figure()` today [VERIFIED: UpdateTransaction.php `figure()`]: typed figure means manual; manual stays manual until `czk_manual` is false; computed (identity/CNB) recomputes only when date or amount changed (`$changed`), or when it was manual; otherwise returns `[]` (stored figure and snapshot untouched). Note `$changed` ignores a currency change on its own: the amount equality uses `Money::equals`, which includes currency, so a currency change is detected through `! $input->amount->equals($stored->amount)`.

Recommended rule for `custom` (published behaviour, needs owner confirmation, A1):
1. A PATCH that names `exchange_rate` (non-null) makes the transaction `custom` with that rate (and `exchange_unit_amount`, default 1) and recomputes `czk_minor` from the (new or stored) amount.
2. A PATCH that names `czk_amount_minor` (non-null) makes it `manual`, as today.
3. A PATCH that names neither, on a stored `custom` transaction:
   - amount changes, same currency: recompute `czk_minor` with the **stored** rate and unit; keep `exchange_rate_date` (the snapshot is the rate that was fixed for this transaction; the transaction date does not move it);
   - date changes only: nothing recomputes (a custom figure does not depend on the date);
   - currency changes: the stored rate belongs to the old currency, so fall back to the CNB rule (recompute, `cnb`), or refuse with a field error asking for a new rate. Recommend the CNB fallback, which is what a computed transaction does today.
4. Back to CNB: a PATCH with `exchange_rate: null` and `czk_amount_minor: null` both explicitly null means "computed again" (maps to the existing `czk_manual => false`). This needs the API mapping to translate "both named and null" into `czk_manual = false`; it adds no new Action key.
5. The UI (Filament) sends `czk_manual = false` for every computed foreign transaction (`actionData`). Under the existing `$changed` gate, a `custom` transaction edited in the UI keeps its figure and snapshot when amount, date and currency are untouched, and is recomputed through CNB (becoming `cnb`) when one of them changes. That is "the UI keeps its current behaviour" and needs no UI change, but it silently drops an API-set custom rate when the Admin edits the amount in the UI. Recommend a one-line hint in the edit form for a `custom` row and the `custom` badge in the list (`czkCell` currently badges only `CzkSource::Manual`, [VERIFIED: TransactionResource.php `czkCell`]); both are optional polish.

### Anti-Patterns to Avoid
- **Re-implementing a rule in the request class.** Category archived/type mismatch, project-of-client, usable currency, CZK computation all stay in the Actions (CONTEXT: "the API adds no parallel rule set"). The request validates types and syntax only.
- **Returning Action error keys unmapped.** `amount` and `czk_amount` are not API field names. Remap in one function used by the single create, the batch and PATCH.
- **Float money.** Never `(float)`; `amount_minor`, `czk_amount_minor`, `exchange_unit_amount` are integers; `exchange_rate` is a decimal string (see Pitfall 6). `tests/Arch/MoneyBoundaryTest.php` guards the brick boundary.
- **A finance route in a time group or vice versa**, or a route with two abilities: the route walk fails.
- **Implicit model binding** for `{transaction}`: the time-entry controllers deliberately take a string and answer the Czech 404 themselves; follow that.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Minor to major conversion | String math with `intdiv`/`sprintf` | `Money::ofMinor($m, $cur)->toMajor()` | Handles currencies with 0 and 3 fraction digits exactly |
| CZK conversion with an own rate | `bcmul`/float | `Money::convert($rate, 'CZK', $unit)` | The single rounding point (HALF_UP), validates rate shape and unit |
| Idempotency | Own key table | `EnsureIdempotency` + `IdempotencyStore` | Claim/replay/stale takeover already concurrency-tested (`tests/Concurrency/IdempotencyConcurrencyTest.php`) |
| Cursor tamper protection | Own cursor encoding | `ApiCursor::rule()` (extended with two kinds) | Forged cursors would be 500s (22P02/22007) |
| Project key lookup | Query in the controller | `ReferenceResolver::projectId()` / `writeProject()` | Regex-guarded, archived projects resolve |
| Filtering/sorting | Manual `where` from `request()` | spatie `QueryBuilder` + `AllowedFilter::callback` | Allow-list; unknown keys already rejected by the `array:` rule |
| Category subtree filter | A recursive query | One `where category_id = ? OR category_id IN (select id ... where parent_id = ?)` (two levels only, [VERIFIED: `transaction_categories_depth_check`]) | Same clause the Admin screen uses (`TransactionResource::filters`) |
| Partner/Admin gate | Controller `if` | The Actions' `Gate::forUser($actor)->authorize(...)` plus the route group | Already the rule; Partner tokens are refused earlier with 401 |

**Key insight:** every hard part (money rounding, snapshot rules, idempotency, cursor validity, Partner isolation) already exists as a tested component. The risk in this phase is in the seams: key names, pinned tests, and the `custom` rule in `UpdateTransaction`.

## Common Pitfalls

### Pitfall 1: Adding routes breaks existing pinned tests
**What goes wrong:** the following fail the moment the routes and abilities exist, by design:
- `tests/Isolation/ApiAccessTest.php`: `apiWalkProblems()` has `$limits = [ApiAbility::TimeRead->value => 'throttle:api-read', ApiAbility::TimeWrite->value => 'throttle:api-write']` and reports "names the unknown ability" for any other. Add the two finance abilities. The probe test that builds sample bad routes uses `time:*`; leave it.
- `tests/Feature/Api/ApiDocumentationTest.php`: "pins the twelve routes of the API, no more and no fewer" (becomes 20, rename the test); "documents the Idempotency-Key on exactly the two create operations" (expected list gains the two transaction POSTs); "states exactly the limits ..." expects `->toHaveCount(4)` per_page descriptions (becomes 6, one per list route: transactions and transaction-categories) and `documentedLimitProblems` needs the new batch limit.
- `tests/Feature/Api/RateLimitTest.php` first test: add the new config key to the "carries the other API settings" expectations.
- `tests/Feature/Api/ApiTokenScreenTest.php`: expects `abilities` `['time:read']` etc.; the checkbox list now shows four options. Check any assertion that counts the options.
- `lang/cs/kokpit.php` `api_tokens.abilities` and `api_tokens.ability_descriptions`: `ApiAbility::getLabel()` and `ListApiTokens::abilityDescriptions()` read `kokpit.api_tokens.abilities.<value with : replaced by _>` and `...ability_descriptions...`; missing keys render the key string and `LocalisationTest` may flag them. Add `finance_read`, `finance_write` to both blocks.
- `config/scribe.php` `intro_text` and `auth.extra_info` mention only time abilities and "two create endpoints".
- `CONTRIBUTING.md` line "Everything under `/api/v1` lives in `routes/api.php` in exactly two route groups" must say four groups; `tests/Feature/Repo/RepositoryFilesTest.php` checks that the class short names CONTRIBUTING mentions exist, so a new name added there must be a real class.
**How to avoid:** put the route, test-pin and docs edits in the same plan, and run `tests/Isolation/ApiAccessTest.php` and `tests/Feature/Api` before and after.
**Warning signs:** "names the unknown ability finance:read" in the route-walk failure.

### Pitfall 2: Batch duration vs the idempotency stale lock
**What goes wrong:** `idempotency_stale_lock_seconds` is 120 [VERIFIED: config/kokpit.php:158]. A claimed key that is not completed within 120 s can be taken over by a retry, which would run the same 500-item batch a second time while the first is still saving (double rows, because each item commits on its own).
**Why it happens:** the batch has no outer transaction by design, and 500 items do roughly 6-10 queries each (category share lock, client, project, currency check, CNB lookup, insert, refresh).
**How to avoid:** measure a 500-item batch in a test (existing test "saves exactly 100 items" is the template) and keep it far below 120 s; one `RecordTransaction` test in this repo runs in about 0.03-0.04 s including setup [VERIFIED: pest run `TransactionCzkTest`, 28 tests in 2.72 s], so a 500-item batch is expected in the order of seconds [ASSUMED: extrapolation, A3]. Also confirm the production PHP request time limit on the host (not visible in the repo: `zerops.yml` and `site.conf.tmpl` set no timeout; the ddev override documents `max_execution_time = 240`).
**Warning signs:** a batch test over 30 s; the response of a second concurrent request being 409 `idempotency_in_progress` for long.

### Pitfall 3: Error keys the caller never sent
**What goes wrong:** an invalid `amount_minor` produces `{"errors": {"amount": [...]}}` because `TransactionInput` throws `self::error('amount', 'amount_invalid')`; a missing CNB rate produces `czk_amount` [VERIFIED: TransactionCzk.php `ValidationException::withMessages(['czk_amount' => ...])`]. The client has no `amount` or `czk_amount` field.
**How to avoid:** one `TransactionPayload::remap(ValidationException)` that renames `amount` to `amount_minor` and `czk_amount` to `czk_amount_minor` (and leaves every other key: `type`, `transaction_date`, `category_id`, `currency`, `client_id`, `project_id`, `description`, `counterparty`, `document_number`, `exchange_rate`, `exchange_unit_amount`). Use it in the single create, PATCH and every batch item. Test it on one case per renamed key.
**Warning signs:** a 422 in a test whose key is `amount`.

### Pitfall 4: Float and overflow at the edges of the numeric columns
**What goes wrong:** a JSON number such as `25.125` decodes to a PHP float; `1.0E-5` stringifies with an exponent; a rate with 11 integer digits passes `Money::convert()` but overflows `decimal(20,10)` (PostgreSQL 22003, a 500); `exchange_unit_amount` above 2147483647 overflows `integer`; `amount_minor` above `PHP_INT_MAX` arrives as a float.
**How to avoid:** `amount_minor` and `czk_amount_minor`: `integer` (non-strict lets `"12000"` from a string-typing client through; cast with `(int)` after validation) with `min:1` for the amount and `min:0` for the bank figure (the DB allows `czk_minor >= 0` and `amount_minor > 0`); `exchange_rate`: accept a decimal string; accept a JSON number only when `(string) $value` matches the pattern; pattern `^\d{1,10}(\.\d{1,10})?$`, non-zero. Document "send the rate as a string". [ASSUMED] n8n usability trade-off, A7.

### Pitfall 5: PATCH with a currency but no amount
**What goes wrong:** with `currency` named and `amount_minor` absent, `TransactionInput::amount()` re-parses the stored major string in the new currency (`"100.50"` in JPY fails `amount_invalid`; `"100.00"` silently becomes 100 yen).
**How to avoid:** make `amount_minor` required whenever `currency` is present on PATCH (a `required_with:currency` rule); document it. Any other combination is well defined.

### Pitfall 6: Cursor and sort mismatch
**What goes wrong:** `ApiCursor::kindOf()` throws `LogicException` for `transaction_date` / `czk_minor` until they are added; with an alias sort the request's cursor keys must be the internal column, not the public sort name.
**How to avoid:** Pattern 3, plus tests: a page-2 request with the cursor from page 1 under each sort, a forged cursor 422, and the example cursor of the docs accepted with 200 (the pattern of `TimeEntryContractTest` "accepts the example cursor of the documentation with a 200").

### Pitfall 7: `ApiDocs` regenerates the real docs and must not run in parallel
**What goes wrong:** the documentation tests run `php artisan scribe:generate` in a subprocess and overwrite the gitignored docs [VERIFIED: ApiDocs.php docblock: "The suite must not run with `--parallel`"].
**How to avoid:** never `--parallel` for the API doc tests; rerun `ddev exec php artisan scribe:generate` afterwards. The generation runs with the database unreachable, so a FormRequest `rules()` or `bodyParameters()` must not query the database (no `Rule::exists`, no category lookups).

### Pitfall 8: Phase 10 overlap
**What goes wrong:** Phase 10 plans 10-16 and 10-19 (not yet executed) edit `RecordTransaction` (adds an optional third argument `?array $invoiceLink`), `UpdateTransaction` and `DeleteTransaction`, and plan 10-06 edits `tests/Feature/Schema/TransactionTablesTest.php`; plan 10-16 describes `RecordTransaction` data keys as "type, transaction_date, category_id, amount, currency, czk_amount, czk_manual, description, counterparty, document_number, client_id, project_id".
**How to avoid:** keep every 9.1 change to the Action data keys additive (new optional keys, no rename, no removal), keep the `handle()` signatures, and tell the orchestrator that 10-16 / 10-19 should be re-read against the post-9.1 code. The Phase 10 payment-income refusals will reach API callers as the Action's exception type; whichever type plan 10-19 uses (not specified in the plan text) must be mapped to a 409 or 422 in the API controllers, which is another reason to centralise the exception mapping in one `TransactionPayload`/controller helper now.

### Reading the filter set into the query (pattern from `TimeEntryController::index`)
```php
// Source: app/Http/Controllers/Api/V1/TimeEntryController.php (read this session); adapted
$transactions = QueryBuilder::for(Transaction::query())
    ->allowedFilters(
        AllowedFilter::callback('type', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.type', $v)),
        AllowedFilter::callback('category', static fn (Builder $q, mixed $v): Builder => $q->where(static fn (Builder $in): Builder => $in
            ->where('transactions.category_id', $v)
            ->orWhereIn('transactions.category_id', static fn ($sub) => $sub
                ->select('transaction_categories.id')->from('transaction_categories')
                ->where('transaction_categories.parent_id', $v)))),
        AllowedFilter::callback('client', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.client_id', $v)),
        AllowedFilter::callback('project', static function (Builder $q, mixed $v) use ($refs): Builder {
            $id = is_string($v) ? $refs->projectId($v) : null;

            return $id === null ? $q->whereRaw('false') : $q->where('transactions.project_id', $id);
        }),
        AllowedFilter::callback('currency', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.amount_currency', $v)),
        AllowedFilter::callback('czk_source', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.czk_source', $v)),
        AllowedFilter::callback('date_from', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.transaction_date', '>=', $v)),
        AllowedFilter::callback('date_to', static fn (Builder $q, mixed $v): Builder => $q->where('transactions.transaction_date', '<=', $v)),
    )
    ->allowedSorts(
        AllowedSort::field('transaction_date'),
        AllowedSort::field('amount', 'czk_minor'),
        AllowedSort::field('created_at'),
    )
    ->defaultSort('-transaction_date')
    ->orderBy('transactions.id', $descending ? 'desc' : 'asc')
    ->cursorPaginate($request->perPage())
    ->withQueryString();
```
Filter validation lives in `ListTransactionsRequest` (`'filter' => ['sometimes', 'array:'.implode(',', FILTERS)]`, `filter.type` in `income,expense` via `Rule::in(array_map(fn ($c) => $c->value, TransactionType::cases()))`, `filter.czk_source` via `CzkSource::cases()` so `custom` is included automatically, `filter.category|client` `uuid`, `filter.currency` `^[A-Z]{3}$`, `filter.date_from|date_to` real Prague day via `PragueDay::day()`). The date range is inclusive on both ends, the same as the Admin screen ("Both days are inclusive" comment in `TransactionResource::filters`). `filter[category]` with an unknown UUID matches nothing (not an error), like the unknown project key.

## Open Questions

1. **How is the 409 required by the docs helper satisfied for PATCH and DELETE of a transaction?**
   - What we know: `ApiDocs::statusCodes()` demands 409 documented on every PATCH and DELETE route; `DeleteTransaction` can throw a `RuntimeException` when the database refuses the delete; no PATCH conflict exists until Phase 10 adds the payment-income lock.
   - What's unclear: whether to relax the helper or document a forward-looking 409.
   - Recommendation: map `RuntimeException` to `ApiError::conflict('transaction_in_use', ...)` for DELETE and document it; for PATCH relax the helper so 409 is required only for controllers that declare it (a constant), or document `transaction_locked` as reserved. Decide before planning the docs plan.

2. **Should a `custom` transaction edited in the Admin UI keep its rate?**
   - What we know: the UI sends `czk_manual = false` for computed rows, so a changed amount recomputes through CNB; unchanged amount/date/currency keeps the figure.
   - What's unclear: whether the owner accepts the silent switch to `cnb` on an amount edit in the UI.
   - Recommendation: accept it ("UI keeps current behaviour", D-06), add the `custom` badge and an edit-form hint; revisit if the owner wants stickiness in the UI.

3. **Does the transaction `id` belong in the response?** D-07's list omits it. Recommendation: include `id` first (it is the only way to PATCH/DELETE/show); treat the omission as an oversight.

4. **Category list default sort.** Cursor pagination needs a single sort column plus id. Recommend default `name` ascending (text kind exists in `ApiCursor`) and `created_at`; the tree is rebuilt by the caller from `parent_id`. With a few dozen categories a caller reads them in one page with `per_page=200`.

5. **Add `exchange_unit_amount` / `exchange_rate_date` to the Transaction activity allowlist?** Optional; costs a Czech label and an allowlist test pass.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Mass assignment of `czk_source`, `czk_minor`, `id`, snapshot columns | Tampering | Mapping class builds only allow-listed Action keys; model fills only three text columns; Actions `forceFill` from checked input |
| Partner or Partner token reads finance | Information disclosure | Route group + Sanctum guard (401) + `DeniesPartners` + policy; extend the canary harness with a finance control read |
| Token with only `time:*` writes finance (or the reverse) | Elevation of privilege | `abilities:` requires the exact ability; test both directions (D-01) |
| Forged or mismatched cursor | Tampering / DoS (500) | `ApiCursor::rule()` extended with `date`/`integer` kinds; walk test sends a forged cursor to every list route |
| Oversized batch / slow batch | Denial of service | 500-item cap in config, envelope validation before any item runs, one rate-limit hit, rate limits per token |
| Replay or cross-token replay of a create | Spoofing / Repudiation | `EnsureIdempotency` binds the key to the token and the body hash |
| Numeric overflow (rate, unit, amount) reaching PostgreSQL | DoS (500, SQLSTATE leak) | Validate digit counts; `Money` overflow caught and mapped; batch catches `Throwable`, calls `report()`, returns a generic message so no SQL state or schema detail reaches the client |
| SQL/filter injection through filter values | Tampering | `QueryBuilder` callbacks bind parameters; values validated as UUID/enum/regex first; unknown filter keys rejected by `array:` rule |
| Leaking receipt or file data | Information disclosure | Resource is an explicit allow-list with no receipt keys (D-07); DELETE removes receipts through `DeleteDocument` inside the Action |
| Sensitive data in docs/tests | Information disclosure | Fixed example constants, `example.com`, `12345678`; `ApiDocumentationHygieneTest` scans generated output |
