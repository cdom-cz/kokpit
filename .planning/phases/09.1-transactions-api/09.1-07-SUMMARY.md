This is far below the 60 second threshold (half of `idempotency_stale_lock_seconds` = 120), so **no blocker is raised** and neither the 500 limit nor the stale-lock setting was changed. Caveats the owner should know: the 500 items were CZK expenses (no CNB rate lookup per item; a foreign-currency item adds one rate lookup), the database was the DDEV PostgreSQL on a local machine, and the production figure will differ with network latency, activity logging load and hardware. ## Accomplishments

- `POST /api/v1/transactions/batch` saves each item through `RecordTransaction` in its own transaction, with no outer transaction, so a refused item never touches its neighbours; it answers 201 (all saved), 207 (some saved) or 422 with a message (none saved), listing only failed items as `{index, errors}`.
- `TransactionPayload::forBatchItem()` applies the single-create rules to every item; the controller passes each `ValidationException` through `remap()`, so a refusal of the Action is keyed by `amount_minor` / `czk_amount_minor`, never `amount` / `czk_amount`.
- An item that is not a JSON object, and any fault of the server, fails under `transaction` with a generic Czech message; the fault is `report()`ed and its text never reaches the client, and a late fault cannot end in a 500 that releases the Idempotency-Key (a retry would save the batch twice).
- `api.transaction_batch_max_items = 500` is read at validation time; an empty list and 501 items answer 422 under `transactions` and save nothing. The public docs state the limit in their own sentences and `ApiDocumentationTest` pins them to the config, with a self-check case for 501.
- The Idempotency-Key is proven on both transaction creates with no change to the middleware: replay of a stored 201 or 207 byte for byte with `Idempotent-Replayed`, 422 `idempotency_key_reused`, 409 `idempotency_in_progress`, key released by a 422, header ignored by PATCH, DELETE and GET.
- A batch counts as one write; finance writes and reads keep separate per-token buckets.
