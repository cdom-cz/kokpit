Decisions carried in (locked): D-06; owner decision A1 made at planning (2026-10-16): sticky rate - the own rate is kept when the amount changes, the transaction falls back to CNB when the currency changes, sending both `exchange_rate: null` and `czk_amount_minor: null` through the API returns it to CNB, and editing the amount in the Admin UI switches a custom row to cnb. Phase 9: a manual figure stays manual until `czk_manual` is false; a computed figure is recomputed only when date, currency or amount change.

Decisions made in this plan (recorded):
- The API's "back to CNB" reaches the Action as `exchange_rate => null` plus `czk_manual => false` (plan 09.1-06 maps it); `TransactionInput::customRateCleared` (plan 09.1-01) carries the first part. The UI never sends `exchange_rate`, so a UI save of a custom row with nothing relevant changed keeps the own rate.
- The distinction between the API and the UI is the presence of `czk_manual`: the UI always sends `czk_manual` false for a computed foreign row, the API sends no `czk_manual` unless it returns a row to CNB. A custom row with `czk_manual` absent follows the sticky rule; with `czk_manual` false it follows the Phase 9 computed rule (recompute through CNB only when date, currency or amount change).
- A sticky recompute keeps the stored rate date: the snapshot is the rate fixed for this transaction, the transaction date does not move it.
- A cnb transaction is never recomputed by "back to CNB" alone (Phase 9: a list added or corrected later never moves a stored figure).
