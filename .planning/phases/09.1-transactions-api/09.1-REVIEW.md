# Phase 09.1: Code Review Report

**Reviewed:** 2026-10-17
**Depth:** standard
**Files Reviewed:** 52
**Status:** issues_found

## Summary

The phase adds the Transactions REST API (list, show, create, update, delete, batch, read-only categories), the `finance:read` / `finance:write` abilities, and the `custom` CZK source (own exchange rate) in the domain Actions and the Filament screen.

Overall the work is careful. Route groups carry `auth:sanctum`, a per-group ability and a throttle, with no route outside a group. Partner tokens are refused by the token guard. Every write goes through the same Actions as the panel, with `Gate` authorization inside the Action. The mapping class builds an allow-listed payload, so smuggled keys never reach the Actions. Cursor values are validated before they reach PostgreSQL, and the migration swaps the two check constraints by name. `scripts/check-sensitive.sh` is clean over all changed files (app, config, routes, lang, database, tests).

I could not run the test suite (the host has no DB, and the project rule is DDEV only). All findings below come from tracing the code. The one BLOCKER is a silent loss of an explicitly sent CZK figure on PATCH.

## Critical Issues

### CR-01: PATCH `exchange_rate: null` plus a `czk_amount_minor` on an own-rate transaction silently discards the sent CZK figure

**File:** `app/Http/Requests/Api/V1/TransactionPayload.php:225-231` (consumed in `app/Domain/Finance/Actions/UpdateTransaction.php:103-130`)
**Issue:** Take a stored `custom` transaction and send `{"exchange_rate": null, "czk_amount_minor": 252000}`. This is a natural request for "drop the own rate, use the bank figure", and an importer that PATCHes full state with explicit nulls will send it.

1. `figure()` emits `czk_amount` = `"2520.00"`, because the value is non-null.
2. `cleared()` sees `$rateNull && stored === Custom` and returns `['exchange_rate' => null, 'czk_manual' => false]`. It never checks whether a non-null figure was sent in the same request.
3. `forUpdate()` merges `cleared()` last, so `czk_manual = false` wins. In `TransactionInput`, `manualCzk()` then returns `null`, because `czkManual === false`.
4. `UpdateTransaction::figure()` skips the manual branch. It reaches `$wasCustom && $input->customRateCleared` and calls `resolve(..., null)`, which is the CNB rule.

The bank figure the client sent is dropped without any error. The response is 200 with `czk_source: cnb` and a CNB-computed amount. If no CNB list exists for the day, the client gets a 422 under `czk_amount_minor` telling it to "enter the CZK amount manually", although it just did. If the request also changes the currency, `figureGiven` is computed as false because of the injected `czk_manual = false`, so the failure surfaces as a misleading `currency_unknown` for a currency that has no CNB rows.

Money is wrong without any signal, and none of the tests cover the combination. The tests only cover both nulls together, `exchange_rate: null` alone, and `czk_amount_minor` alone.

**Fix:** Do not force `czk_manual = false` when a non-null figure is sent. Only the rate needs to be cleared, because a typed figure already outranks everything in `UpdateTransaction::figure()`:
```php
if ($rateNull && $stored->czk_source === CzkSource::Custom) {
    return ($validated['czk_amount_minor'] ?? null) !== null
        ? ['exchange_rate' => null]   // the figure sent in this request becomes the manual one
        : $toCnb;
}
```
Also guard the both-null branch (`$rateNull && $figureNull`), which is fine as written because the figure is null there. Add a test `{exchange_rate: null, czk_amount_minor: N}` on a custom transaction. It must assert `czk_source = manual` and `czk_minor = N`, and a variant with a changed currency that has no CNB rows.

## Warnings

### WR-01: A JSON boolean passes the `integer` rule and is silently ignored or mis-applied on update

**File:** `app/Http/Requests/Api/V1/TransactionPayload.php:57,59,61` and `:268-275`
**Issue:** Laravel's `integer` rule is `filter_var($v, FILTER_VALIDATE_INT) !== false`, and `filter_var(true, FILTER_VALIDATE_INT)` returns `1`. So `true` passes the shape rule. `major()` then returns `null` for a non-numeric value (`is_numeric(true)` is false), and the callers treat `null` as "key not sent".

- **Create, `amount_minor: true`:** caught only indirectly, as `amount_invalid` from the Action. The test asserts this, so it works by accident.
- **Update, `{"currency": "EUR", "amount_minor": true}`:** the rule passes (`required_with:currency` is satisfied), `$data['amount']` is never set, and the Action keeps the stored major-unit text and re-reads it in the new currency. A stored `1234.50` CZK becomes `1234.50` EUR, which bypasses the documented guarantee that a currency change needs an amount. The CZK figure is then recomputed at the CNB rate of that wrong amount.
- **`czk_amount_minor: true`** on create or update becomes `czk_amount = null`, so a garbage figure silently means "use the CNB rate". `exchange_unit_amount: true` is read as `1`.

**Fix:** Use strict integers for the three fields, `'integer:strict'` (Laravel 11+), or a closure that requires `is_int($value)`. Also make `major()` throw instead of returning `null`:
```php
'amount_minor' => $create ? ['required', 'integer:strict'] : ['required_with:currency', 'integer:strict'],
'czk_amount_minor' => ['nullable', 'integer:strict'],
'exchange_unit_amount' => ['nullable', 'integer:strict'],
```
If numeric strings must stay accepted, check `is_int($v) || (is_string($v) && preg_match('/^-?\d+$/D', $v))` in a closure rule. Add a test for `PATCH {currency: "EUR", amount_minor: true}`.

### WR-02: A 500-item batch can outlive the idempotency stale-lock window, and a retry then saves the batch twice

**File:** `app/Http/Controllers/Api/V1/TransactionBatchController.php:78-112`, `config/kokpit.php:161`, `app/Domain/Api/Idempotency/IdempotencyStore.php` (`takeOver`)
**Issue:** The claim carries `locked_at` and is never refreshed while the controller runs. After `idempotency_stale_lock_seconds` (120 s), a retry with the same key and body takes the claim over (`takeOver`) and runs the whole batch again. Items have no natural unique key (the docs say so), so every item saved by the first, still running, request is saved a second time.

The time-entry batch is capped at 100, but this batch allows 500 items. Each item takes a share lock on the category, client and project, runs several queries and a `refresh()`, and one test measures 500 items only "for the owner" without asserting a bound. A slow database, or a client that retries aggressively on timeout (the typical client behaviour this feature exists for), makes the takeover reachable. The first request's `complete()` is correctly refused afterwards, but the duplicates are already committed.

**Fix:** Either refresh the lock periodically inside the loop (for example `IdempotencyStore::touch($row)` every N items), or lower `transaction_batch_max_items` / raise `idempotency_stale_lock_seconds` so that the worst case stays well below the window. Document the measured worst case next to the setting.

### WR-03: Update and delete decide on a row read before the lock, and a concurrent delete leaks the model class in the 404 body

**File:** `app/Http/Controllers/Api/V1/TransactionController.php:242-245,263-266`, `app/Http/Requests/Api/V1/TransactionPayload.php:138-168,218-238`, `app/Domain/Finance/Actions/UpdateTransaction.php:63`, `app/Domain/Finance/Actions/DeleteTransaction.php`
**Issue:**
1. `update()` reads `$stored` without a lock, and `TransactionPayload::forUpdate()` and `cleared()` branch on `$stored->czk_source` and `$stored->amount_currency` (the `assertNoRateOnCzk` currency check, and which "null clears" keys are injected). The Action then re-reads the row under `lockForUpdate`, but the payload was already built from the old snapshot. If two PATCHes race (an importer retrying after a timeout), the second one can apply a `cleared()` decision or a CZK check that is wrong for the row it actually locks.
2. If the row is deleted between `find()` and the Action's `lockForUpdate()->firstOrFail()`, a `ModelNotFoundException` escapes. Laravel turns it into a `NotFoundHttpException` whose message (`No query results for model [App\Domain\Finance\Models\Transaction] <uuid>`) is shown even with debug off. This contradicts the controller's stated rule that every miss answers the same Czech 404 without a model class name.

**Fix:** Catch `ModelNotFoundException` around both Action calls and `abort(404, __('api.errors.not_found'))`. For (1), pass the Action only the intent (which fields were sent as null) and let the Action resolve against the locked row, or recompute the payload from `$locked` inside the transaction.

### WR-04: The "finance:write token is refused on every write route" assertion can pass with no routes

**File:** `tests/Feature/Api/TransactionAbilityTest.php:91-103`
**Issue:** The test builds `$statuses` from `financeAbilityRoutes('finance:write')` and asserts `toBe(array_fill(0, count($routes), 403))`. If the route set were empty (a renamed middleware string, a refactor of route registration), the expectation is `[] === []` and the test passes vacuously. Only the `finance:read` variant has `expect($routes)->not->toBeEmpty()`, and the generic "finds finance routes" test covers `finance:` as a whole, not `finance:write`. The comment above the loop ("The write routes arrive with later plans of the phase; with none yet there is nothing to refuse") is stale now that the write routes exist, and it explains away the vacuity instead of guarding against it.
**Fix:** Add `expect($routes)->not->toBeEmpty();` as in the read variant (ideally `toHaveCount(4)` for store, batch, update and destroy), and delete the stale comment.

## Info

### IN-01: The public intro describes `manual` wrongly

**File:** `config/scribe.php` (intro text, "Formats and errors" list; added in this phase)
**Issue:** It says `manual` is "a rate entered by hand". In the domain, the endpoint docs and the resource docs, `manual` is a CZK figure the user typed, with no rate (the rate snapshot is `null`). The intro now contradicts `TransactionController::show` ("manual (a CZK figure typed by the user)").
**Fix:** "`manual` (a CZK amount entered by hand, as the bank booked it)".

### IN-02: The API docs do not say that a manual CZK figure stays frozen when the amount or currency changes

**File:** `app/Http/Requests/Api/V1/UpdateTransactionRequest.php:50-57`, `app/Http/Controllers/Api/V1/TransactionController.php:216`
**Issue:** The update docs explain the sticky own rate, but not that a `manual` transaction keeps its stored CZK figure whatever `amount_minor`, `currency` or `transaction_date` become. The domain deliberately does this (research Pitfall 13), but a CNB transaction recomputes on the same change. An API client that edits only `amount_minor` of a manual row gets an unchanged `czk_minor` with no hint.
**Fix:** Add one sentence to the `amount_minor` and `currency` body-parameter descriptions and to the endpoint description. Say that a manual figure is kept until `czk_amount_minor` is changed or set to `null`.

### IN-03: A PATCH for an unknown id with an invalid body answers 422, not 404

**File:** `app/Http/Controllers/Api/V1/TransactionController.php:240-242`
**Issue:** `UpdateTransactionRequest` is resolved (and validated) before the method body calls `self::find()`. A request for a non-existent transaction that also has an invalid body therefore returns the validation error first. That is harmless, but it leaks no existence information either way and is inconsistent with DELETE and GET.
**Fix:** Optional. If 404-first is wanted, drop the FormRequest injection in favour of `Validator::make($request->all(), TransactionPayload::rules(false))` after `find()`, or document the order.

### Verification of CR-01 (fixed)

Traced `PATCH {exchange_rate: null, czk_amount_minor: N}` on a stored `custom` row through the new `cleared()` branch (`TransactionPayload.php:233-240`):

- `cleared()` returns `['exchange_rate' => null]` only, so `czk_manual` is not injected. `figure()` still emits `czk_amount`.
- `TransactionInput::fromArray`: `customRate()` returns null (null rate, no unit), `czkManual` is null, so `manualCzk()` returns the typed figure. `figureGiven` is true, so a currency without CNB rows is accepted (no misleading `currency_unknown`).
- `UpdateTransaction::figure()`: `$manual` is a `Money`, so it resolves as manual and the `customRateCleared` branch is never reached. Result: `czk_source = manual`, rate snapshot null, as the new tests assert.
- The both-null branch still comes first and still returns to CNB. A `null` figure with a stored `custom` row and no rate key is unchanged. Stored `cnb` and `manual` rows with `exchange_rate: null` plus a figure fall through to `[]` and take the typed figure as before.
- `assertNoRateOnCzk` still refuses the combination on CZK, so the new branch cannot produce a CZK row with a figure.

The two new tests cover the ordinary case (one currency with a CNB list, one without) and the currency-change case (EUR to ISK, no CNB rows). They assert the stored row too, not only the response.

### Verification of WR-01 (fixed)

- `noBoolean()` runs after `bail`, before `integer`, on the three fields. `bail` is per attribute, so a boolean yields exactly one panel message and not an additional English `integer` message. `nullable` still short-circuits an explicit `null` for the two optional fields, and `required`/`required_with` still run first for `amount_minor`.
- Integers and integer strings are unaffected (the create test still posts `'10000'`). Float and array values are still refused by `integer`, as before.
- The batch path goes through `Validator::make($item, self::rules(true))`, so the same rules apply; the batch test confirms the message and that the good item is saved.
- Error keys are the API names (`amount_minor`, `czk_amount_minor`, `exchange_unit_amount`) because the closures fail on the attribute itself, so no `remap()` is needed for them.
- The update test checks that nothing was written (amount, currency, `czk_minor`, source), which is the property WR-01 was about.

### Verification of WR-04 (fixed)

`expect($routes)->not->toBeEmpty()` is in place and the stale comment is gone. The test passes against the real route table.

### Info

#### IN-04: The endpoint description of the update still omits the new `exchange_rate: null` plus figure behaviour

**File:** `app/Http/Controllers/Api/V1/TransactionController.php:216`
**Issue:** Plan 09.1-09 updated the `exchange_rate` body-parameter text in `UpdateTransactionRequest.php:59` and the docblocks in `TransactionPayload`, but the endpoint description of "Update a transaction" still reads "`exchange_rate: null` drops an own rate, `czk_amount_minor: null` drops a bank figure, and both `null` return any transaction to the Czech National Bank rate". It is not wrong, but a reader of the endpoint text alone does not learn that a figure sent with `exchange_rate: null` becomes the bank figure. The two descriptions now differ.
**Fix:** Add one sentence to the endpoint description, for example: "`exchange_rate: null` sent together with a `czk_amount_minor` value drops the own rate and takes that value as the bank figure." Regenerate the Scribe output if it is committed.

#### IN-05: The new tests leave two neighbouring cases and a weak route-count guard

**File:** `tests/Feature/Api/TransactionWriteTest.php:274-315`, `tests/Feature/Api/TransactionAbilityTest.php:106-112`
**Issue:** (1) The CR-01 tests exercise a stored `custom` row only. There is no case for `exchange_rate: null` plus a figure on a stored `cnb` or `manual` row, which falls through `cleared()` to `[]` and is correct today but is not pinned. (2) The WR-01 update test sends a boolean `amount_minor` only together with `currency`; `PATCH {amount_minor: true}` without `currency` takes the same rule but is not asserted. (3) The write-route walk now fails on an empty set, but a partial set (for example one route losing its ability middleware from the route table lookup) would still pass; the original review suggested `toHaveCount(4)` for store, batch, update and destroy.
**Fix:** Add the two small PATCH cases, and replace `not->toBeEmpty()` in the write-route test with an exact count (or an assertion on the sorted list of `METHOD uri` pairs), so a route that disappears from the set fails the test.
