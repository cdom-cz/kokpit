# Phase 09.1: Transactions API - Context

**Gathered:** 2026-10-16
**Status:** Ready for planning

<domain>
## Phase Boundary

External tools (in practice the owner's n8n automations) can read, create (singly and in bulk), update and delete finance transactions, and read transaction categories, through the existing token-secured `/api/v1`. The API applies the same domain rules as the Admin UI by calling the Phase 9 finance actions. The phase depends only on Phase 9 (the `transactions` and `transaction_categories` tables and their actions); Phase 10 does not depend on it.

Not in this phase: writing categories (create, rename, archive, move, delete stay UI-only), receipts and any file handling, the invoice link and income from invoice payments (Phase 10), webhooks, any Partner access to the API.

</domain>

<decisions>
## Implementation Decisions

Carried forward, not re-opened: Phase 7 API conventions (`/api/v1`, Sanctum bearer tokens of an active Admin, `abilities:` middleware per route group, per-token rate limits `throttle:api-read` / `throttle:api-write`, optional `Idempotency-Key` on create routes through `EnsureIdempotency` with replay/422/409 semantics, cursor pagination default 50 / max 200, `spatie/laravel-query-builder` filters and sorting, Scribe documentation with fictional examples only, errors in Laravel's JSON validation shape with Czech messages); the domain actions are the single place for rules and the API adds no parallel rule set (`RecordTransaction`, `UpdateTransaction`, `DeleteTransaction`, input checked by `TransactionInput`); money is bigint minor units plus ISO 4217 currency; the CZK amount and its CNB snapshot rules (Phase 9 D-12, D-13); transactions are Admin-only and a Partner never reaches finance data (Policies, `DeniesPartners`, canary harness extended with API lines); UUID v7 keys; Phase 7 D-13 reference style (UUID or key, never names).

### Token abilities
- **D-01:** Two new abilities `finance:read` and `finance:write` are added to `ApiAbility` and offered on the token creation screen next to `time:*`. Transaction and category GET routes need `finance:read`; POST, PATCH, DELETE need `finance:write`. A token with only `time:*` abilities gets 403 on finance routes, and a finance token gets 403 on time routes. — **Reversibility:** costly — ability strings are stored on issued tokens and named in the published API contract.

### Endpoint scope
- **D-02:** Transactions: list, detail, create, bulk create, PATCH, DELETE, each going through `RecordTransaction`, `UpdateTransaction` and `DeleteTransaction`. Transaction categories: read-only list and detail so a client can discover the UUIDs; category management stays in the UI. Deleting a transaction through the API follows the Phase 9 delete rules (its receipt files are removed with it, as in D-14/D-21 of Phase 9). Receipts and other files are not exposed.
- **D-03:** Client and project are optional on a transaction; a project requires a client and must belong to it (DB CHECK and composite FK from Phase 9). The API refuses a project without a client or of another client with the same field error as the UI.

### Bulk create
- **D-04:** Bulk create is partial-success, the same contract as time entry batch (Phase 7 D-14): every valid item is saved in its own DB transaction through `RecordTransaction`, invalid items are skipped, the response lists only failed items (item index plus errors) with counts of saved and failed items. It carries `Idempotency-Key` like the single create and counts as one write against the rate limit. Exact status codes (201 all saved, 207 mixed, 422 none saved, as in Phase 7) and response layout follow the Phase 7 batch endpoint. — **Reversibility:** costly — importers rely on the partial-success contract.
- **D-05:** The maximum batch size is **500** items (value in `config/kokpit.php`, separate from the 100 limit of time entry batches); more returns 422.

### Amounts and CZK conversion
- **D-06 (owner decision during discussion):** The caller can set the exchange rate and the currency directly on the transaction; it is a rate of that one transaction, not a general rate. The client sends `amount_minor` and `currency` plus either (a) an own rate `exchange_rate` (with `exchange_unit_amount`, default 1), from which the CZK amount is computed and the rate stored as the transaction's snapshot with a new `czk_source = custom`; or (b) `czk_amount_minor`, the real bank figure (`czk_source = manual`, no rate stored); or (c) neither, and the CZK amount is computed from the CNB rate of the transaction date (`ExchangeRateConverter`, `czk_source = cnb`; `identity` for CZK). Supplying more than one of (a) and (b) is a 422. A currency without any stored CNB row is accepted when (a) or (b) is given; without either it fails with 422 (nothing is saved without a CZK figure, so the CHECK constraints stay intact). The UI keeps its current behaviour. This needs a migration widening `transactions_czk_source_check`, `transactions_identity_check` and `transactions_snapshot_check` to the new `custom` source (snapshot columns required, date of the rate defaults to the transaction date) and a change to `RecordTransaction` / `UpdateTransaction` / `TransactionInput` so the UI and the API share one rule set. — **Reversibility:** costly — a new `czk_source` value touches the DB CHECKs, the actions, the finance overview labels and the published API contract.
- **D-07:** The transaction response returns `type`, `transaction_date`, `category_id`, `amount_minor`, `currency`, `czk_minor`, `czk_source`, `exchange_rate`, `exchange_unit_amount`, `exchange_rate_date`, `description`, `counterparty`, `document_number`, `client_id`, `project_id`, `created_at`, `updated_at`. It carries no receipt data. The snapshot is shown so the caller can verify what was booked. — **Reversibility:** one-way — published response contract once n8n depends on it.
  - *Clarification (recorded at planning, 2026-10-16):* the response also carries `id`, the transaction UUID, as its first key, before `type`. The list above did not name it; it is the only way a caller can address a transaction for the detail, PATCH and DELETE endpoints, and the owner accepted it at planning. The other keys, their order and "no receipt data" are unchanged. Implemented and pinned by plan 09.1-02 (`TransactionResource`, `TransactionContract::KEYS`).

### References
- **D-08:** The category is referenced by UUID only (the category list gives the IDs). Client and project are referenced by UUID or by key, resolved by the same resolver as the time entry API (Phase 7 D-13); names are never accepted. A category that is archived, or of another type than the transaction, is refused with the same error as the UI.
  - *Clarification (recorded at planning, 2026-10-16):* clients have no key in the schema (`ReferenceResolver::clientId()` takes a UUID only), so a client is referenced by UUID only, in `client_id` of a write and in `filter[client]` of the list; a project keeps "UUID or key", resolved by `ReferenceResolver`. Names stay refused for both. The owner accepted this at planning. Implemented by plans 09.1-05 (filters) and 09.1-06 (writes; the batch of 09.1-07 reuses the same mapping).

### Listing
- **D-09:** The list uses cursor pagination (default 50, max 200), default sort by transaction date, newest first. Filters mirror the Admin screen: `filter[type]`, `filter[category]` (a parent category includes its children), `filter[client]`, `filter[project]`, `filter[date_from]` / `filter[date_to]`, `filter[currency]`, `filter[czk_source]`. Sorting by date and amount (`sort`). The category list returns the tree data needed to use it (id, parent, name, type, archived flag).

### Claude's Discretion
Controller, resource and request class names; the exact route and filter parameter names where not given above; the status code layout of the bulk response (follow the Phase 7 batch endpoint); how the ability checkbox is added to the token form; Scribe example values (fictional only); test structure (extend the canary harness with API lines for finance).

</decisions>
