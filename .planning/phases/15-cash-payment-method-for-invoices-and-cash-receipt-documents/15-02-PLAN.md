Rulings made in this plan (recorded; valid for option `single-table`, the recommendation):
- R-15-02-1 (columns, in this order): `id uuid PK DEFAULT uuidv7()`, `invoice_id uuid NOT NULL`, `client_id uuid NOT NULL`, `invoice_payment_id uuid NULL`, `number varchar(32) NOT NULL`, `document_number varchar(32) NOT NULL`, `issued_on date NOT NULL`, `received_on date NOT NULL`, `amount_minor bigint NOT NULL`, `currency char(3) NOT NULL`, `purpose varchar(500) NOT NULL`, `language char(2) NOT NULL`, `supplier_snapshot jsonb NOT NULL`, `customer_snapshot jsonb NOT NULL`, `appearance_snapshot jsonb NOT NULL`, `lock_state varchar(8) NOT NULL DEFAULT 'open'`, `cancelled_at timestamptz NULL`, `pdf_document_id uuid NULL`, `created_at`, `updated_at` (`timestampsTz`). `document_number` is the frozen number of the paid invoice or proforma, copied at issue (15-08), so the "Hrazený doklad" line of the PDF is rendered from the receipt row alone (D-11, no read of invoices; the invoice number itself never changes after issue). No `created_by`, `cancelled_by` or reason column: the causer and the cancel and unlock reasons live only in the Admin-only activity log written by the Actions (precedent: the invoice unlock reason, Phase 10.1 D-13 / A12; owner confirmed as AS-16).
- R-15-02-2 (keys and indexes): unique `cash_receipts_number_unique (number)`; unique `cash_receipts_invoice_payment_unique (invoice_payment_id)`; index `cash_receipts_invoice_id_index (invoice_id)`; index `cash_receipts_client_id_index (client_id)`; FK `cash_receipts_invoice_client_fk (invoice_id, client_id) REFERENCES invoices (id, client_id)` (target `invoices_id_client_unique`); FK `cash_receipts_payment_fk (invoice_payment_id, invoice_id) REFERENCES invoice_payments (id, invoice_id) ON DELETE SET NULL (invoice_payment_id)` (target `invoice_payments_id_invoice_unique`; PostgreSQL 18 in DDEV supports the column list); FK `cash_receipts_pdf_document_fk (pdf_document_id) REFERENCES documents (id) ON DELETE SET NULL`.
- R-15-02-3 (checks): `cash_receipts_amount_check (amount_minor > 0)`, `cash_receipts_currency_check (currency ~ '^[A-Z]{3}$')`, `cash_receipts_language_check (language IN ('cs', 'en'))`, `cash_receipts_lock_state_check (lock_state IN ('open', 'locked'))`, `cash_receipts_purpose_check (btrim(purpose) <> '')`, `cash_receipts_number_check (btrim(number) <> '')`, `cash_receipts_document_number_check (btrim(document_number) <> '')`, `cash_receipts_received_on_check (received_on <= issued_on)`, and the D-08 rule `cash_receipts_payment_link_check (invoice_payment_id IS NOT NULL OR cancelled_at IS NOT NULL)`.
- R-15-02-4 (row guard `kokpit_guard_cash_receipt_row()`, trigger `cash_receipts_row_guard BEFORE INSERT OR UPDATE OR DELETE`, every refusal `ERRCODE = 'KP001'`):
  - INSERT: refused unless `lock_state = 'open'`, `cancelled_at IS NULL`, `invoice_payment_id IS NOT NULL`, and a row of `invoice_payments` exists with that id, the same `invoice_id`, `method = 'cash'`, the same `amount_minor` and the same `currency`, and the `invoices` row of `invoice_id` has `number = NEW.document_number`.
  - DELETE: always refused ("a cash receipt is never deleted").
  - UPDATE: `frozen` = id, invoice_id, client_id, number, document_number, issued_on, amount_minor, currency, language, appearance_snapshot, created_at; any change refused ("the number, amount and identity of a cash receipt never change").
  - `invoice_payment_id`: a change is accepted only to NULL, only when `OLD.cancelled_at IS NOT NULL`, and only when nothing else of the row changes (the foreign-key action after the payment deletion).
  - `cancelled_at`: once set it never changes ("a cancelled cash receipt is never restored"). The statement that sets it (OLD NULL, NEW not NULL) may change only `cancelled_at`, `pdf_document_id` and `updated_at`, in either lock state. A row with `OLD.cancelled_at IS NOT NULL` accepts only the FK set-null above and changes of `pdf_document_id` and `updated_at` ("a cancelled cash receipt accepts no edit").
  - open row, not cancelled: may change `received_on`, `purpose`, `supplier_snapshot`, `customer_snapshot`, `pdf_document_id`, `lock_state`, `updated_at`; `open -> locked` is accepted from any writer (the confirmation send).
  - locked row, not cancelled, staying locked: only `pdf_document_id` and `updated_at` may change (a missing PDF recreated); `locked -> open`: only `lock_state` and `updated_at` change, and `current_setting('kokpit.cash_receipt_unlock', true)` must equal `OLD.id::text` ("a cash receipt is unlocked only by the sanctioned unlock").
- R-15-02-5 (PDF link guard `kokpit_guard_cash_receipt_pdf_link()`, trigger `cash_receipts_pdf_link_guard BEFORE INSERT OR UPDATE`): mirror `kokpit_guard_invoice_pdf_link()` of `2026_10_17_000300_create_invoice_admin_tables.php`: a non-null link names only a `documents` row with `owner_type = 'cash_receipt'` and `owner_id = NEW.id`; a link is never repointed from one file to another; it is cleared only when its file is gone. Plus `Immutability::truncateGuardSql('cash_receipts')`.
- R-15-02-6 (no forcing trigger): the database does not force a receipt for every cash payment. No cash payments exist before this phase (AS-2, owner confirmed), so D-06 holds for every cash payment without a backfill; it is held by the one write path `RecordPayment::recordLocked()` (15-08), proven by its issue and concurrency tests. A forcing trigger is not added because the copies `RecordPayment::carry()` makes during a proforma conversion are cash payments that legitimately have no receipt of their own (D-07), and the raw-SQL fixtures of the existing schema tests insert payments directly. Owner acceptance (2026-10-27, recorded in AS-2 of 15-01 and in 15-CONTEXT.md): asked about a database constraint trigger, the owner decided that D-06 stays enforced in the application only, by `RecordPayment`, with no database constraint trigger; the residual risk that a cash payment written outside `RecordPayment` (raw SQL, console) has no receipt is accepted by the owner. The migration header states this acceptance.
- R-15-02-7 (down): drops the triggers, the two functions and the table. The header comment says why (no data exists before this phase) and states the guard limits like the other guard migrations.
- R-15-02-8 (Partner-safe pin): `PartnerSafeColumnsTest` pins `cash_receipts` in the R-15-02-1 order with the review sentence: the table holds what the receipt prints (the paid document number included, which is the number of the client's own document), its lock and cancel state and three opaque links (`invoice_payment_id`, `pdf_document_id`, the invoice); the payment link names an Admin-only row a Partner cannot read and is reviewed on purpose; reasons and causers live in the Admin-only activity log. Its suspicious-name test allows exactly `invoice_payment_id` for this table.
