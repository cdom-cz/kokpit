Rulings made in this plan (recorded):
- R-15-10-1 (resolve at send time): after the recipient check `handle()` reads the receipt of the payment (`CashReceipt::query()->where('invoice_payment_id', $payment->id)->first()`, system context of the job). Not cancelled: read the bytes of its stored PDF from the media disk exactly as `SendInvoiceEmail::storedPdf()` does; no bytes: `giveUp(self::FAILURE_ATTACHMENT_MISSING)` with the new constant `FAILURE_ATTACHMENT_MISSING = 'attachment_missing'` and return. Cancelled: no attachment (AS-1). No receipt (a transfer or card payment, or a carried copy, which sends no confirmation of its own; no cash payments exist before this phase, AS-2): unchanged behaviour.
- R-15-10-2 (mail): `PaymentConfirmationMail::forPayment()` gets an optional `?array $receipt = null` (`{name: string, data: string, number: string}`); the constructor keeps `public readonly ?string $receiptNumber` and the private file; `attachments()` returns one `Attachment::fromData(fn () => data, name)->withMime('application/pdf')` when a receipt is given, else `[]`. The view adds one escaped line `payment_mail.receipt_attached` (cs "V příloze posíláme příjmový pokladní doklad č. :number." / en "The cash receipt no. :number is attached.") only when a receipt is attached; the text alternative follows from the same view. File name from `CashReceiptPdf::fileName()` (generated, never user text).
- R-15-10-3 (lock on send): `markSent(?string $receiptId)` becomes one `DB::transaction`: when a receipt id is given, the receipt row is locked first (`lockForUpdate`); then the existing conditional update `sending -> sent`; when it changed exactly one row and the receipt is neither cancelled nor locked, `forceFill(['lock_state' => CashReceiptLockState::Locked])->save()` and `CashReceiptAudit::locked($receipt, <the payment's creator or null>)`. A failure rolls back both and reaches the existing catch (back to queued). The `catch (Throwable $e)` block and `failed()` stay as they are. Race with the cancel of 15-12 (stated in the class docblock): the cancel locks the invoice, the payment and then the receipt row; this job locks only the receipt row and reads `cancelled_at` and `lock_state` under that lock, so a cancel and a send serialize on the receipt row: a receipt cancelled first is never locked by the send, and a receipt locked first can still be cancelled (the guard of 15-02 accepts a cancel in either lock state). The job never takes the invoice or payment row lock, so the two cannot deadlock.
- R-15-10-4 (docblocks): `SendPaymentConfirmation` class docblock: the confirmation now carries the receipt of a cash payment and its successful send locks that receipt (Phase 15 D-12), a different row in a different table; it still takes no lock on and writes nothing to the invoice. `PaymentConfirmationMail` docblock: "no attachment" becomes "the receipt of a cash payment as the only attachment". `QueuePaymentConfirmation` docblock: a cash payment's receipt is attached by the job; the grace window lets an edit or a cancel happen before it leaves. `SendInvoiceEmail` docblock (lines ~62-66): the document e-mail stays the only lock of an invoice; the confirmation locks only the cash receipt (Phase 15 D-12).
