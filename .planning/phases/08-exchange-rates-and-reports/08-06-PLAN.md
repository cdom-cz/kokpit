Decisions made in this plan (recorded):
- Expected list date = today when today is a Czech working day and the Prague time is at or after `kokpit.rates.final_hour`, otherwise the previous working day; lag = number of Czech working days after the newest stored `rate_date` up to and including the expected date. Thresholds `kokpit.rates.health.warning_after_working_days` = 1 and `error_after_working_days` = 2. Never downloaded = Error (same philosophy as the scheduler heartbeat; research Pitfall 15, the operator note follows in plan 08-14).
- The indicator reads `MAX(rate_date)` in the system context: the System page is Admin-only and a date is not sensitive, and the registry may run outside a request.
- Gap self-heal: working days from `max(oldest stored rate_date, day - kokpit.rates.gap_lookback_days)` up to the previous working day of the run's day that have no stored list trigger one `daily-year` request per affected year, inserted with insert-or-ignore; at most one heal round per Prague day (cache key `kokpit:cnb-gap-heal:<day>`), so a day the calendar wrongly expects (assumption A5) costs one request a day, not four. Lookback 31 days. A fresh install (only today stored) heals nothing; history is the Admin's backfill (plan 08-08).
- A heal failure fails the run like a daily failure (the final run then alerts); the daily rows already stored stay.
- `daily-year` takes only `year` (API description); its rows are validated like the daily rows and grouped by `validFor`; a list dated after the run's day is ignored.

Fictional data only: year payloads in tests are built at runtime with invented rates. Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
