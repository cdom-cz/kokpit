Decisions made in this plan (recorded):
- Assumption A1: Czech Excel opens a UTF-8 BOM CSV with `;` as delimiter and a decimal comma; both are config values (`kokpit.reports.csv.delimiter` ';', `kokpit.reports.csv.decimal_separator` ','). Dates are ISO `Y-m-d` (sortable, read as dates by Czech Excel).
- Numbers in the CSV are written as text in the configured decimal format (seconds as an integer); amounts are the exact major-unit strings of `Money::toMajor()` with the separator swapped, never floats.
- Text cells are built as explicit OpenSpout string cells after the apostrophe prefix; the value-inferring row factory of OpenSpout is never fed user text (research Pitfall 1). A self-check test proves the canary would catch the inferring factory.
- The job reads the record in the system context (`KokpitJob` middleware), skips a ready record, writes to a temporary file and then streams it to `ReportExport::storagePath()` on the default (private) disk, and marks the record ready and notifies the owner with `notifyNow` in one transaction (pattern of `NotifyLongRunningTimers`). `failed()` marks the record failed inside an explicit system run (the job middleware does not wrap `failed()`).
- `#[Timeout(240)]`, below the 300 s supervisor (`HorizonConfigTest`); rows are streamed from the lazy reader (Horizon workers have 128 MB).
- The bell notice is database-only and non-queued; its body escapes the label once with `e()` (pattern of `LongRunningTimerNotification`).
- The record label is built by the page action from the selected client and project names and the period (`Str::limit` 200).

Fictional data only: names and descriptions in tests are invented, formula canaries are built at runtime. Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
