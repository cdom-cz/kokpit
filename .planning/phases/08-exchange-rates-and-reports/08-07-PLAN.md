Decisions made in this plan (recorded):
- Amounts are computed per entry and rounded once, then summed (research Pattern 5), so the export and the dashboard reproduce the report totals exactly.
- The effective type and rate are resolved set-based in the reader's SQL (`COALESCE` over task, parent task, project, client; zero is a value, only null defers); `TimeEntryRateResolver` and `TaskBillingResolver` stay the specification and a parity test pins the SQL to them. The global default never applies in SQL because every client stores a rate.
- The entry's own billable flag decides whether it carries an amount (TI-04 lets the Admin override the default); an effective type `fixed_price` never carries one (D-07), whether it comes from the project or from a task or parent override (assumption 3: task-level fixed prices show hours only, no amount and no per-task effective rate).
- Assumption 4 (adopted research recommendation): billed entries are priced with the current rate until Phase 10 snapshots them; the page labels its amounts accordingly.
- The reader refuses any caller that is neither the Admin nor a system run (its joins bypass the Partner scope of the joined tables, like `TimeEntryRateResolver`).
- Archived clients, projects and tasks stay in the report (joins read them; archiving never hides tracked time).
- Filters live in the URL and are re-validated on every request like `TimesheetPage`; a bad value falls back (non-uuid ids are dropped, a bad or too long custom range falls back to this month); `ReportFilters::MAX_RANGE_DAYS` = 366.
- Group switch values `task` (default), `day`, `user` replace the innermost level under each project.
- No UI-SPEC exists for this phase: the page uses Filament form components, `x-filament::section`, `x-filament::badge`, Alpine collapse and inline styles, never Tailwind utility classes (research Pitfall 11).

Fictional data only: clients, rates and CNB rates in tests are invented. Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
