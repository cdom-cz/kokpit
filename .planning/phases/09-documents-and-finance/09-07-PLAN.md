Decisions carried in (locked): D-09 (deletion single or bulk is permanent after a confirmation dialog and removes the stored object with the row; each deletion is written to the activity log with name, size, owner type; no trash; reversibility one-way, decided by the owner, so no checkpoint is inserted), D-02 (rename, visibility toggle, delete on the shared tab), D-03 (flag only for project and task files; Admin can hide later).

Decisions made in this plan (recorded):
- `Document` logs `name`, `visible_to_client`, `owner_type`, `size_bytes` (research Pitfall 11); `description` is never logged. The activity package moves the attributes to `old` on the deleted event.
- `Document` has no record page, so its history is read in the activity overview (`ActivityResource`) and not through an `ActivityHistoryRelationManager` subclass; recorded as a deviation from Add-a-model checklist item 8.
- Delete order: authorize as actor, then inside `runAsSystem()` and `DB::transaction()` re-read the row `lockForUpdate()` and call Eloquent `delete()`; the medialibrary hook deletes the media and the observer the object; the `s3` disk throws on failure, so the row rolls back (research Pitfall 4). A commit failure after a removed object is the accepted rare orphan; plan 09-20 adds the consistency check.
- Bulk delete runs one `DeleteDocument` per record, catches per record and reports counts; it never stops at the first failure.
- Explicit file deletion here and the transaction deletion of plan 09-13 are the only paths that remove stored objects (D-21 amends D-09); archiving an owner never calls `DeleteDocument`.
- `Document.php` was last edited by plan 09-21 (archived-owner scopes, wave 2), hence the dependency; this plan adds the activity attributes only.
