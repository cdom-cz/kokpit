Decisions carried in (locked): D-12 (receipts through the shared Soubory relation manager; Admin-only), D-14 (deleting a transaction deletes its receipt files with confirmation; receipt-count column and "without receipt" filter), D-09 as amended by D-21 ("deleting an owning record also removes its files" means the real deletion of a transaction; archiving a client, project or task hides its files and never deletes objects; restore brings them back), D-03 (transaction files never visible), D-11 (a file counts for the client in its denormalized `client_id`).

Decisions made in this plan (recorded):
- Clients, projects and tasks are only archived (soft delete) and comments are append-only, so the transaction is the only owner whose deletion removes files in this phase (research Pitfall 6, D-21). Archiving hides an owner's files from the Partner and from the default Admin listing (scopes of plan 09-21, filter of plan 09-14); the Admin still reaches them under the "archived owners" filter and on the owner's own page.
- Receipts are not caught by the archived-owner rule (plan 09-21 limits it to client, project, task and comment files), so a receipt of a transaction whose client is archived stays in the default listing; this plan adds that case to `TransactionReceiptsTest`.
- `DocumentOwnerDeletionTest` lives under `tests/Feature/Documents` (not `tests/Arch`), because its archive and restore proofs need the refreshed database that the Feature directory provides; its source-scan cases work there unchanged.
- Receipts move with a changed transaction client or project through one query update of `documents` (no model event, so no activity row, acceptable because the logged document attributes do not change).
- `DeleteTransaction` deletes each receipt through `DeleteDocument` before the transaction row, inside one DB transaction; an object already removed when a later step fails is the accepted rare case of D-09 (one-way).
