<objective>
Close code review finding WR-01: `DeleteDocument` and `DeleteTransaction` destroy stored objects inside the database transaction, so a later failure (a second receipt, the transaction row, the commit) rolls the rows back but not the objects, and receipts (finance records) end up listed without their file.

Purpose: the database is the source of truth and the irreversible side effect comes last. Rows go in the transaction; objects go only after the outermost commit; a rollback costs nothing; an object the disk refuses after the commit is retried in the background, so DO-03 ("deleting a record also removes its stored object") is not weakened.
Output: a restructured `DeleteDocument`, the queued `RemoveDocumentObjects` job, a `DeleteTransaction` whose receipts keep their objects on rollback, corrected failure copy, and tests for commit, rollback, refusal and retry.
</objective>

Decisions made in this plan (recorded):
- Supersedes the plan 09-07 order ("remove the object inside the transaction, verify it is gone, roll back when it stands") per 09-REVIEW.md WR-01: rows first, objects after the commit. A failure to remove an object after the commit can no longer refuse the delete; it is reported and retried by `RemoveDocumentObjects` instead. An orphan object is invisible and recoverable; a row without its object is neither.
- The media rows are deleted with a query-builder delete (`Media::query()->whereKey(...)->delete()`), which fires no model event, so the medialibrary `MediaObserver` cannot remove the file inside the transaction; the document is deleted with `deletePreservingMedia()`, so the package's own deleting hook skips the media. The allowlisted `deleted` activity row of the document is still written in the same transaction.
- After the commit the same remover the observer used runs on the retained media instances (`Spatie\MediaLibrary\MediaCollections\Filesystem::removeAllFiles()`, conversions and the empty directory included), followed by the existing check: object still there, one strict `delete()`, check again.
- The retry job exists so that DO-03 is not weakened: without it a transient bucket error would leave an orphan object that only a test-time consistency check could find. The job is guarded (media disk only, document object path shape only, never an object a media row still uses) because it deletes by path on the private bucket.
- `DeleteTransaction` keeps its code shape: each receipt goes through `DeleteDocument` inside the outer transaction, and Laravel attaches the after-commit callback of the nested transaction to the outer one, runs it only after the outermost commit, and drops it when the outer transaction rolls back.
- The transaction delete failure copy no longer blames a receipt file (that can no longer stop the delete): `finance.transactions.notifications.delete_failed` becomes "Transakci se nepodařilo smazat. Zkuste to znovu."
