Rulings made in this plan (recorded):
- R11-07-1 (Pattern 1): `DocumentIssuer::issue()` ends, after `storePdf()`, with: when the admin row's `card_payment_enabled` is true, `PaymentLink::open($issued, $issued->total_minor, $context->actor)` and `CreatePaymentLink::dispatch($link->id)->afterCommit()`. The insert guard of plan 11-06 needs the state already issued, which is why the row is written after the flip; a rollback of the issue takes the row and the dispatch back.
- R11-07-2 (Pattern 2, Pitfall 7): `CreatePaymentLink extends KokpitJob`, `#[Idempotent(how: ...)]`, default tries, backoff and 60 s timeout; constructor `public readonly string $linkId`. `handle(StripeGateway $gateway, StripeConfig $config)`: (A) one transaction locking the document then the link row; a row that is not pending is done; a cancelled document deactivates it with `cancelled`, remaining 0 with `paid`, remaining other than the offered amount with `amount_changed`, without calling Stripe; otherwise the request is built and the transaction commits. (B) Not configured: failed `not_configured`. Otherwise `createLink()` with idempotency key = row id; a `StripeGatewayFailure` that `isRetryable()` while `$this->attempts()` is below the tries is rethrown so the queue retries with the same key; any other failure marks the row failed with its class. (C) one transaction locking the document then the row: still pending, not cancelled and the remaining amount still equal to the offered one makes it active with `stripe_link_id`, `stripe_url` and `activated_at`; otherwise the Stripe id and URL are stored on the row, a still-pending row is deactivated with the matching reason, and after the commit `deactivateLink()` is called and `remote_deactivated_at` set (a failure there is left for the sweep of plan 11-10). A returned URL that is not https on a stripe.com host is treated as failure class `api_error`.
- R11-07-3 (D-09, Surface I): `failed(Throwable)` enters the system context by hand (the `SendInvoiceEmail` precedent) and marks a still-pending row failed with the failure class of a `StripeGatewayFailure` or `unexpected`. Every move to failed sends, after its transaction, `AdminAlerter::alert('payment-link-failed:'.$invoiceId, new OperationalAlert(title, body, url of the document detail, label, mailSubject))` with the copy of `lang/cs/payment_notices.php` `link_failed`; the body names the document number only.
- R11-07-4 (Surface I mail subject): `OperationalAlert` gains a last optional constructor argument `?string $mailSubject = null`; `toMail()` uses it when set, otherwise the title as today; `withLine()` keeps it. Existing alerts are unchanged.
- R11-07-5 (U-15, research Code Examples): the Stripe-side texts come from `lang/{cs,en}/payment_links.php` `stripe.product.invoice` ("Faktura :number" / "Invoice :number"), `stripe.product.proforma` ("Zálohová faktura :number" / "Proforma invoice :number"), `stripe.confirmation` and `stripe.inactive` (UI-SPEC "Stripe-side strings"), in the document language.
