Rulings made in this plan (recorded):
- R-13-05-1 (one predicate, two shapes): `PayLinkBlock::forHtml(Invoice $invoice): ?array{lead: string, url: string, label: string}` returns null exactly when `applies()` is false (it calls the same private `url()`), else the lead `invoice_mail.pay_block_lead`, the stable URL and the label `invoice_mail.pay_button`, both texts in the document language. `PayLinkBlock::textBlock(array $link): string` returns a blank line, the lead and the URL on its own line (today's block). `forMail()` becomes `forHtml()` plus `textBlock()` with unchanged output. The class docblock records that the Phase 13 hand-over is done: the HTML button and the text block of the document e-mail both come from one `forHtml()` call.
- R-13-05-2 (InvoiceMail): constructor `(public readonly string $mailSubject, public readonly string $body, public readonly ?array $payLink, public readonly array $files, string $language)`; it computes `public readonly string $plainText` as the body, or the right-trimmed body followed by `PayLinkBlock::textBlock($payLink)`, which is byte for byte the text sent before this phase; it calls `$this->locale($language)`; `content()` is `new Content(markdown: 'mail.invoice', text: 'mail.invoice-text')` (an explicit text view wins over the Markdown text rendering, research Pattern 1); `attachments()` unchanged; the class docblock is rewritten (HTML on the shared layout, the Admin text escaped and never parsed as Markdown, the plain-text alternative kept, not queued). `resources/views/mail/invoice-text.blade.php` stays as it is.
- R-13-05-3 (PlainTextHtml, research Pattern 3, verified in DDEV): `App\Domain\Notifications\Mail\PlainTextHtml::paragraphs(string $text): HtmlString` normalises CR LF and CR to LF, trims, splits into paragraphs at two or more line breaks, escapes every line with `e()`, joins the lines of a paragraph with `<br>` and a line break, wraps each paragraph in `<p>` and separates paragraphs by exactly one blank line, with no indentation. CommonMark reads a line that starts with `<p` as an HTML block that ends at a blank line, so nothing inside is parsed as Markdown. An empty text gives an empty string.
- R-13-05-4 (view): `resources/views/mail/invoice.blade.php`, flush-left inside `<x-mail::message>`: the paragraphs of `$body` printed raw from `PlainTextHtml::paragraphs()`; when `$payLink` is set, the lead as an escaped paragraph, `<x-mail::button :url="$payLink['url']">` with the escaped label, and an escaped paragraph `mail_layout.button_fallback` followed by the URL as text (some clients block buttons). No `{{ $body }}` into the Markdown slot anywhere (research Pitfall 4).
- R-13-05-5 (send job): `SendInvoiceEmail` reads the invoice once, calls `PayLinkBlock::forHtml()` once and sends `new InvoiceMail($row->subject, $row->body, $link, $files, $invoice->language->value)`; `bodyToSend()` goes; the log row still stores only what the Admin confirmed; the docblock paragraph about the pay block says the button (HTML) and the block (text) both follow the stored body at send time from one predicate.
