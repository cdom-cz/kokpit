<objective>
One shared HTML layout for every e-mail Kokpit sends: the published Laravel mail theme named `kokpit`, a header with the supplier name or logo, a footer with the supplier details, all read through one system-context reader, the logo embedded inline, layout strings in Czech and English, and a plain-text alternative that never shows Markdown escapes. The tracer: a partner invitation sent from a worker with no user, and again from a Partner session, leaves with the supplier's header and footer and the kokpit theme inlined.

Purpose: P13-01, P13-02 and the shared parts of P13-08 and P13-10; D-02 (Laravel mail theme, costly), D-03 (supplier header and footer, logo renders in mail clients), D-04 (alerts share the layout); research Patterns 1 and 2, Pitfalls 1, 2, 3, 5 and 11. Every later plan of the phase builds its e-mails on this layout.
Output: the published and customised mail views, the `kokpit` theme, `MailBrand`, `MailLogo`, `EmbedMailLogo`, `MailText`, `DocumentImage::contents()`, the `mail_layout` strings, the shared test fixture `MailFixtures` and the layout tests.
</objective>

Rulings made in this plan (recorded):
- R-13-01-1 (published files): publish with `ddev exec php artisan vendor:publish --tag=laravel-mail` and `--tag=laravel-notifications`, then keep only the files this phase customises: `html/layout`, `html/message`, `html/header`, `html/footer`, `html/themes/kokpit.css`, `text/layout`, `text/message`, `text/header` under `resources/views/vendor/mail/`, and `resources/views/vendor/notifications/email.blade.php`. Every other published copy (html and text button, panel, subcopy, table, text footer, `html/themes/default.css`) is deleted again: the framework copies stay the fallback through the component path (`Markdown::htmlComponentPaths()` appends the framework directory), so upstream fixes keep reaching them. A later re-publish runs without `--force`, which keeps the customised files.
- R-13-01-2 (theme config): `config/mail.php` gets an explicit `markdown` block with all three keys: `theme` `kokpit`, `paths` `[resource_path('views/vendor/mail')]`, `extensions` `[]` (the observed framework default plus the theme, so the path cannot be lost).
- R-13-01-3 (MailBrand): `App\Domain\Notifications\Mail\MailBrand` is a `final readonly` value class with `name` (string), `street`, `postalCode`, `city`, `companyId`, `vatId`, `email`, `phone`, `website`, `registrationNote` (each `?string`, null when blank), `logoPng` (`?string`), `logoWidth` and `logoHeight` (`?int`, the display size), the constant `LOGO_NAME = 'kokpit-logo.png'`, `addressLine(): ?string` (street, then postal code and city, comma-separated, blanks skipped), `hasLogo(): bool`, `static current(): self` (resolves the scoped container binding), `static read(): self` (reads exactly the whitelisted fields of `SupplierSettings` inside `app(PartnerContext::class)->runAsSystem(...)`; `name` is the trimmed `company_name` when not blank, otherwise `config('app.name')`; any `Throwable` gives `fallback()`), `static fallback(): self` (the application name and nothing else). It holds raw values only; labels are translated by the views at render time (R-13-01-4). Bound with `$this->app->scoped(MailBrand::class, ...)` in `AppServiceProvider::register()`, so one read serves one request, console run or queue job and the next job reads again (the scope `PartnerContext` uses).
- R-13-01-4 (labels follow the e-mail): the views print labels through `__('mail_layout.<key>')` when they render, so the locale of each Mailable or notification decides them, not the locale at read time.
- R-13-01-5 (header and footer markup): the header cell shows the logo image (task 2) or the name as text, and wraps it in a link only when `website` is set (the `url` prop defaults to null; the stock special case for the word Laravel is removed). The footer prints up to five lines, each only when it has content: the name; `addressLine()`; the company ID and the VAT ID with their `mail_layout` labels; the contacts (e-mail, phone, website joined with a middle dot); the registration note. Every value goes through `{{ }}` (escaped). The published footer component prints its slot as it is, without the Markdown parse of the stock footer, so an asterisk or underscore in a company name stays literal. The `<title>` of the layout is the brand name.
- R-13-01-6 (logo): `DocumentImage::contents(string $path): ?string` is a public read of a stored document image that reuses the private path-pattern check and returns null for a foreign path or a missing object. `App\Domain\Notifications\Mail\MailLogo::fromPng(string $png): ?array{png: string, width: int, height: int}` decodes with GD, scales down (never up) to fit 360 x 120 px keeping alpha, re-encodes as PNG and returns the display size that fits 180 x 60 (never enlarged); any GD failure returns null. `MailBrand::read()` fills the logo fields from `logo_path` through both. The HTML header emits `<img src="cid:kokpit-logo.png" alt="{name}" width height>` only when `hasLogo()`. `App\Domain\Notifications\Mail\EmbedMailLogo::handle(MessageSending $event): void` embeds the same memoised bytes with `$event->message->embed($png, MailBrand::LOGO_NAME, 'image/png')` only when the HTML body is a string containing the cid reference; it returns nothing (a false return would cancel the send). Registered in `AppServiceProvider::boot()` with `Event::listen(MessageSending::class, EmbedMailLogo::class)` (domain folders are not auto-discovered). No route, no hosted URL, no data URI (research: T-10-07 and the Phase 12 public-route audit).
- R-13-01-7 (theme): `kokpit.css` starts from the framework `default.css`: primary button background and border amber `#f59e0b` with dark text `#18181b` (the Filament panel primary is Amber; white on amber fails contrast), success and error buttons kept for the `level` mapping, the system font stack, zinc text colours, the 570 px column, no CSS custom properties, no web fonts, no external URL.
- R-13-01-8 (notification view): the published `notifications::email` uses `mail_layout.greeting` as the default greeting for every level, prints a salutation only when the notification sets one (no default, so a second sign-off under the footer never appears), each line of that salutation escaped and the lines joined with `<br>` (so "regards" and the supplier name can stand on two lines), and its subcopy is `mail_layout.button_fallback` followed by the link, instead of the cs.json sentences of the stock view.
- R-13-01-9 (escaping): `App\Domain\Notifications\Mail\MailText::escapeMarkdown(string $text): string` is the body of the current private helper of `TaskNotification`, moved unchanged (whitespace collapsed, backslash, backtick, asterisk, underscore, brackets, parentheses, hash, pipe, tilde and exclamation mark escaped). `MailText::unescapeMarkdown(string $text): string` removes exactly one backslash in front of exactly those characters. The published text layout runs the stripped header, slot, subcopy and footer through `unescapeMarkdown()`, so the plain-text part reads as written (research Pitfall 5). `TaskNotification` calls `MailText::escapeMarkdown()` and keeps no copy of its own.
- R-13-01-10 (strings): `lang/cs/mail_layout.php` and `lang/en/mail_layout.php` with the same keys `company_id` (IČO / Company ID), `vat_id` (DIČ / VAT ID), `greeting` (Dobrý den, / Hello,), `regards` (S pozdravem / Kind regards), `button_fallback` (Pokud tlačítko nefunguje, zkopírujte tento odkaz do prohlížeče: / If the button does not work, copy this link into your browser:). Header comment as in `lang/en/invoice_mail.php` (a test compares the keys).
- R-13-01-11 (test fixture): `Tests\Support\MailFixtures` with `sent(): list<Email>` (the original messages of the array transport), `to(string $address): list<Email>` (those addressed to one recipient) and, in task 2, `storeLogo(int $width, int $height): string` (a GD-drawn PNG uploaded through `DocumentFixtures::upload()` and `DocumentImage::store(..., 'logo')` as the system, saved as `SupplierSettings::logo_path`, then `app()->forgetScopedInstances()`; no binary in git).
