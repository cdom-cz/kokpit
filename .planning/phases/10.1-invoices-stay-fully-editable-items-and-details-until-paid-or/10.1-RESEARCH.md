## User Constraints (from CONTEXT.md)

### Locked Decisions

**Lock model**
- **D-01:** An issued invoice or proforma is locked **only by a successfully sent e-mail** (the e-mail reaches the sent state in `invoice_emails` / `InvoiceEmailState`). A queued, pending or failed e-mail does not lock. Payments (manual or card), partial payments, credit notes and storno do **not** lock and are not lock conditions; the payment state is simply recomputed from the data. — **Reversibility:** costly — replaces the status-driven immutability that DB guards, actions, policies and the Partner view were built on.
- **D-02:** No "mark as sent manually" action in this phase; only an actual successful e-mail locks.
- **D-03:** Admin can **unlock** a locked invoice with an `Unlock` action that requires a **reason**; the unlock is audited. The invoice stays editable until the next successful e-mail send locks it again. There is no one-edit auto-relock.
- **D-04:** Editing an invoice that has payments or credit notes is allowed (when unlocked); the system shows a warning when totals fall below what was paid or credited and recomputes the payment status. No hard block.

**What stays editable (while unlocked)**
- **D-05:** Items (text, quantity, unit, price, add, delete) are editable; line amounts and totals are recomputed with the same single `HALF_UP` rounding as at issue.
- **D-06:** Dates (issue, taxable supply, due), customer and supplier snapshots and the bank account, and invoice currency and language are editable. A currency change re-takes the CNB rate and CZK total (Phase 8 `ExchangeRateConverter`) and the bank account follows the currency (Phase 3 D-04).
- **D-07:** Linked time can be added and released on an issued invoice exactly as on a draft (Phase 10 D-03, D-05, D-06): adding generates new items, releasing returns entries to unbilled. While the invoice is locked the time stays locked with it; unlocking frees it for these changes. Time entry billing state and the entry-to-invoice link guard must follow the invoice lock instead of the issued state.
- **D-08:** Fixed, never editable: the document **number** and the document **kind** (invoice / proforma / credit note). The series stays gap-free. — **Reversibility:** one-way — a changed number would break the gap-free guarantee and every printed or sent reference.

**PDF, e-mail, payment links**
- **D-09:** Saving an edit **regenerates the PDF** and replaces the stored one in `documents` (existing `RegeneratePdf` flow); the replace is not subject to the deletion confirmation of Phase 9 D-03. No PDF version history.
- **D-10:** After an edit, nothing is sent automatically. Admin re-sends manually; a successful send locks the invoice again.
- **D-11:** When amount or currency change, the Stripe payment link is invalidated (deactivated) and a new one created for the current amount; the SPAYD QR is regenerated with the PDF. A card payment already recorded keeps its record.

**Database guards and audit**
- **D-12:** The DB guard triggers stay but are **conditional**: a lock column (for example `locked_at`) decides. An issued-but-unlocked invoice, its items and its linked time entries are writable; a locked one refuses INSERT, UPDATE and DELETE (also raw SQL), except what stays writable today (payment state, internal note). Number and kind have their own always-on immutability rule. Exact column and trigger design is the planner's call but must keep the raw-SQL test helper (`Immutability`) coverage. — **Reversibility:** costly — migration of the guards of `invoices`, `invoice_items`, `time_entries` link guard.
- **D-13:** Every change to an issued invoice after its first send, plus every unlock and lock, is written to the Audit domain with who, when and before/after (items, dates, parties, currency) and, for an unlock, the reason. Invoices that were never sent are not logged (they behave like drafts).

## Summary

Phase 10 froze an issued document at four layers that all key on the stored `invoices.state = 'issued'`: (1) one table guard trigger on `invoices` created with an empty mutable list (not even `updated_at` may change), (2) four child guards on `invoice_items`, `invoice_item_sources`, `invoice_admin` (and `invoice_item_sources`) that follow the parent state, (3) the `time_entries` link guard `kokpit_guard_time_entry_link()` that allows a reservation only by a draft and a release only by a storno credit note, and (4) application code (`UpdateDraft`, `AddEntriesToDraft`, `ReleaseEntries`, `AddFixedAmount`, `RegeneratePdf` all throw `not_draft`/refuse an issued document; `EditInvoice::mount()` redirects non-drafts; the entries relation manager is read-only for non-drafts). The Phase 10.1 change is therefore not one switch but a coordinated move of the *freeze criterion* from `state` to a new lock marker, plus a genuinely new "edit an issued document" pipeline.

The cleanest, smallest-blast-radius database design is a **new text lifecycle column `invoices.lock_state` (`open` | `locked`)**. The three existing child-guard triggers and the existing generic child function `kokpit_guard_child_of_frozen_parent()` accept any parent column and any "open" string (`childGuardTriggerSql(table, fk, parentTable, parentStateColumn, openState, ...)`), so they are simply re-created with `('invoices', 'lock_state', 'open')` and **no function change**. The `invoices` row itself needs a *new dedicated guard function* (the generic `kokpit_guard_frozen_row()` would let a raw `DELETE` of an issued-but-open row through and cannot express "number/kind always immutable" or "unlock only through a sanctioned path"). The time-entry link guard needs its `'draft'` checks widened to "document accepts time changes" (draft, or issued and open and not a credit note). The Stripe composite foreign key `payment_links(invoice_id, currency) -> invoices(id, currency)` blocks any currency change once a link row exists (links are never deleted); this must be relaxed for D-06 + D-11 to work together.

The new application pipeline is one transactional Action (`UpdateIssuedDocument`) that locks the invoice row, asserts "editable", reuses the draft line/total code (`InvoiceItemInput`, `DraftTotals`, `DraftLines`, extracted shared parts of `UpdateDraft` and `DocumentIssuer::convertTimeLines`), re-takes the CNB trio when needed, recomputes totals, reconciles/re-creates the Stripe link (`PaymentLinks::reconcile()` already deactivates with reason `amount_changed`), replaces the PDF (`DeleteDocument` with the confirmation flag + `StoreGeneratedDocument`, inside the same transaction), and writes one explicit audit row. The lock itself is set by `SendInvoiceEmail` in the same step that marks the e-mail row `sent`; the unlock is a separate Admin-only Action guarded in the database by a transaction-local flag in the same style as `kokpit.payment_deletion`.

**Primary recommendation:** Add `invoices.lock_state`, re-key the existing child guards on it, write one new `kokpit_guard_invoice_row()` function (always-on number/kind/identity immutability, open rows writable but never deletable once issued, locked rows frozen except a flag-gated `locked -> open`), widen the time-link guard through one SQL helper, then build `UpdateIssuedDocument` / `UnlockInvoice` / a lock step in `SendInvoiceEmail`, generalise the existing editor page instead of forking it, and treat credit notes as locked-at-issue forever.

### Pattern 1: Lock marker as a plain text lifecycle column (re-using the child guards)
**What:** `invoices.lock_state varchar(8) NOT NULL DEFAULT 'open'` with `CHECK (lock_state IN ('open','locked'))`, `CHECK (state = 'issued' OR lock_state = 'open')`, `CHECK (kind <> 'credit_note' OR state = 'draft' OR lock_state = 'locked')`. Names are the planner's call (CONTEXT: "Names ... Claude's Discretion").
**When to use:** every child guard and the time-link helper read this one column.
**Example (sketch, new names are `[ASSUMED]` proposals):**
```sql
-- invoices row guard (replaces invoices_frozen_guard)
CREATE OR REPLACE FUNCTION kokpit_guard_invoice_row() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE
  open_cols   text[] := ARRAY['currency','language','issue_date','taxable_supply_date','due_date',
                              'subtotal_minor','vat_minor','total_minor','note',
                              'supplier_snapshot','customer_snapshot','bank_snapshot','lock_state','updated_at'];
BEGIN
  IF TG_OP = 'DELETE' THEN
    IF OLD.state <> 'draft' THEN
      RAISE EXCEPTION 'an issued document is never deleted' USING ERRCODE = 'KP001';
    END IF;
    RETURN OLD;
  END IF;
  IF OLD.state = 'draft' THEN RETURN NEW; END IF;                       -- draft edits and the issue flip
  IF NEW.state <> 'issued' OR (to_jsonb(NEW) - open_cols) IS DISTINCT FROM (to_jsonb(OLD) - open_cols) THEN
    RAISE EXCEPTION 'number, kind and identity of an issued document never change' USING ERRCODE = 'KP001';
  END IF;
  IF OLD.lock_state = 'locked' THEN
    IF (to_jsonb(NEW) - ARRAY['lock_state','updated_at']) IS DISTINCT FROM (to_jsonb(OLD) - ARRAY['lock_state','updated_at']) THEN
      RAISE EXCEPTION 'a locked document accepts no write' USING ERRCODE = 'KP001';
    END IF;
    IF NEW.lock_state = 'open' AND (OLD.kind = 'credit_note'
       OR current_setting('kokpit.invoice_unlock', true) IS DISTINCT FROM OLD.id::text) THEN
      RAISE EXCEPTION 'a document is unlocked only by the sanctioned unlock' USING ERRCODE = 'KP001';
    END IF;
  END IF;
  RETURN NEW;
END $$;
```

### Pattern 2: Sanctioned-path flag for the unlock (copy of the payment-deletion pattern)

### Pattern 3: The lock is set where "sent" becomes true
In `SendInvoiceEmail::handle()` the existing success path is a bare `InvoiceEmail::query()->...->update(['state' => Sent, 'sent_at' => now()])` after `Mail::to(...)->send(...)` [VERIFIED: `app/Domain/Invoicing/Jobs/SendInvoiceEmail.php` handle()]. Wrap "mark sent" and "lock invoice" in one `DB::transaction` that locks the invoice row first (same lock order as the edit Action: invoice, then children). If the lock write fails after the transport accepted the message, the existing catch puts the row back to `queued` and the retry re-sends: that is the already documented at-least-once guarantee, not a new hazard. Put the lock step in the **document e-mail job**, not on any `invoice_emails` state observer: Phase 13 D-05 adds a payment-confirmation e-mail after every credited payment, and that e-mail must never lock the invoice [CITED: `.planning/phases/13-unified-e-mail-layout-and-html-e-mail-templates/13-CONTEXT.md` D-05, D-06].

### Pattern 4: One transactional Action per write path, thin Filament page
Unchanged project rule: the page hands a plain array to an Action that re-validates, locks the row first, computes every amount itself, and never trusts ids/totals from the browser (`UpdateDraft` docblock, `EditInvoice` class docblock). `UpdateIssuedDocument` follows the same contract and reuses `InvoiceItemInput::list()`, `DraftTotals::lineTotal()`, `DraftLines`, and the id-matching logic (`assertOwnLines`).

### Pattern 5: PDF replace inside the edit transaction
`DeleteDocument::handle($actor, $document, confirmedIssuedPdf: true)` deletes the document row and media row in its own (nested) transaction and removes the S3 object only in `DB::afterCommit()`; the `invoice_admin.pdf_document_id` FK is `ON DELETE SET NULL`, which the PDF-link guard explicitly allows ("cleared only when its file is deleted") [VERIFIED: DeleteDocument.php docblock; `kokpit_guard_invoice_pdf_link()` body]. Then `StoreGeneratedDocument::handle()` stores the new bytes (it registers `DB::afterRollBack` cleanup of the new object) and the Admin row gets the new link (null -> own document is allowed). A render or storage failure throws and rolls the whole edit back, mirroring Phase 10 D-23. A new class `ReplaceIssuedPdf` is recommended over adding a flag to `RegeneratePdf`, whose test asserts "an existing PDF is never replaced" (`tests/Feature/Invoicing/RegeneratePdfTest.php`).

### Pattern 6: Stripe link refresh is reconcile-then-open, never a Stripe call in the transaction
After the totals are written and the invoice row is still locked: `PaymentLinks::reconcile($locked)` (deactivates the live link with `Cancelled`/`Paid`/`AmountChanged` and queues the remote deactivation after commit) and, when `invoice_admin.card_payment_enabled` and `remaining > 0`, `PaymentLink::open($locked, $remaining, $actor)` + `CreatePaymentLink::dispatch($new->id)->afterCommit()`. This is exactly the body of `RegeneratePaymentLink::handle()` minus the Gate [VERIFIED: file read]. The `reconcile()` precondition is "inside the caller's transaction, document locked" (it throws `LogicException` otherwise).

### Anti-Patterns to Avoid
- **Reading the lock from `state`.** Every place that today means "frozen" via `isDraft()`/`isIssued()` must be reviewed; `state` keeps meaning "numbered or not".
- **A second lock source (`invoice_emails` EXISTS) beside the column.** Two truths will diverge after an unlock. The column is the single truth; the emails table is the history.
- **Bulk `Invoice::query()->update()` for lock/unlock.** It writes no activity row (`LogsAllowlistedActivity` docblock: "a bulk query update raises no model event") - use a model save or an explicit audit row.
- **Calling Stripe inside the edit transaction** (Phase 11 research Pattern 3: link ops are DB rows + queued job after commit).
- **Forking the 1336-line draft editor** into a second page; generalise it.
- **Letting the unlock flag literal appear outside `UnlockInvoice`/the guard migration.**

## Common Pitfalls

### Pitfall 1: The generic guard function lets an open issued row be deleted
**What goes wrong:** Re-using `Immutability::guardTriggerSql('invoices', 'lock_state', 'open', ...)` makes `DELETE FROM invoices WHERE id = <issued, open>` succeed (the generic function only refuses DELETE when the lifecycle column differs from the open value). Children would follow (child guard allows deletes under an open parent), destroying a numbered document and the series' gap-free promise.
**Why it happens:** Phase 10 got "never deletable" for free because every issued row was frozen.
**How to avoid:** dedicated `kokpit_guard_invoice_row()`; test `DELETE` of issued+open via `RawSql::expectSqlState('KP001', ...)`.
**Warning signs:** a schema test that only checks UPDATEs.

### Pitfall 2: Currency change versus composite foreign keys
**What goes wrong:** `UPDATE invoices SET currency = ...` fails with SQLSTATE 23503 once an `invoice_payments` or `payment_links` row exists. Probe: with a referencing composite key `(invoice_id, currency)`, `update inv set currency = 'EUR'` answered `ERROR: update or delete on table "inv" violates foreign key constraint "pl_invoice_id_currency_fkey" ... DETAIL: Key (id, currency)=(..., CZK) is still referenced from table "pl".` [VERIFIED: psql probe on temp tables in DDEV PostgreSQL 18.6]. Because `payment_links` rows are never deleted and nearly every card-enabled issued document has one, D-06 (currency editable) and D-11 (new link after currency change) cannot both hold without migration G10.
**How to avoid:** relax G10 (move the currency check into the link insert guard); refuse currency change in the Action when any `invoice_payments` row exists (G11) and when a credit note names the document (credit notes are denominated in the invoice currency and copy its CNB trio so the CZK totals cancel, `IssueCreditNote` docblock R-23-2).
**Warning signs:** a 23503 surfacing as a 500 in the editor.

### Pitfall 3: Edit racing a queued or in-flight e-mail
**What goes wrong:** The invoice is unlocked, Admin queues the e-mail, then edits before the job runs: the job attaches whichever PDF is linked at send time (`storedPdf()` reads the link when it runs) and then locks the invoice. The customer may receive a version that differs from the stored one, or an edit lands while `Mail::send` is mid-flight and the lock then freezes a document the customer never saw. The lock is not set by "queued" (D-01), so nothing prevents the edit.
**How to avoid (recommendation, Assumption A8):** `QueueInvoiceEmail` and `UpdateIssuedDocument` both take the invoice row lock; the edit refuses with a clear message while an `invoice_emails` row for the document is `queued` or a non-stale `sending`; the job takes the invoice row lock for the "mark sent + lock" step. Stale `sending` (the System page already defines a stale threshold, `UnsentInvoiceEmailsIndicator`) must not block forever.
**Warning signs:** a concurrency test (edit vs send) that is flaky.

### Pitfall 4: Issue-date edits versus numbering period, chronology and CNB rates
**What goes wrong:** (a) The counter scope key comes from the issue date (`NumberPattern::scopeKey()` returns `invoice:<Y>` / `<Y-m>` / `all` by reset period) [VERIFIED: `app/Domain/Settings/Numbering/NumberPattern.php:179-192`]; moving the issue date to another period breaks the meaning of the printed number (D-08 forbids touching the number). (b) `IssueChecks` enforces `issue_date >= latest issue date of the kind` (`issue_date_before_latest`) so the series is chronological; an edited date can break monotonicity against neighbours. (c) The CNB trio and every converted time line were taken "valid on the issue date" (Phase 10 D-09); an edited issue date makes them stale.
**How to avoid:** `IssuedDocumentRules::issueDateWindow()`: the new date must (i) not be in the future (`issue_date_future` blocker precedent), (ii) lie between the issue dates of the previous and next documents of the same kind by `issued_at` order, (iii) map to the same scope key as the old date under the current pattern. The current pattern may have changed since issue (comment: "a pattern change can start a new series but never rewrite a number"), so compare old and new date through the *current* pattern and, if the pattern changed, fall back to same calendar month. CNB re-take on a date change is an open question (A6); default to D-06 literally (re-take on currency change only) and show a warning.
**Warning signs:** Edit moves a December invoice into January under a yearly pattern.

### Pitfall 5: Credit notes and proformas that point at the edited document
**What goes wrong:** A partial or storno credit note holds lines that copy the *original unit price* of the source line and reference it (`credited_item_id`); a storno credit note also copied the CNB trio. Editing a credited line's price/quantity/currency makes the credit note incoherent; deleting a credited line is refused by the FK (23503); `CreditableQuantities` clamps negative remainders to 0 and so would hide a quantity reduction below the credited amount.
**How to avoid (Assumptions A3, A4):** an editable document excludes `isCancelled()` documents and proformas that already have an invoice (`invoiceFromProforma`); a line referenced by any credit line keeps quantity/unit/price and cannot be deleted (description stays editable); currency change refused when a credit note exists; D-04 warnings cover the totals-below-credited case. This is the answer to the question CONTEXT flagged.

### Pitfall 6: Time lines of foreign-currency documents are frozen with a conversion snapshot
**What goes wrong:** `UpdateDraft::generatedPrice()` re-previews time lines with *today's* CNB lists; `DocumentIssuer::convertTimeLines()` freezes the issue-date conversion into `invoice_item_sources.conversion_snapshot` and skips lines that already carry one. If the issued-document edit re-uses the draft preview code, a plain quantity edit would silently re-price a frozen line with today's rate.
**How to avoid:** extract the conversion into a shared service with two modes: *draft preview* (today) and *issued freeze* (issue-date lists, snapshot written, only for lines without a snapshot or whose snapshot is invalidated by a currency/date change). New lines added by D-07 are converted at the document's issue date and frozen at once.

### Pitfall 7: Writing the lock or `updated_at` on a locked row
**What goes wrong:** Under the new rule a locked invoice refuses even an `updated_at`-only write; Eloquent `touch()`, `$touches` relations and `Invoice::save()` on a clean-but-timestamped model all hit KP001. Phase 10 already learned this ("The relation writes nothing to its parent: there is no `$touches`" in `InvoiceEmail` docblock). Open rows accept the write, which can mask bugs in tests that only exercise unlocked rows.
**How to avoid:** keep the "no touch" discipline; add tests that run every relevant Action against a *locked* document.

### Pitfall 8: Existing tests assert "issued = frozen" and will fail by design
**What goes wrong:** After this phase `issue` leaves the document open. Verified examples: `tests/Feature/Schema/InvoiceTablesTest.php:174-184` ("an issued invoice accepts no write at all"), `:196-204` (items), `:206-213`, `:215-221`, `:476-484`; `tests/Feature/Invoicing/IssueDocumentTest.php:188,192` (`forceFill(['total_minor' => 1])->save()` and `touch()` expected KP001); `tests/Feature/Invoicing/DraftEditorTest.php:241` (edit address of an issued document redirects); `tests/Feature/TimeTracking/BillingLockTest.php:926,933` (release refused without storno). Likely also `InvoiceAdminTablesTest` (30 KP001 assertions), `TimeEntryInvoiceLinkTest` (22), `PaymentLinkRecordTest` (22; FK currency mismatch), `RegeneratePdfTest`, `PartnerSafeColumnsTest` (pins the `invoices` column list).
**How to avoid:** introduce a test fixture helper that issues *and locks* (`InvoiceFixtures::issuedLocked()`), update the frozen-state tests to use it, and add the new matrix tests for the open state. Grep `KP001`, `isDraft`, `not_draft` before editing.

### Pitfall 9: Audit conflicts with the existing "free text is never logged" rule
**What goes wrong:** D-13 asks for before/after of items (text), dates, parties and currency. The codebase rule is that the printed note and the snapshots are never logged (`Invoice` docblock: "the printed note and the snapshots are never logged"; `InvoiceHistoryRelationManager` docblock; `UpdateInternalNote`: free text is not logged, T-10-30). Also `InvoiceItem` is *not* a logging model [VERIFIED: `tests/Arch/ActivityAllowlistTest.php` lists the logging models: Client, Contact, Document, Transaction, Invoice, InvoiceAdmin, InvoicePayment, CardPayment, PaymentLink, Project, ProjectBilling, Task, TaskBilling, TimeEntry]. `ActivityPresenter` renders only `attribute_changes` ("Only `attribute_changes` is rendered ... The free-form properties payload of a row is deliberately not read here").
**How to avoid:** write one explicit manual row per edit/lock/unlock through `activity()->performedOn($invoice)->causedBy($actor)->event('edited')->withChanges(['attributes' => $new, 'old' => $old])->log('edited')` with flattened keys such as `items.<position>.quantity`, `customer.name`, `due_date`, `currency`; the unlock reason goes into `attributes.unlock_reason`. This renders in the existing history tab with no presenter change. The values are Admin-only (log is `DeniesPartners`). The owner decision D-13 overrides T-10-30 for this narrow case (Assumption A12 - confirm). For an invoice that was ever sent, save the invoice row with logging disabled (`disableLogging()`, `LogsActivity.php:72`) so one edit does not write both a model-driven row and the explicit row; never-sent invoices keep the existing model-driven logging (drafts are already logged that way, so "not logged" in D-13 should be read as "no explicit post-send entry").

### Pitfall 10: Dropping/recreating the guard in the migration
**What goes wrong:** the old `invoices_frozen_guard` blocks the backfill `UPDATE` itself (no write allowed), and any new CHECK that the backfill violates fails the migration mid-way. 
**How to avoid:** order inside one migration: drop old triggers -> `ALTER TABLE ADD COLUMN lock_state ... DEFAULT 'open'` (metadata-only on PG 18) -> backfill without touching `updated_at` -> add CHECKs -> create the new function/triggers -> re-create child guards -> replace the time-link function -> relax the `payment_links` FK. `down()` must refuse to run if any issued invoice/proforma is open (or backfill them to locked) so the old model's guarantee can be restored.

### Pitfall 11: Partner column exposure
`invoices` is Partner-readable and its column list is pinned (`tests/Isolation/PartnerSafeColumnsTest.php` expects the exact list ending `'issued_at','created_at','updated_at'`) [VERIFIED: lines 159-186]. A `lock_state` column fails that test until a reviewer extends the list; `lock_state` alone is harmless, but **no** unlock reason, locked-at timestamp or sender belongs on `invoices`; those live in the Admin-only activity log (and, if wanted, an Admin-only table). The suspicious-name check (`/hourly|internal|cnb|czk|exchange|payment|source|cost|budget|estimate|billing/i`) does not match `lock_state`.

| A4 | A line referenced by a credit line keeps quantity/unit/price, cannot be deleted; quantity may not drop below the credited amount; description stays editable | Pitfall 5 | Otherwise credit notes diverge from their source; stricter or looser rule is a product call |
| A5 | New issue date must stay in the same numbering scope (current pattern, else calendar month) and between neighbouring documents of the same kind by `issued_at` | Pitfall 4 | Without it, numbers contradict dates; too strict a rule annoys the owner |
| A6 | CNB trio and frozen time-line conversions are re-taken on currency change only (D-06 literally); an issue-date change keeps them and warns | Pitfall 4 | Accounting may require the rate of the (new) issue date |
| A7 | Currency change is refused when payments or credit notes exist; `payment_links_invoice_currency_fk` is relaxed to a plain `invoice_id` FK with an insert-time currency check | Pitfall 2, G10/G11 | If the owner wants currency change with payments, a deeper model change is needed |
| A8 | Edits (and the lock step) are serialised with e-mail sending by the invoice row lock; an edit is refused while a `queued` or non-stale `sending` e-mail exists | Pitfall 3 | Without it the customer may receive a PDF different from the stored one |
| A9 | "Customer and supplier snapshots ... editable" means free editing of the snapshot fields of this document (name, address, ids) plus a "reload from current client/settings" convenience; the bank account follows the currency from `BankAccountSettings`; `appearance_snapshot` and `vat_mode` are not editable | D-06 reading | If the owner only meant "refresh from source", the form is simpler; if free editing, field validation (lengths, company id format) must be defined |
| A10 | A `lock_state` column on the Partner-readable `invoices` is acceptable; reason/who/when live only in the Admin-only activity log | Pitfall 11 | If any lock metadata must be hidden, it needs an Admin-only table |
| A11 | New requirement IDs IN-11..IN-15 and the IN-03 rewording | Phase requirements | Cosmetic; planner may renumber |
| A12 | Explicit audit rows may carry item text and party data (Admin-only log) despite the T-10-30 precedent; values truncated by `ActivityPresenter` (80 chars) | Pitfall 9 | Privacy/secret hygiene; owner decision D-13 supports it but the precedent is a documented threat |
| A13 | The lock is taken only by the document e-mail job (`SendInvoiceEmail`), so Phase 13's payment-confirmation e-mail never locks | Pattern 3 | If confirmation e-mails reuse the same job/table without a kind, they would lock invoices |
| A14 | Taxable-supply date stays hidden/disabled in non-payer mode as in the draft editor (VAT payer issuing is blocked by `vat_payer_unsupported`), so "editable taxable supply date" has no v1 effect | UI | If the owner expects the field visible, the editor's rule changes |

## Open Questions

1. **Credit notes and proformas of an edited invoice (flagged by CONTEXT).**
   - What we know: credit lines reference source lines (FK) and copy unit price and CNB trio; a converted proforma moved its time and copied its lines; payments carried over.
   - What's unclear: whether a cancelled invoice / converted proforma should be editable at all.
   - Recommendation: block both (A3), freeze credited lines (A4), refuse currency change when a credit note exists; surface the reason in the UI.
2. **Does an issue-date edit re-take the CNB rate (A6)?** Recommendation: no, warn; revisit if the owner's accountant requires the rate of the issue date.
3. **E-mail in flight (A8).** Recommendation: refuse edit while `queued`/fresh `sending`, take the invoice row lock in `QueueInvoiceEmail`, the edit Action and the job.
4. **Backfill (A2).** Recommendation: as stated; the owner has the only instance, confirm before the migration is written.
5. **Audit scope (A12 / Pitfall 9).** Recommendation: keep model-driven logging for never-sent edits, add explicit rows only after the first send; confirm that item text and address data may appear in the Admin-only history.
6. **Customer/supplier "editable" (A9).** Confirm free-field editing vs reload-from-source.

### Applicable ASVS Categories
| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|
| V2 Authentication | no (unchanged) | existing Filament auth |
| V3 Session Management | no (unchanged) | existing |

| V6 Cryptography | no new | `pay_token` generated by `PayToken::generate()` at issue; never regenerated, never logged |

### Known Threat Patterns
| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Raw-SQL / package writer bypasses the lock | Tampering | DB triggers (new invoice guard, child guards, link guard); KP001 tests per writer class |
| Forged unlock (set flag from other code) | Elevation | flag literal confined to `UnlockInvoice` by an arch test; transaction-local, per-invoice value |
| IDOR via item ids / entry ids in the edit payload | Tampering | ids re-read through scoped queries under the row lock; foreign id = field error, no write |
| Race: edit vs send vs credit note vs payment | Tampering / Repudiation | invoice row `FOR UPDATE` first in every path; child guards take `FOR SHARE` on the parent; concurrency test |
| Stale PDF / link leaving the system after an edit | Information disclosure | PDF replaced and link reconciled in the same transaction; no auto-send (D-10) |
| Mass assignment of `lock_state`, totals, snapshots | Tampering | `forceFill` only in Actions; `#[Fillable(['note'])]` unchanged |
| Partner reading lock metadata or history | Information disclosure | only `lock_state` on `invoices`; `Activity` and `InvoiceEmail` are `DeniesPartners` |
| Bearer `pay_token` changed or exposed | Spoofing | always-on DB rule + never in audit payload |
