<objective>
Close audit gap G2: a payment on a proforma that has already been converted into an invoice is refused by the one shared rule `RecordPayment::refuses()`, with its own message telling the Admin to record the payment on the invoice made from the proforma. The manual path and the card path obey the same rule.

Purpose: IN-06 and PA-01. A payment on a converted proforma books no income (a proforma books none, and its payments were carried over once at the conversion), so it would leave money without its income and the receivables out of balance.
Output: the refusal in `RecordPayment`, one Czech message, and Feature tests of the dialog, the Action, the job core and the card assignment.
</objective>

Planner findings (recorded):
- Where the dialog is still offered: `RecordPaymentAction::available()` hides the dialog only while `ReceivablesReader` derives the status Converted, which needs nothing left to pay. After the carried copy on the invoice and then the proforma payment are deleted (`DeletePayment` allows that order, see `tests/Feature/Invoicing/DeletePaymentTest.php` lines 309-328), the proforma owes its total again, its status is Unpaid or Overdue, and the header dialog is offered; today it saves a payment that books no income. The dialog stays offered (D-07: no new flow), and the new message tells the Admin where the payment belongs (D-06).
- Card paths: `RecordCardPayment` classifies a payment on a paid document as `already_paid` before it reaches `recordLocked()`; `AssignCardPayment` offers the record's own document even when paid (`ViewCardPayment::documentOptions()`), so a duplicate on a converted proforma can be assigned to it and reaches `recordLocked()` with the Admin. Both stay unchanged; the shared rule refuses (D-07).
- Locales: `lang/cs/invoices.php` is the only file that holds `invoices.errors` (`lang/en` has no `invoices.php`; the Admin panel is Czech, English exists only for client-facing documents), so the Czech file is every supported locale of this message, exactly like `payment_not_allowed` (D-06).
- Context: `refuses()` reads the relation through the Partner-scoped model, the same as `Invoice::isCancelled()` does today. `handle()` runs under the Admin Gate and `recordLocked()` is called by the Admin (`AssignCardPayment`) or inside a job that runs in the system context (`ProcessStripeWebhook`), so the scope sees every row.

Rulings made in this plan (recorded):
- R-17.1-02-1 (rule): `private function refuses(Invoice $locked): ?ValidationException` replaces `private function refuses(Invoice $locked): bool`. It returns `ValidationException::withMessages(['payment' => __('invoices.errors.payment_not_allowed')])` for the unchanged condition (not issued, or a kind that carries no payment, or cancelled); otherwise, for `$locked->kind === InvoiceKind::Proforma` with `$locked->invoiceFromProforma()->exists()`, it returns `ValidationException::withMessages(['payment' => __('invoices.errors.payment_on_converted_proforma', ['number' => $number])])`, where `$number` is the `number` of that invoice read with `$locked->invoiceFromProforma()->value('number')` and narrowed with `is_string()` to a string (an empty string when the row has none, so PHPStan sees no cast of mixed); otherwise null. A docblock says it is judged on the locked row and names D-05 to D-07. In `handle()` and in `recordLocked()` the two existing `if ($this->refuses($locked)) { throw ... payment_not_allowed ... }` blocks become: keep the result of `$this->refuses($locked)` and throw it when it is a `ValidationException`, at the same place as today (in `handle()` before `PaymentInput::fromArray()`, in `recordLocked()` after the two LogicException guards and before anything is written). The `payment` key stays, so `RecordPaymentAction::underModal()` keeps mapping it under the amount and every caller that already handles `payment_not_allowed` handles this one the same way (D-07).
- R-17.1-02-2 (message): `lang/cs/invoices.php`, `errors` block, group "// Payments.", directly after `payment_not_allowed`: `'payment_on_converted_proforma' => 'Ze zálohy už vznikla faktura :number. Platbu zaznamenejte na této faktuře.'` (NFC UTF-8, as `LangEncodingTest` checks).
- R-17.1-02-3 (docblocks): the class docblock sentence "What it refuses is a payment on a draft, a credit note or a cancelled invoice (`payment_not_allowed`)." gains: and a payment on a proforma that already has its invoice (`payment_on_converted_proforma`, Phase 17.1 D-05 to D-07), which would book no income because the conversion carried the proforma payments over once; the Admin records it on the invoice. The `recordLocked()` docblock and its `@throws` line name the new key next to `payment_not_allowed`.
