# Phase 17.1: Close gap G1/G2 — release time on full partial credit and reject payments on converted proformas - Context

**Gathered:** 2026-10-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Close two integration gaps found by the v1 milestone audit (`.planning/v1-MILESTONE-AUDIT.md`):

- **G1 (core value):** a fully credited invoice keeps its time entries billed and locked when the credits were issued as partial credit notes. Time must return to unbilled once partial credit notes have used up every creditable quantity.
- **G2:** `RecordPayment::refuses()` accepts a manual payment on a converted proforma, which books no income. It must refuse such a payment.

Future behavior only. No new capabilities.

</domain>

<decisions>
## Implementation Decisions

### G1 — release trigger
- **D-01:** Time is released when the partial credit notes of an invoice exhaust everything creditable: in the same transaction in which the last partial credit note lowers the creditable quantity of every line to zero, all time entries of that invoice go back to unbilled and unlocked (the existing `releaseEntries()` / `EntryBilling::release()` path used by `storno()`). A partial credit note that leaves any creditable quantity does not release anything.
- **D-02:** The judgement runs on the locked invoice row, like the credit itself, so two concurrent partial credit notes cannot release early, twice, or not at all.
- **D-03:** The invoice is NOT treated as cancelled when partial credits exhaust it. `cancels_invoice` stays the single definition of cancelled (`Invoice::isCancelled()`, `invoices_one_storno_per_invoice` unchanged). Only the time is released.

### G1 — proforma scope
- **D-04:** The unpaid issued proforma that holds time is OUT of this phase (the phase title does not name it, and cancelling a proforma would be a new capability). Recorded as a deferred idea.

### G2 — rejection of payments on a converted proforma
- **D-05:** `RecordPayment::refuses()` rejects a payment on a proforma that has already been converted (an invoice with `proforma_id` pointing at it exists, see `Invoice::invoice()` relation hasOne on `proforma_id`).
- **D-06:** The rejection uses its own validation message (new key under `invoices.errors`, e.g. `payment_on_converted_proforma`), telling the Admin to record the payment on the invoice made from the proforma. Translations in all supported locales, matching the existing `payment_not_allowed` handling.
- **D-07:** The check lives in the shared `refuses()`, so the Stripe card path (`recordLocked()`, no user) is refused by the same rule and handled exactly like a payment on a cancelled invoice today. No redirect of card payments to the invoice, no new flow.

### Existing data
- **D-08:** Future behavior only: no data migration, no repair command. Already-affected rows are left alone (immutable data, migrations only after merge).

### Tests
- **D-09:** Feature tests prove G1 (last partial credit releases time; a non-exhausting one does not; entries become unbilled and unlocked) and G2 (manual payment on a converted proforma refused in the UI action and through `recordLocked()`; unconverted proforma still accepts payment).
- **D-10:** A Concurrency test issues two partial credit notes at once and proves the time is released exactly once and never before the creditable quantity is exhausted.
- **D-11:** No dedicated Partner regression test was requested; keep the existing Partner policy/scope tests green.

### Claude's Discretion
- Exact method names, where the "exhausted" check lives (reuse `CreditableQuantities::for()`), the exact message wording and the choice of locale files, following the surrounding code.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `IssueCreditNote::releaseEntries()`: locks the invoice's entries in id order and releases them through `EntryBilling`; reuse for the exhaustion case.
- `CreditableQuantities::for($invoice)`: remaining creditable quantity per line, positive means something is left; same figure `storno()` uses for `credit_nothing`.
- `InvoiceKind::carriesPayment()` and `Invoice::isCancelled()` already used by `refuses()`.

### Established Patterns
- Credit and payment actions lock the original invoice first (shared lock order), then judge on the locked row.
- Validation errors are `ValidationException::withMessages([...__('invoices.errors.*')])`.
- Link guard in the DB lets entries go only after the credit note is issued, so release must come after `issueCredit()`.

### Integration Points
- `IssueCreditNote::partial()` — after `issueCredit()` and before/with `paymentLinks->reconcile()`.
- `RecordPayment::refuses()` — shared by `handle()` and `recordLocked()`.

</code_context>
