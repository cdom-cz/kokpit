Decisions carried in (locked): D-15 (two levels; a type per category; a child inherits its parent's type; a transaction takes only a category of the same type; archive but not delete once used, DB restrict FK; unused can be deleted; manual order with eloquent-sortable), D-16 (small generic Czech-named seed; one system income category for invoice payments used by Phase 10, renameable but not deletable or archivable; no real business data).

Decisions made in this plan (recorded):
- The two-level and type rules are composite foreign keys in the style of `tasks_parent_fk`: `UNIQUE (id, type, depth)` and `FOREIGN KEY (parent_id, type, parent_depth) REFERENCES transaction_categories (id, type, depth)` with a stored generated `parent_depth` (research Pattern 6). `UNIQUE (id, type)` is the target of the transactions FK in 09-09. Foreign keys use NO ACTION so they answer 23503 (STATE decision 02-07).
- Composite FK columns `transaction_categories.type` and `.parent_depth` are not identifiers; they get `PgSchema::EXEMPT` entries with reasons, like `tasks.parent_depth`.
- The system category is guarded by `Immutability::guardTriggerSql('transaction_categories', 'is_system', 'false', ['name', 'position'])` (research A19): rows with `is_system` true are frozen except name, position and updated_at and cannot be deleted (KP001).
- Seeding is a data migration (research A13), so production gets the system category without a seeder; the starter set is generic Czech names. Seed names are data, not translations.
- Categories are not activity-logged (D-14 names transactions only).
- No soft deletes: archiving is an `archived_at` timestamp so the restrict FK keeps working.
