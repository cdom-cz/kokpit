Corrections from research adopted here:
- C1: there is no `projects.next_task_number` column and none is added. The counter is the `number_sequences` row `task:<project uuid>`, reached only through `DocumentNumbering::nextTaskNumber(string $projectId, string $projectKey): string`, which returns `KEY-N`; the integer is the suffix after the last `-`.

Decisions carried in (already chosen by the user, recorded, not re-asked):
- D-01: status and priority reuse `ProjectStatus` and `ProjectPriority` (no new enum).
- D-04, D-05: people rules are enforced in the Action, not only in a form.

Assumptions adopted (unattended run, recorded, easy to reverse):
- "The Admin" is the active user with role `RoleName::Admin` (`kokpit:install` allows one); when several exist in tests, the oldest by `created_at`, then `id`, is used. No active Admin is a `DomainException` (`kokpit.tasks.errors.no_admin`).
- One neutral field error (`kokpit.tasks.errors.project_unavailable` on `project_id`) for a project that does not exist, is not visible to the actor, is archived or belongs to an archived client, so the message is no existence oracle.
- Positions are one global order per status column (D-02 "position is stored per status column"); the per-project board (plan 05-11) is a filtered view of it. Done rows carry position 0 and are ordered by `completed_at` (research A11).
- The `tasks` migration already carries the escalation columns (`escalated_at`, `escalated_by_id`) used by plan 05-13 and the generated `parent_depth` column used by plan 05-05, so no later plan alters the Partner-readable table.
