Decisions carried in (locked): D-07 (threshold 12 h in config, warning state, one-time bell notification from a scheduled job, no e-mail by default, never auto-stop). Deferred (not built): e-mail for a forgotten timer. Phase 3 rules: every queued class extends `KokpitJob` with `#[Idempotent]` and runs in the system context; every scheduled event uses `onOneServer()`. Phase 5 rule 05-19: bell values escaped once.

Decisions made in this plan (recorded):
- Research A9: the notification is a plain (not queued) database-channel notification sent with `notifyNow` inside the claim transaction, so claim and notice commit or roll back together; a queued notification could be lost after the claim.
- U-14: no profile switch for this notification; the bell always delivers it.
- An owner who is deactivated or not the Admin is skipped without claiming, so a reactivated Admin still gets the notice while the timer runs.
- The claim is an Eloquent builder update (`TimeEntry::query()->whereKey(...)->whereNull(...)->update(...)`), not `DB::table()` (QueryEscapeHatchTest), and raises no model event, so no activity row is written for the internal marker.

Fictional data only (an XSS canary client name assembled at runtime). Run `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
