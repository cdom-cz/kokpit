Rulings made in this plan (recorded, Claude's discretion in CONTEXT):
- R-04-1 Stored state is `state` (`draft`, `issued`); cancelled is derived from the storno credit note (R-04-5), and unpaid, partially paid, paid, overdue, converted and "paid proforma without invoice" are derived too (plans 10-05, 10-16 and 10-19). Payment rows live in an Admin-only table (plan 10-06).
- R-04-2 The Partner-readable `invoices` table holds only what the document prints and its links to other issued documents. Its 26 columns: `id`, `client_id`, `kind` (`invoice`, `proforma`, `credit_note`), `state`, `number` (varchar 32, null on a draft), `variable_symbol` (varchar 10), `currency` (char 3), `language` (`cs`, `en`), `vat_mode` (`non_payer`, `payer`), `issue_date`, `taxable_supply_date`, `due_date` (all `date`, nullable), `subtotal_minor`, `vat_minor`, `total_minor` (bigint, default 0), `note` (varchar 500, printed), `supplier_snapshot`, `customer_snapshot`, `bank_snapshot`, `appearance_snapshot` (jsonb, nullable), `proforma_id`, `credited_invoice_id` (uuid, nullable), `cancels_invoice` (boolean not null default false, R-04-5), `issued_at` (timestamptz, nullable), timestamps. Neither a cancellation timestamp nor a PDF link is a column here (R-04-6).
- R-04-3 `invoice_items` columns: `id`, `invoice_id` (FK, NO ACTION: a draft is deleted by plan 10-11 after its children, so the guard always finds the parent), `position` (int >= 1, UNIQUE (invoice_id, position)), `description` (varchar 500, not blank), `quantity` numeric(14,4) not 0, `unit` (varchar 16, not blank), `unit_price_minor` bigint >= 0, `line_total_minor` bigint, `price_converted` boolean not null default false (true only on a line whose amount was computed once from an exact currency conversion: previewed in a draft at today's rates, plan 10-13 R-13-5, and final at issue, plan 10-17 R-17-1, per plan 10-01 R-01-1; it holds no rate, no CNB figure and no source value), `vat_rate` numeric(5,2) null, `vat_minor` bigint default 0, `credited_item_id` (uuid null, FK `invoice_items`), timestamps. Credit lines carry a negative quantity and the original (positive) unit price (research Pattern 5; STATE blocker "sign convention" resolved). The line CHECK `invoice_items_line_total_check` is `CASE WHEN price_converted THEN abs(line_total_minor - quantity * unit_price_minor) <= abs(quantity) / 2 + 0.5 ELSE line_total_minor = round(quantity * unit_price_minor) END`: an ordinary line is pinned exactly, a converted line is bounded by the rounding of its display unit price (D-09: its amount is rounded once, from the exact conversion, not from the displayed price).
- R-04-4 The child guard looks the parent up by id; a missing parent counts as open (only a draft can be deleted, and the parent guard decides that). `UPDATE` of a child of a frozen parent is allowed only when nothing but the listed always-mutable columns changes; `updated_at` is not implied, so a frozen item or item source refuses even a timestamp write, and a table that keeps a writable column lists `updated_at` itself (only `invoice_admin`, plan 10-06). Moving a child to another parent checks both parents.
- R-04-5 (replaces the set-once timestamp of the earlier revision; CONTEXT leaves to the planner which statuses are stored and which derived) The storno marker of D-14 is the credit note itself. `cancels_invoice` is true only on the full-storno credit note (CHECK `invoices_cancels_invoice_check`: only `kind = 'credit_note'`), the partial unique index `invoices_one_storno_per_invoice` on `credited_invoice_id` WHERE `cancels_invoice` allows one per invoice, and the credit note is written while it is a draft and frozen by the same guard at its own issue. An invoice is cancelled exactly when an issued credit note with `cancels_invoice` names it; nothing is written on the cancelled invoice, so the storno can be neither reverted nor hidden by raw SQL. A Partner sees the cancelled state through that credit note, an own-client issued document it may read anyway (plan 10-05).
- R-04-6 No post-issue write on `invoices` (D-13, roadmap criterion 2: afterwards only the payment state and the internal note change, and both live off this row, in the Admin-only `invoice_payments` and `invoice_admin` of plan 10-06). The frozen guard is created with an empty mutable-column list and without the implied `updated_at`: `guardTriggerSql('invoices', 'state', 'draft', [], withUpdatedAt: false)`, so once `state` is `issued` the row refuses every UPDATE, even one that changes only `updated_at`, and every DELETE. What the earlier revision kept writable moved off the row: the storno marker is the issued credit note (R-04-5, D-14), and the link to the stored PDF is `invoice_admin.pdf_document_id`, an Admin-only column with its own link guard (plan 10-06 R-06-6, D-21, D-23). Setting the PDF link inside the issuing statement before the freeze arms was considered and rejected: the confirmed deletion (D-21, DO-03) and the regeneration (D-23) of an issued PDF must change the link after issue, which a frozen column cannot allow. Consequences for later plans: the state flip is the last write of the issue pipeline on the `invoices` row (plans 10-12, 10-14, 10-17, 10-20); no model declares `$touches` toward `Invoice` (plan 10-08). Any future post-issue column on `invoices` needs an owner decision amending D-13 and criterion 2. This ruling supersedes the `invoices` row of the guard table in 10-RESEARCH Pattern 4 and Pitfall 2 and the former guard call in 10-PATTERNS.
