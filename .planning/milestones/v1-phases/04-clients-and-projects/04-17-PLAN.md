Design decisions carried in from research Pattern 3 (recorded here):
- State is derived from `accepted_at`, `revoked_at` and `expires_at`, never stored.
- The route is `GET /admin/invitation` named `filament.admin.invitation.accept`, registered with the panel `routes()` hook, guarded by the `signed` middleware, with no path parameters (the route walk forbids path parameters other than `{record}`, research Pitfall 7). The invitation id and the token travel as query parameters.
- The guest page reads the invitation only through `ClientInvitation::findAcceptable()`, which wraps its query in `PartnerContext::runAsSystem()`; a guest has no user, so every scope is fail-closed otherwise (research Pitfall 3).
- The notification takes scalars only: a queued notification does not run as system, and a serialised model would be re-fetched under a fail-closed scope.
- Accepted risk A11: a failed mail job keeps the signed URL in `failed_jobs` until the invitation expires or is revoked (single use, 7 days); the existing failed-job alert carries no payload.

Fictional data only: `exampleEmail()` invitees, `Example` names. `scripts/check-sensitive.sh` before every commit; never bypass the hook.
</context>
