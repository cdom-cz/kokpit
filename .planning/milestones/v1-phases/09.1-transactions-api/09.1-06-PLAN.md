Owner decisions at planning (2026-10-16, locked):
- A1 sticky rate (implemented in `UpdateTransaction` by plan 09.1-04; this plan maps the request to it).
- A2: Action error keys are renamed to API field names (`amount` -> `amount_minor`, `czk_amount` -> `czk_amount_minor`).
- Open Question 1: the `DeleteTransaction` refusal maps to 409 `transaction_in_use`; the docs helper is relaxed so a controller declares which of PATCH and DELETE can conflict, until Phase 10 adds the payment-income lock.
- Clients have no key, so `client_id` is a UUID only.

Decisions made in this plan (recorded):
- The delete refusal is caught as `QueryException` whose `SqlState::of()` is `SqlState::FOREIGN_KEY` (23503) or `SqlState::FROZEN_ROW` (KP001): that is "the database refuses the delete" of the DeleteTransaction docblock. Any other fault (lost connection, deadlock) stays a 500, so it never masquerades as "in use".
- `TransactionController::CONFLICT_METHODS = ['DELETE']`; `ApiDocs` requires 409 on a PATCH or DELETE route unless its controller declares `CONFLICT_METHODS` without that method. Controllers without the constant (time entries) are checked exactly as before. Phase 10 plan 10-19 adds `'PATCH'` when its payment-income lock becomes a conflict answer.
- RESEARCH A5 accepted as the default: a CZK transaction with a rate, a unit amount or a CZK figure is a 422 in the API layer (key = the API field, message `api.errors.czk_needs_no_rate`); the domain keeps ignoring them, so the Admin UI is unchanged. This is a wire-contract rule about ignored input, not a second business rule.
- PATCH nulls: `exchange_rate: null` drops an own rate (custom row -> `exchange_rate => null, czk_manual => false`), `czk_amount_minor: null` drops a bank figure (manual row -> `czk_manual => false`), both null always map to `exchange_rate => null, czk_manual => false` (custom or manual -> CNB; a cnb row stays untouched). A null of a field the row does not use changes nothing. This extends owner decision A1 ("both null returns to CNB") with the "null clears" convention of the API.
- `exchange_rate` is accepted as a string, or as a JSON number whose PHP string form matches the rate pattern (an exponent fails with the Action's `rate_invalid`); the docs say "send the rate as a string" (RESEARCH A7).
- Request rules check presence on create and shape only (integer, string, UUID, UUID or project key, `^[A-Z]{3}$`); the Actions decide every value. Unknown ISO codes leave `amount` out of the Action data so the Action's `currency` error answers.
