# Phase 9.1 Plan 02: Finance abilities and the transaction detail endpoint Summary

**Two new token abilities (`finance:read`, `finance:write`) and the first finance endpoint, `GET /api/v1/transactions/{transaction}`, returning the pinned 18-key D-07 response with `id` first, refused to guests, Partner tokens and every token without the ability.**

- **Duration:** ~35 min

## Accomplishments

- `ApiAbility` carries `FinanceRead` and `FinanceWrite` with Czech labels and descriptions under `kokpit.api_tokens`, so the token screen and `EnumLabelsTest` know them.
- The finance read route group (`auth:sanctum`, exactly `finance:read`, `throttle:api-read`) holds the detail route with `whereUuid` and the Czech 404 from a controller-side lookup, as the time entry detail does.
- `TransactionResource` is an explicit allow-list (id, type, transaction_date, category_id, amount_minor, currency, czk_minor, czk_source, exchange_rate, exchange_unit_amount, exchange_rate_date, description, counterparty, document_number, client_id, project_id, created_at, updated_at); no receipt, document or file key can appear.
- The endpoint is fully documented through Scribe attributes and a fixed fictional `TransactionExamples::TRANSACTION`; the generated spec marks exactly the nullable keys.
- `TransactionContract::KEYS` pins keys, order and JSON types; `TransactionAbilityTest` derives the finance and time route sets from the `abilities:` middleware, so the routes of plans 09.1-05 to 09.1-07 are covered without edits.
- The route walk of `ApiAccessTest` knows both finance abilities and a canary control reads the seeded transaction canary through the new route, so the Partner and guest 401 proofs are not vacuous.
