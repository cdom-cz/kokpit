# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Scope: Phase 11 puts the card-payment surfaces on top of the Phase 10 invoicing screens. Public surface: A the stable pay page behind the printed and e-mailed link. Document outputs: B the "Zaplatit kartou" button in the invoice PDF; C the pay-link block in the invoice e-mail and the e-mail dialog. Admin surfaces: D the per-document switch in the draft editor and the issue confirmation; E the "Platba kartou" section of the issued document detail (link state, regenerate, deactivate); F the header action "Zaplatit kartou" (Admin and Partner); G the card-payment lines in the "Platby" tab; H the payments overview "Platby kartou" (list, tabs, record view, the three resolutions); I the Admin notices (bell and e-mail); J the dashboard card "Nevyřešené platby"; K the System page indicators (unprocessed webhooks, Stripe configured); L the settings and client-form hints. Partner surface: M the "Zaplatit kartou" button of the Partner invoice detail.
>
> Nothing is built yet. Everything below is a target for plans, not a record of built work. Class, file, table, route, token and status-storage names are the planner's call (CONTEXT "Claude's Discretion"); names such as "PaymentResource" and "/pay/{token}" below are working labels. Screen and document copy is Czech (and English where the document language is English); the contract text around it is English because it lives under `.planning/`.

Upstream decisions applied (not re-asked): `11-CONTEXT.md` D-01 to D-18 (stable public URL that redirects to the active Stripe link or shows a login-free information page with the document number only; e-mail never waits for the link job; header action in Admin and Partner detail hidden when paid, cancelled or without an active link; links for invoices and proformas only; creation = global switch AND client flag AND per-document flag, frozen at issue; link for the remaining amount; a partial manual payment deactivates the link; matching, mismatch, duplicate, unmatched and refund handling; the three resolutions; deletion of a Stripe-matched payment through the one `DeletePayment` path; signed webhook; secrets only in the environment; 90-day pruning; fake Stripe client in tests), `10-UI-SPEC.md` (surfaces E, F, G, H, J, K, L, N and the Partner header slot, treated as locked and extended here), `02-UI-SPEC.md`, `08-UI-SPEC.md` (dashboard card pattern, System page), `REQUIREMENTS.md` PA-01 to PA-08, FI-03, IN-05, and the existing code under `app/Filament` (`InvoiceResource`, `ViewInvoice`, `ViewPartnerInvoice`, `UnpaidInvoices`, `SystemPage`, `AcceptInvitation` as the guest-page precedent, `ClientResource`, `SettingsPage`), `resources/views/pdf/invoice.blade.php`, `resources/views/mail/invoice-text.blade.php`, `HealthResult` (carries an optional link), and Stripe's Payment Link API (`restrictions`, `after_completion.hosted_confirmation.custom_message`, `inactive_message` up to 500 characters, `metadata`).

Contract notes (screen):

- Declared sizes: 14, 16, 24, 30. Declared weights: 400, 600.
- Money: `Money::format('cs')` on screen, `tabular-nums`, right aligned in columns. A card payment is always shown in the currency Stripe reports; amounts of different currencies are never summed in one cell or one tile.

## Access and Visibility Contract

Applies to every new class; the registry and canary tests enforce it (FND-18). Phase 12 proves the whole matrix; this phase must not make it harder.

- Every new Resource, Page, Widget and relation manager declares `#[AccessRule(...)]` with the matching `Enforces*AccessRule` trait. The payments overview, its record view, the dashboard card, the link section and every link action are `Audience::AdminOnly`. The pay page is `Audience::Guest` like `AcceptInvitation`: reached only through its own route, never granted through the panel access checks.
- The pay page and its route are public by design and therefore the narrowest surface of the phase: it shows the document number only, never an amount, a client, a supplier, a line, a Stripe id or a payment state beyond the four documented states. A wrong, tampered, expired or unknown token and a document without a payable state answer with the same neutral "Odkaz není platný" page and an identical response shape, so the page is neither a document oracle nor a client oracle. The response carries `noindex`, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`; the route is rate limited per visitor.
- The redirect to the Stripe link is a `302` that is never cached and never exposes the Stripe URL in HTML or in the Partner/Admin page markup. The Partner button and the Admin header action both point at the stable Kokpit URL, never at the Stripe URL (D-01).
- The Partner button reads only the facts it needs: kind (invoice or proforma), derived state (not paid, not cancelled) and whether an active link exists. It reads no link amount, no link id, no failure state. A failed or pending link looks to a Partner exactly like a document without a link: no button, no message.
- Everything else is Admin only and re-checks the Admin on every Livewire update: the link section, the regenerate and deactivate actions, the payments overview, the resolution actions, the dashboard card, the System page indicators, the notices. A hidden action is not rendered, not disabled (the one inherited exception is the disabled "Smazat platbu" with a tooltip on a carried proforma payment).
- Hand-written SQL in overview and dashboard readers is guarded by `PartnerContext` (Admin or system only).
- The canary harness gets one card payment record per type (matched, duplicate, unmatched, refund) per client, with a Stripe-reference canary and a resolution-note canary. The route walk and a rendered-HTML check prove that the Partner of client A sees none of client B's canary strings and none of the strings under "Never on a Partner surface".

## Screens and Interaction Contract

### Visual anchors

| Screen | Primary anchor | Why |
|--------|----------------|-----|
| Pay page (A) | The state icon and heading | The visitor needs one answer: can I pay, or why not |
| PDF button (B) | The button inside the payment box, next to the bank-transfer facts | The recipient chooses between two ways to pay |
| Link section (E) | The state badge next to "Odkaz pro klienta" | "Can the client pay this document by card right now" |
| Overview (H) | The "Nevyřešené" tab with its `danger` count, then the Typ badge | The core promise: no payment is lost silently |
| Record view (H) | The banner explaining what happened, then the one accent action | The Admin decides what to do with money that did not match |
| Dashboard card (J) | The count in `danger` | An unresolved payment must be seen without opening a menu |
| Partner detail (M) | "Zaplatit kartou" in the header | The Partner's question is "how do I pay this" |

### Surface A: Stable pay page `/pay/{token}` — new (PA-02; D-01, D-02, D-03)

A public guest page. A valid token with an active Stripe link answers `302` to that link and renders nothing. In every other case it renders one centered card (stock `SimplePage` width) with, top to bottom: the state icon (48px, in the state colour, `aria-hidden`), the heading (24px, 600), the body (14px), and for the "preparing" state one accent button. The document number is the only document datum on the page; the panel brand ("Kokpit") is the only other identity. Language: the document's language from the snapshot (`cs` or `en`); the invalid state, which has no document, shows Czech and English stacked (Czech first) because the language is unknown.

| State | When | Icon / colour | Heading (cs / en) | Body (cs / en) | Action |
|-------|------|---------------|-------------------|----------------|--------|
| Preparing | Valid token, document unpaid, no active link yet (job running or failed, deactivated and not yet regenerated, partially paid) | `OutlinedClock`, `info` | "Odkaz na platbu se připravuje" / "The payment link is being prepared" | "Doklad č. :number. Zkuste to prosím za chvíli. Pokud se odkaz nezobrazí ani později, kontaktujte dodavatele dokladu." / "Document no. :number. Please try again shortly. If the link is still not available later, contact the supplier." | "Zkusit znovu" / "Try again" (accent; a plain reload of the same URL, so a link created in the meantime redirects) |
| Paid | Valid token, document fully paid | `OutlinedCheckCircle`, `success` | "Doklad je zaplacený" / "This document is paid" | "Doklad č. :number je zaplacený. Děkujeme." / "Document no. :number is paid. Thank you." | none |
| Cancelled | Valid token, document cancelled (storno) | `OutlinedXCircle`, `gray` | "Doklad byl stornován" / "This document was cancelled" | "Doklad č. :number byl stornován, platba kartou už není možná. S dotazy se obraťte na dodavatele." / "Document no. :number was cancelled, so card payment is no longer possible. Contact the supplier with any questions." | none |
| Invalid | Unknown, tampered, malformed or expired token; document of a kind that never has a link; online payment off for the document | `OutlinedExclamationCircle`, `gray` | "Odkaz není platný" / "This link is not valid" | "Tento odkaz na platbu nelze použít. Požádejte dodavatele o nový." / "This payment link cannot be used. Ask the supplier for a new one." | none |

Rules:

- No amount, no client, no supplier, no line item and no payment date appears in any state. A page title (`<title>`) is the heading, never the number.
- "Zkusit znovu" is a link to the same URL, not a Livewire action: it works without JavaScript and cannot be double-submitted. Keyboard order: the button is the only focusable element; focus ring as everywhere.
- The card reflows to one column at 375px with the same order; no horizontal scroll.
- Stripe-side wording, sent when Kokpit creates the link and not rendered by Kokpit: `inactive_message` and the hosted-confirmation `custom_message` (strings in the Copywriting Contract, in the document language), so a payer who reaches a deactivated link or finishes paying also reads wording that matches the document.

### Surface B: "Zaplatit kartou" button in the invoice PDF — extends Phase 10 Surface H (PA-02; D-01, D-05, D-06)

Printed only on an invoice or a proforma whose three switches and Stripe configuration were on at issue (assumption U-4); never on a credit note. The decision is frozen into the issue snapshot, so a regenerated PDF is equivalent and keeps the button even after the document is paid or the Stripe link is replaced (the stable URL then leads to the "paid" or "preparing" page). The URL is the stable pay URL (D-01), never the Stripe URL, and exists from the moment of issue, so the PDF never waits for the link job.

- **Placement:** inside the Phase 10 payment box, in the right column, below the fact list: a 12pt gap, then the lead line, then the button, then the printed URL. The QR (bank transfer) keeps its column; a document without a QR (non-CZK) has the same right column. No second QR code is added (two QR codes on one box invite the wrong scan; the printed URL covers paper readers). The box is still one table row, never split across pages.
- **Lead line** (8pt regular, ink): "Nebo zaplaťte online kartou:" / "Or pay online by card:".
- **Button:** a one-cell table with the document accent as background, 4pt corner radius, padding 8pt vertical and 16pt horizontal, label "Zaplatit kartou" / "Pay by card" in 9pt bold with the on-accent text colour, wrapped in an anchor to the stable URL (a clickable link annotation in the PDF). Inline-block width, left aligned with the facts.
- **Printed URL** (8pt regular, muted colour, 4pt below the button): the full stable URL as text, so a paper reader can type it. The URL must fit one line in the 8pt column: the full URL is at most 80 characters (short public path, compact token; token format is the planner's call within this limit, D-01 reversibility).
- **Variants:** proforma identical; cs and en by document language; with or without logo, signature and footer unchanged. Hyphenation off; the URL line never wraps mid-token.
- **Safety:** the URL is escaped by Blade `{{ }}`; no remote asset; no JavaScript.

### Surface C: Pay-link block in the e-mail and the e-mail dialog — extends Phase 10 Surface G (PA-02; D-03)

- **Mail body:** the mailer appends a fixed block after the Admin-editable text, so editing or clearing the text can never remove the link (D-03: the e-mail always carries the stable URL): a blank line, then the lead line and the stable URL on its own line (plain text, auto-linked by mail clients). The mail is plain text (as built); no HTML button is introduced. Strings in the Copywriting Contract.
- **When the block is present:** the document is an invoice or proforma, the card switch was on at issue (frozen), and at send time the document is not paid and not cancelled. A resend of a paid or cancelled document carries no block. The mail never waits for the link job and never contains the Stripe URL.
- **Dialog (Phase 10 G):** the attachments line gets a second gray line, shown only when the block will be added: "Do e-mailu se automaticky přidá odkaz Zaplatit kartou." The textarea does not contain the block, and the Admin cannot edit it.

### Surface D: Per-document switch and issue confirmation — extends Phase 10 Surfaces C1 and D (PA-03; D-06)

- **Draft editor, section "Doklad":** a toggle "Platba kartou" below "Způsob úhrady", on an invoice or proforma draft. Default: the client's online-payment value at the time the draft is created; the Admin can override it until issue. Helper: "Na dokladu a v e-mailu se zobrazí tlačítko Zaplatit kartou. Po vystavení už nejde změnit." The toggle is disabled and off, with its own helper, when the global switch is off ("Online platby jsou vypnuté v Nastavení.") or when Stripe is not configured ("Stripe není nastavený. Doplňte klíče v prostředí aplikace."). It is absent on a credit note.
- **Issue confirmation (Phase 10 D):** the summary list gains a row "Platba kartou" with the value "Ano, odkaz se vytvoří po vystavení" or "Ne". Failure of the link job never blocks issuing and is not a pre-issue blocker (D-09).
- **Issued detail, section "Doklad" (Phase 10 E3):** a read-only row "Platba kartou": "Ano" or "Ne" (the frozen value).

### Surface E: "Platba kartou" section of the issued document detail — new (PA-01, PA-03, PA-04; D-06 to D-09)

### Cross-cutting interaction rules (this phase)

- Keyboard: every control works by keyboard alone with the accent focus ring; modals close on Esc, submit on Enter and return focus to the trigger; the pay page has a single focusable control at most.

- The link job, the webhook job and the notices never block or roll back issuing, payment recording or any user action (D-09); a failure shows a state and a next step, never an exception text.
- Resolution, assignment and return are single transactions: any failure rolls the step back and shows a danger toast with a next step.
- Money never appears next to a value of a different currency in one cell; the overview shows each record in its own currency and the dashboard card shows counts only.
- Enum labels (link state, payment type, resolution state, reason, payment method "Kartou") come from `lang/cs/enums.php`; new screen strings go to `lang/cs/card_payments.php`, public page strings to `lang/{cs,en}/pay_page.php`, e-mail and PDF additions to the existing `lang/{cs,en}/invoice_mail.php` and `invoice_pdf.php`, following the Phase 10 precedent.
