<objective>
The Stripe webhook endpoint: it verifies the signature, stores a handled event exactly once under its unique event id, answers immediately and hands the event to a queued job; a bad signature is rejected with 400. It builds on `spatie/laravel-webhook-client` and `WebhookCall` (D-15).

Purpose: PA-05 in full, PA-07 (repeated events ignored, idempotence enforced by a database constraint); D-12, D-15, D-16, D-17 (the processed marker the pruning of plan 11-14 reads); research Pattern 4 and Pitfalls 1, 2, 3, 4, 10, 11, 14; Open Question 4.
Output: the migration, the config entry, the model additions, the validator, the processor, the controller, the public routes file, the exception mapping, the job, the job-contract amendment, the test helpers and the feature test.
</objective>

Rulings made in this plan (recorded):
- R11-04-1 (research Pattern 4, Pitfall 2): `config/webhook-client.php` holds one entry `stripe` (the `default` entry goes): `signing_secret` env `STRIPE_WEBHOOK_SECRET`, `signature_header_name` `Stripe-Signature`, `signature_validator` `StripeSignatureValidator`, `webhook_profile` the package's `ProcessEverythingWebhookProfile` (the processor filters the types), `webhook_response` `DefaultRespondsTo`, `webhook_model` `WebhookCall`, `store_headers` empty, `store_attachments` false, `process_webhook_job` `ProcessStripeWebhook`; `delete_after_days` 90 (D-17).
- R11-04-2 (D-15, Pitfall 1): `StripeSignatureValidator::isValid()` returns false when `StripeConfig::hasWebhookSecret()` is false (fail closed) and otherwise calls `\Stripe\WebhookSignature::verifyHeader($request->getContent(), (string) $request->header('Stripe-Signature'), $secret, 300)` and maps `SignatureVerificationException` to false. `bootstrap/app.php` renders `Spatie\WebhookClient\Exceptions\InvalidWebhookSignature` as JSON 400 `{"message":"invalid signature"}`.
- R11-04-3 (Pitfall 3, Open Question 4): `StripeWebhookProcessor::process()` = signature check (package), then decode the raw body as a JSON object (not an object, no string `id` starting `evt_` of at most 255 characters, no string `type`, no `data.object` array: 400 `{"message":"invalid payload"}`), then a type outside `StripeWebhookProcessor::HANDLED_TYPES` (the three types) is answered 200 without storing, then `WebhookCall::storeStripeEvent()`, then dispatch when the row is new or not processed, then the package response. The stored payload is the decoded body without `data.object.customer_details`, `customer_email`, `shipping_details`, `shipping`, `collected_information` (A7, flagged for the owner).
- R11-04-4 (Pitfall 3, D-12): `WebhookCall::storeStripeEvent(WebhookConfig $config, string $eventId, string $eventName, array $payload): array{0: WebhookCall, 1: bool}` inserts with `insertOrIgnore` (PostgreSQL `ON CONFLICT DO NOTHING`, which the partial unique index `webhook_calls_name_event_id_unique ON (name, event_id) WHERE event_id IS NOT NULL` serves) and reads the row back by name and event id; the boolean says whether it was inserted now. Runs as system (the model is DeniesPartners).
- R11-04-5 (Pitfall 10): the public routes live in `routes/public.php`, loaded by `withRouting(then: ...)` outside the `web` group, so no session, cookie or CSRF middleware runs; `POST /webhooks/stripe` named `webhooks.stripe`. Plan 11-08 adds the pay route and both throttles to this file.
- R11-04-6 (Pitfall 2, research Pattern 4): `ProcessStripeWebhook extends Spatie\WebhookClient\Jobs\ProcessWebhookJob` and declares `#[Tries(3)]`, `#[Backoff(10, 60, 300)]`, `#[Timeout(60)]`, `#[Idempotent(how: ...)]` and `middleware()` returning `[new RunsAsSystem]`. The restored model comes back without scopes (`Model::newQueryForRestoration` uses `newQueryWithoutScopes`), and `handle()` re-reads the row under `lockForUpdate` as system; lock order for every later handler: the event row, then the document, then the payment, then the income. `handle()` routes by `event_name` through `ProcessStripeWebhook::handlers()`; in this plan no type has a handler yet, so the row is only marked processed (plans 11-13 and 11-16 add the checkout and refund handlers). On success `processed_at` is set and `failed_at`, `failure_class` cleared in the same transaction. `failed()` enters the system context by hand and sets `failed_at` with `failure_class` `validation` for a `ValidationException` (for example a missing CNB list for the income) and `unexpected` otherwise, never the message.
- R11-04-7 (Pitfall 2): `tests/Arch/JobContractTest.php` keeps "every dispatchable class under app/ extends KokpitJob" and admits exactly the subclasses of `ProcessWebhookJob` listed in `EXPECTED_WEBHOOK_JOBS` (`ProcessStripeWebhook`) whose `JobDeclaration::webhookJobProblems()` is empty: `#[Idempotent]` with text, `#[Tries]`, `#[Backoff]`, `#[Timeout]` on the class itself, and `middleware()` containing `RunsAsSystem`.
