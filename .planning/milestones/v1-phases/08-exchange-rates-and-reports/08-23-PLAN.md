<objective>
Close the consumer half of CR-01. The time report (page and aggregate) and the CSV and XLSX exports must stay usable when one client's entries are priced in two currencies. This happens when a task rate was stored in the old currency before the client currency changed (the root cause is closed in plan 08-25). Every report row keeps its client-currency amounts per currency, and nothing in the report path calls `Money::plus()` across currencies.

Purpose: 08-VERIFICATION.md gap 1 (SC3 amounts in client currency and CZK, SC4 exports). RE-01, RE-02, RE-03; D-01 (CZK at the entry's day), D-06 (one report page with the tree), D-07 (fixed price carries no amount), D-09 (exports follow the report).
Output: per-currency `ReportBucket` and tree nodes, the view listing one amount line per currency, regression tests for the page, the aggregate and both export formats, the UI-SPEC bullet and the CONTRIBUTING sentence that described the old invariant.
</objective>

Gap being closed (08-VERIFICATION.md `gaps[0]`): `ReportBucket::add()` sums the per-entry amounts of a client with `Money::plus()`, which throws on mixed currencies. The report SQL takes the currency from the same billing level as the rate (`TimeReportReader::RATE_CURRENCY_SQL`, task, then parent task, then project, then client). A task rate stored in EUR therefore prices that task's entries in EUR, while the rest of a CZK client prices in CZK, all inside one client bucket. The missing list of the gap asks for currency-safe buckets ("per-currency amounts or a visible mixed-currency marker, never an exception") and for a test of a CZK client with one EUR task rate on the report and the XLSX export. The dashboard widget half is plan 08-24 and the lock half is plan 08-25, both in the same wave with no shared file.

Facts read while planning:
- `TimeReport::build()` already keys the summary amounts by currency (lines 97-108). The footer merges `$client->amount` per currency (lines 153-163). The throw comes from `ReportBucket::add()` (line 84) on the client and project buckets, and on the task bucket only if one task had entries in two currencies.
- `BuildReportExport::writeXlsx()` already accumulates the summary amounts under `$amounts[$priced['amount']->currency]` and sums CZK only in CZK (lines 265-273), and the CSV path sums nothing. So the export is expected to pass the new regression test without a code change. 08-REVIEW.md said the XLSX path fails; this plan pins the real behaviour with a test, and touches the job only if that test fails.
- `time-report.blade.php` reads `$node['amount']` in three places: the missing-rate tooltip currency at lines 271-273, the Částka cell at lines 328-332 and the CZK dash condition at line 338. No other app or resources file reads a node's single amount.
- The only test that reads a node's single amount is TimeReportTest lines 1001-1002 (`$both->tree[n]['amount']?->currency`).
- A legacy row is written as in TimeReportTest: inside `timeReportSystem()`, through the task's `billing()` relation, with `billing_type` `TaskBillingType::Inherit` and `hourly_rate` `Money::fromMajor('120', 'EUR')`. `task_id` is set by the relation (not fillable). The DB CHECKs on `task_billing` only pair minor and currency and check the ISO pattern, so a EUR row under a CZK client is storable. Such a row is exactly the data the old lock let through.
