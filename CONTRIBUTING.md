# Contributing to Kokpit

Kokpit is a public AGPL-3.0 project (SPDX `AGPL-3.0-only`). This guide covers repository hygiene, the development setup and the conventions every change follows. Reporting a vulnerability is described in `SECURITY.md`; installing the application is described in `README.md`.

## Repository hygiene

The rule is: **Fictional data only.** Never put client names, prices, rates, invoice or production data, real e-mail addresses, company IDs, bank accounts, IP addresses, hostnames, tokens or personal absolute paths into code, tests, fixtures, docs, planning docs under `.planning/`, or commit messages.

Use `example.com` addresses, the placeholder company ID `12345678`, paths like `/Users/example/`, and test fakes assembled at runtime from fragments, so that no single line of a test file looks like a real value.

Review procedure before every commit:

1. `git status`
2. `git diff --staged`
3. `scripts/check-sensitive.sh`

Commit author name and e-mail are Git metadata and are not scanned. Each contributor decides what identity to commit with.

## Setup

Required tools: lefthook and gitleaks. Optional: shellcheck (lints the scripts).

Tested versions: lefthook 2.1.17 (minimum 2.1.0) and gitleaks 8.30.1.

Install with either of:

    brew install lefthook gitleaks
    mise use -g lefthook@2.1.17 gitleaks@8.30.1

Do not use the npm package for lefthook; use one of the commands above.

Run `scripts/install-hooks.sh` after every fresh clone. It checks both tools, refuses a `core.hooksPath` override, runs `lefthook install` and verifies the hook is in place. It is idempotent.

The pre-commit hook runs two jobs in order: `sensitive-content` (`scripts/check-sensitive.sh` over the staged changes), then `gitleaks` over the staged changes. If lefthook is not installed, the generated hook aborts the commit instead of skipping it.

Run the self-tests with `scripts/tests/run.sh` (`--quick` skips the tests that need lefthook or gitleaks). `scripts/tests/run-in-ubuntu.sh` repeats the quick suite in a container with the awk and grep flavours CI uses.

## Development

The application runs in a DDEV project (PHP 8.5, PostgreSQL 18, Redis, RustFS, Mailpit, a queue worker and a scheduler). `README.md` has the install sequence; day to day:

    ddev start
    ddev composer install
    ddev artisan migrate
    ddev exec vendor/bin/pest --filter=<name>

Run every PHP command through DDEV (`ddev composer ...`, `ddev artisan ...`, `ddev exec vendor/bin/pest ...`). The tests use the separate `kokpit_test` database that DDEV creates on start; `tests/TestCase.php` refuses any database whose name does not end in `_test`.

[Laravel Debugbar](https://github.com/fruitcake/laravel-debugbar) (`fruitcake/laravel-debugbar`, MIT) is a dev-only dependency for spotting N+1 queries, slow queries and Livewire round-trips. It is auto-discovered, follows `APP_DEBUG` locally (override with `DEBUGBAR_ENABLED` in your own `.env`), is forced off in `phpunit.xml` and is absent from production installs (`composer install --no-dev`). Its request history lands in `storage/debugbar/`, which is git-ignored; it can hold query bindings, so never share or commit it.

Composer scripts (the PHP gates; `composer ci` runs the first five in order):

| Script | What it runs |
|---|---|
| `composer test` | Pest: the Unit, Feature, Arch, Concurrency and Isolation suites (the Audit suite runs separately) |
| `composer partner-audit` | Pest: the Audit suite (routes, screens, endpoints, Partner actions and fields, leak channels) |
| `composer lint` | Pint in check mode (`--test`); run `vendor/bin/pint` to fix |
| `composer stan` | Larastan level 8 |
| `composer check-licenses` | the AGPL-compatible licence allowlist over `composer.lock` |
| `composer ci` | all of the above, the same gates CI runs |

The bash self-tests of the hygiene tooling are a host command: `bash scripts/tests/run.sh`. All gates must be green before a pull request.

### Conventions

Each convention is enforced by a test, so a violation fails `composer test` and not only the review.

- **Keys and time.** Every table has a UUID v7 primary key with the `uuidv7()` column default; foreign keys, morph `*_id` columns and package tables are `uuid` too. Every timestamp is `timestamptz` (`timestampsTz()`, never `timestamps()`); storage is UTC. The schema tests (R1 to R9) read the PostgreSQL catalogue and name the offending column; an exception goes into `PgSchema::EXEMPT` with a reason.
- **Morph aliases.** Polymorphic relations store a short snake_case alias, never a class name. Aliases live only in `MorphMap`; the morph map is enforced, so an unmapped model fails loudly.
- **Money.** Money is the `Money` value object with a `<name>_minor` (bigint, minor units) and a `<name>_currency` (char(3)) column pair and `MoneyCast`. There is no float money. `Money::fromExactMinor` is the single rounding point (half up); `tests/Arch/MoneyBoundaryTest` guards the boundary.
- **Numbering.** Gap-free, duplicate-free numbers (tasks, invoices) come only from `SequenceAllocator`, called inside the caller's own transaction so a rolled-back caller gives the number back. The year is part of the scope key; never hand-roll `max(number) + 1`. Application code does not call the allocator directly: `DocumentNumbering` is the single entry point. `next()` allocates and writes the number of a document kind from the stored pattern, `preview()` shows the number the next allocation would give (a stored or a candidate pattern) and never takes, skips or reuses one, and `nextTaskNumber()` writes task numbers as `KEY-N` with a counter per project. A changed pattern applies only to documents issued afterwards. `tests/Feature/Operations/NumberingTest.php` enforces it.
- **Immutability.** Frozen records (issued documents once locked by a successful send or by the Admin's manual lock, credit notes from their issue, and billed time entries) are protected by database triggers built with `Immutability`; the number and the kind of an issued document are always frozen, and a forbidden change raises SQLSTATE `KP001`. Application code is not the only guard. The rule for invoices is in the **Editable invoices.** bullet.
- **Localisation.** Every user-facing string lives in `lang/cs` (the interface is Czech, the fallback locale is English); no literal Czech or English text in classes or views. Enum labels are translated too. Times show as `j. n. Y H:i` in Europe/Prague, from the defaults set once in `LocalisationServiceProvider`.
- **Ordering.** A list that sorts by a timestamp breaks ties by `id`, so pagination is stable. Text that is sorted for people (names, titles) uses the Czech collation instead of the database default, through `CzechCollation::orderBy()` (`cs-CZ-x-icu`: `č` after `c`, `ch` after `h`), never a bare `orderBy('name')`. The REST API lookup lists (`/clients`, `/projects`, `/tasks`) are the one exception and sort `name` / `title` by the plain column with an id tiebreaker on purpose: a cursor page compares the last row's values in its keyset predicate, and that predicate would need the same collation. The API documents that this order is not Czech alphabetical order. The collation is a property of the database server: `kokpit:deploy:verify` checks `CzechCollation::isAvailable()` and fails the readiness gate when it is missing, so a server without ICU never goes live. There is no fallback to the default collation on purpose, because it would sort Czech names wrongly and nobody would notice. The remedy is an ICU-enabled PostgreSQL, which the official images are. `tests/Feature/TimeTracking/CzechOrderingTest.php` and `tests/Feature/Operations/DeployVerifyCommandTest.php` enforce it.
- **Isolation.** A Partner must never see another client's data, and the rule is enforced in the data layer, not by hiding UI. Every model implements `PartnerIsolated` (with `IsolatesPartners`, and a `KokpitPolicy` subclass that grants Partners explicitly; `DeniesPartners` for Admin-only data) or carries `NotPartnerScoped` with a reason. Every Filament resource, page, widget and relation manager carries an `AccessRule` attribute (`Audience::AdminOnly`, `Audience::PartnerAllowed` or `Audience::Guest`, each with a reason; `Guest` is always denied by the panel access checks and is allowed only on a `SimplePage`, see Guest pages below). Every new `PartnerIsolated` model gets one fixture line in `CanaryRegistry` (`tests/Support/CanaryRegistry.php`); the canary tests search every Partner-visible surface for another client's canary string. Known limit: the permission package registers a `Gate::before` callback that runs before `KokpitPolicy`, so a Partner who is granted a permission named like a policy ability would pass the gate before the policy is asked. No permissions exist yet; the first plan that introduces one must close this and extend the isolation tests.
- **Settings.** Every setting is a typed class extending `ValidatedSettings`, listed explicitly in `config/settings.php`; its `rules()` run on every `save()`, so a value written from a command, a job or a test is checked like one from the form. Create and change settings only through a migration under `database/settings` that extends `SettingsMigration` (its `up()` is final and runs `migrate()` in the system context, because the settings rows are Partner-scoped and fail closed). The package cache stays off, as a literal `false`: a cached read would bypass the Partner scope of `SettingsProperty`. A secret setting (a token, a key) goes into the package's `encrypted()` list of its class and never into a plain property. `SettingsProperty::PARTNER_VISIBLE_GROUPS` is the one widening point and is empty; a group added to it must be added on purpose together with the model's canary fixture. `tests/Feature/Operations/SettingsStorageTest.php` and the model declaration and canary tests (`tests/Arch/ModelDeclarationTest.php`, `tests/Isolation/CanaryRegistryTest.php`) enforce it.
- **Audit.** A model whose changes are audited uses `LogsAllowlistedActivity` and declares `#[LoggedAttributes([...])]` on the class itself, in the style of `#[NotPartnerScoped]`. Only the listed attributes are written, only when they change; there is no log-all option, and a missing or empty list throws on the first logged event. The allowlist covers model saves only: a bulk query update raises no model event and writes no row. Changes without a user are logged with a source label (`ActivitySourceLabel`: web, console, job, webhook, api) resolved from the execution context; a request to `/api/v1` is labelled `api` by the `LabelApiActivitySource` middleware of the api route group; a webhook handler wraps its work in `ActivitySource::as(ActivitySourceLabel::Webhook, ...)`. Activity rows older than `activitylog.clean_after_days` (365 days) are pruned every night by the scheduled `activitylog:clean --force` (`kokpit-activity-log-prune`, on one server). The package's clean action is replaced by `KokpitCleanActivityLogAction`, which runs the delete as system because the fail-closed Partner scope would otherwise turn it into a silent no-op. A record shows its history through a concrete subclass of `ActivityHistoryRelationManager` that carries its own `#[AccessRule(Audience::AdminOnly, ...)]` (the attribute is not inherited, so a subclass without one is denied to everybody). `tests/Arch/ActivityAllowlistTest.php`, `tests/Feature/Operations/ActivityAllowlistColumnsTest.php`, `tests/Feature/Operations/ActivityLogPruningTest.php` and `tests/Feature/Operations/ActivityViewsTest.php` enforce it.
- **Jobs and alerts.** Every queued class extends `KokpitJob`, which gives 3 attempts, a backoff of 10 s, 60 s and 5 min, a 60 s timeout and the `RunsAsSystem` middleware (a worker has no user, and the Partner scopes are fail-closed). Add middleware through `jobMiddleware()`; the system context cannot be dropped. Every concrete job declares `#[Idempotent(how: '...')]`: a job can run twice, so it identifies its work by a natural key, checks before it acts, and lets a unique constraint be the last line of defence. The queue connection dispatches after commit, so a job dispatched inside a transaction is invisible to workers until the commit and never pushed after a rollback. A final failure is reported by the `ReportFailedJob` listener through `AdminAlerter`: a synchronous e-mail to the Admin plus a bell notification, neither going through the queue, throttled per job class (`config/kokpit.php`, `alerts`). Delayed jobs and jobs waiting in their backoff count as old in the "oldest pending job" indicator, because its age runs from the creation of the job record; a job with a delay or backoff beyond the warning threshold must account for this. `tests/Arch/JobContractTest.php`, `tests/Feature/Operations/QueueContractTest.php` and `tests/Feature/Operations/AdminAlertTest.php` enforce it.
- **Health indicators.** The System page renders `HealthIndicatorRegistry`, which holds one `HealthIndicator` per `HealthSlot`. Thresholds are fixed values in `config/kokpit.php` (`health`), not editable in the UI. A slot that is still a placeholder ("not available yet") is replaced by the phase that can measure it with `HealthIndicatorRegistry::replace($slot, $indicator)` in a service provider; the indicator must report that slot. An indicator that throws, and a slot without an indicator, show as Error. `tests/Feature/Operations/HealthRegistryTest.php` fails when one of the six slots has no indicator. The `last_rate_date` slot is real since Phase 8: `LastRateDateIndicator` counts the Czech working days the newest stored CNB list is behind the list that should exist (Warning after 1, Error after 2, values in `config/kokpit.php` under `rates.health`), and a database that never held a list is Error, not "not available" (see Exchange rates below). `tests/Feature/Operations/LastRateDateIndicatorTest.php` enforces it.
- **Storage.** Private files use the `s3` disk, which is configured with `'throw' => true`, so a failed write raises instead of returning false. `php artisan kokpit:storage:check` (`StorageCheck`) proves the disk from configuration alone: write, signed read, refused unsigned read, delete, gone. It never prints a signed URL, a signature or a credential, and neither may any code you add. In DDEV the temporary URLs are built from the endpoint `http://rustfs.ddev-kokpit.orb.local`; the application never hands such a URL to a browser for a download, because every file is streamed through the application behind a signed route (`DocumentFileController`, see Documents), never through a presigned bucket URL. `tests/Feature/Operations/StorageCheckTest.php` enforces it and runs against RustFS in the `s3` Pest group. Every stored file goes to the `s3` disk: the default disk (`FILESYSTEM_DISK`, which falls back to `s3`), Filament uploads (they follow `FILESYSTEM_DISK`), the media library (`MEDIA_DISK`, which defaults to `s3`) and Livewire temporary uploads (below). `phpunit.xml` pins `FILESYSTEM_DISK` and `MEDIA_DISK` to `local` so the suite never writes to the bucket by accident; the `s3` Pest group uses the `s3` disk explicitly. **Temporary uploads (D-18).** Production runs more than one web container, so Livewire temporary uploads go from the browser straight to the private bucket through a presigned PUT (ACL private, valid five minutes, object under `livewire-tmp/`); the default of `livewire.temporary_file_upload.disk` is `s3` itself, not `FILESYSTEM_DISK`, so the suite and production take the same branch. The bucket needs two rules, which the operator notes and the deploy rehearsal check: a CORS rule that allows `PUT` from the instance origin only (no read methods, no other origin), and a one-day expiry rule on `livewire-tmp/`, because Livewire does not clean temporary uploads on S3 (`php artisan livewire:configure-s3-upload-cleanup` sets it). `ProductionConfigGuard` refuses to boot in production when the temporary disk (or, when unset, the default disk) is not a configured disk with the `s3` driver. DDEV takes the same path: RustFS is reachable under `rustfs.ddev-kokpit.orb.local`, which OrbStack serves to both the browser and the containers, so a presigned URL signed for `S3_ENDPOINT` is valid for the browser too (`S3_TEMPORARY_URL` only swaps the scheme to https, the Host stays and the signature holds); the `rustfs-init` service in `.ddev/docker-compose.rustfs.yaml` sets the CORS rule (`PUT` from the DDEV primary URL only) on the bucket at every `ddev start`. `phpunit.xml` pins `LIVEWIRE_TEMPORARY_FILE_UPLOAD_DISK` to `s3`: Livewire keeps test uploads on its own faked disk and signs nothing real, and a test fills a file field one file at a time like the browser (Livewire refuses a list of files on one property on S3; Filament uploads each file of a multiple field separately). One 10 MB rule applies everywhere (`livewire.temporary_file_upload.rules` mirrors `kokpit.documents.max_size_kb`), and `preview_mimes` is empty because a temporary preview is a presigned read URL valid up to a day on the bucket and an SVG preview would run as script on the app origin. No Content-Security-Policy restricts `connect-src` today; one added later must allow the bucket origin for uploads. `tests/Feature/Documents/UploadConfigTest.php` and `tests/Unit/Support/ProductionConfigGuardTest.php` enforce it.
- **Scheduled tasks.** Every event in `routes/console.php` is registered with `->onOneServer()` (closure and job events call `->name()` first, which Laravel requires), because the production crontab runs `schedule:run` on every container. The lock lives in the cache store, which must be the shared Redis in production (`CACHE_STORE` `redis`, refused otherwise by `ProductionConfigGuard`). Leave `SCHEDULE_CACHE_STORE` and `SCHEDULE_CACHE_DRIVER` unset so the scheduler uses that store. `tests/Feature/Operations/ScheduleOnOneServerTest.php` enforces it.

- **Partner-visible data.** A table that a Partner may read carries no Admin-only attribute. The `projects` table is Partner-readable, so its columns come from an allowlist and the rate, price, estimate, billing type and internal note live in `project_billing` (`ProjectBilling`: `DeniesPartners`, `AdminOnlyPolicy`, own uuid key, a unique foreign key to `projects`). `tests/Isolation/PartnerSafeColumnsTest.php` fails on any new column of `projects` that is not on the reviewed list and on a suspicious column name; extend the list only after checking that every Partner may read the new column. The Partner list and detail of a project are built only from the Partner-safe builders of `ProjectColumns` (`partnerColumns()`, `partnerEntries()`), shared with the Admin resource so the two cannot drift; `tests/Isolation/PartnerProjectVisibilityTest.php` pins the column and entry names and walks what a Partner can open. A model that a Partner may read has a real `constrainForPartner` (`Project` by its own client, `Tag` by the tags of visible own projects), a canary fixture in `CanaryRegistry` and a visibility test; `Client`, `Contact` and `ClientInvitation` stay closed to Partners. A project picker in any later phase uses `Project::selectable()` (not archived, client not archived), never its own repeat of that rule. Tasks follow the same rule: the `tasks` table and the `task_comments` table (`TaskComment`, whose Partner scope drops every internal comment) are Partner-readable with pinned column lists (`PartnerSafeColumnsTest`), while the checklist (`TaskChecklistItem`, table `task_checklist_items`) and the billing terms (`TaskBilling`, table `task_billing`) live in Admin-only tables (`DeniesPartners`, `AdminOnlyPolicy`). The Partner list and page of a task are built only from the Partner builders of `TaskColumns` (`partnerColumns()`, `partnerEntries()`, with the pinned name lists `PARTNER_COLUMN_NAMES` and `PARTNER_ENTRY_NAMES`), and `tests/Isolation/PartnerTaskVisibilityTest.php` walks what a Partner can open, canary strings included.
- **Tags.** Tags are typed (`TagType`), and every tag input, column, entry and query passes the type (`TagType::Project->value`, `TagType::Client->value`); an untyped read shows every type. Client tags never reach a Partner. Project tags do (they are shown in the Partner project list), so do not write internal wording into a project tag: this is the accepted risk D-07. `Client` and `Project` override `detachTags()` so that archiving (a soft delete, which also fires the package's `deleted` listener) keeps the tags and only a force delete detaches them; a new taggable model with soft deletes needs the same guard. `tests/Isolation/PartnerTagVisibilityTest.php` enforces the visibility.
- **Domain Actions.** A write to a client, contact, invitation or project goes only through its domain Action (`CreateClient`, `UpdateProject`, `InvitePartner` and so on): the Action validates, locks the parent row where a race matters and throws a `ValidationException` keyed by the bare data key or a `DomainException` for a refusal that belongs to no field. A Filament page or modal that hands its form to an Action uses `RethrowsDomainValidation` (`withFormErrors()`), which re-keys the errors to the form state path so each lands next to its field. `client_id` is not fillable on `Project`; creation code sets it through `$client->projects()`. The project key suggested while the name is typed comes from `ProjectKeySuggester` (a pure static helper with no model or database access); the unique key index in the database is the real guard, and the suggestion is only a convenience.
- **Guest pages.** A page that a visitor without an account opens (accepting an invitation, asking for a password reset link) carries `Audience::Guest`, is a `SimplePage`, and gets its access from its own signed route and throttle, not from the panel checks. The guest has no user, so every Partner scope is fail-closed: the page reads and writes through exactly one system-run path (`ClientInvitation::findAcceptable()` for the lookup, the `AcceptInvitation` Action for the write, both wrapping their work in `PartnerContext::runAsSystem`). Every failure on such a page looks the same to the visitor (one neutral message), and the route sends `Referrer-Policy: no-referrer`. `tests/Arch/PanelRegistryTest.php` fails when `Guest` sits on a class that is not a `SimplePage`, `tests/Feature/Clients/AcceptInvitationTest.php` covers the flow.
- **Escape hatches.** Removing the Partner scope (a `withoutGlobalScope` call naming `PartnerScope`), a bare `withoutGlobalScopes()` call or a raw `DB::table()` query is allowed in `app/` only for a file listed in `ESCAPE_HATCH_ALLOWLIST` with the reason it cannot reach a Partner. The list is empty on purpose; removing only `SoftDeletingScope` is fine and not reported. A lookup that must run without a user uses `PartnerContext::runAsSystem`, not a removed scope. `tests/Arch/QueryEscapeHatchTest.php` enforces it.
- **External lookups.** The ARES company lookup (`AresClient`) validates the company number (8 digits, checksum) before it builds a URL, retries only connection errors and 5xx responses, caches successes for an hour and is limited per user; a failure never blocks saving the form. The Pest base class calls `Http::preventStrayRequests()` (`tests/TestCase.php`), so a test that reaches the network fails; fake the response with `Http::fake`. Tests use a checksum-valid but fictional company number assembled at runtime by `FictionalCompanyId`, and the only literal allowed in a file is the placeholder `12345678`. `tests/Feature/Clients/AresClientTest.php` enforces it.
- **Passwords and accounts.** The minimum password length is 12 (`Password::defaults` in `AppServiceProvider`), for the installer, the invitation and the reset page alike. A deactivated Partner account cannot sign in and receives no reset link.
- **Tasks and numbering.** A task is created only through the `CreateTask` Action, and its `KEY-N` reference comes only from `DocumentNumbering::nextTaskNumber()`, which uses the `number_sequences` row `task:<project uuid>`; the `projects` table has no counter column. The project key is frozen from the first task on (archived tasks count): the `projects_key_frozen_guard` trigger raises SQLSTATE `KP002` for a changed key, and `UpdateProject` and the edit form refuse it earlier. A deleted number is never handed out again, and tasks are archived, never hard-deleted. `tests/Feature/Tasks/TaskActionsTest.php`, `tests/Feature/Tasks/TaskKeyTest.php`, `tests/Feature/Schema/TasksTableTest.php` and the parallel-process proof `tests/Concurrency/TaskNumberConcurrencyTest.php` (8 workers) enforce it.
- **Board.** Every write of a task's status or position goes through `TaskBoard` (`appendToColumn()` for a status change, `move()` for a drop) under the board advisory lock, and the order of locks inside one transaction is always the board lock, then the project row, then the counter row. `CreateTask`, `UpdateTask`, `ArchiveTask`, `RestoreTask` and `MoveTask` are the only callers; a new writer takes the same lock first. `MoveTask` checks the status whitelist, the id format, the Partner-scoped lookup and the policy, and re-reads the card under the lock. The `tasks` positions are guarded by a deferred exclusion constraint, so a missing lock fails loudly. `TaskBoard::applyFilters()` drops the tasks with `tasks.hidden_on_board` set, the one place that filters the flag, and `UpdateTask` is the only writer of it. `tests/Feature/Tasks/TaskBoardTest.php` and `tests/Concurrency/TaskBoardConcurrencyTest.php` (two processes moving cards in parallel) enforce it.
- **Rich text.** User-written HTML (task descriptions, comments, escalation reasons) is stored only through `RichText::clean()` and rendered only through `RichText::render()`, which use their own strict sanitiser and not Filament's global configuration. Editors keep file attachments switched off on purpose (`fileAttachments(false)`, D-22): a file dropped into an editor would bypass the document rules, so files go through the separate upload field and `AttachDocuments`. The limit is `RichText::MAX_LENGTH` bytes and a longer text is a field error, never silently cut. `tests/Feature/Tasks/RichTextSanitiserTest.php` enforces it.
- **Partner writes on tasks.** A Partner writes to tasks only through `CreateTask` (content only), `AddTaskComment` (never internal), `EscalateTask`, `ClearEscalation` (the assignee only) and `UpdateTaskDescription`. The last one changes the description of an own client-visible task whose status is in `TaskPolicy::DESCRIPTION_EDITABLE_STATUSES`, that is Planned or To clarify (owner decision D-16). It is guarded by the ability `editDescription`, which is checked again on the row re-read under a row lock, so a status change while the editor is open refuses the save; a save based on an outdated description is refused as stale; and the change is logged as the history event `description_changed` without its text. `UpdateTask` refuses every Partner. A new Partner write path gets its own policy ability and its own Action, never a wider `update`. `tests/Feature/Tasks/PartnerTaskDescriptionTest.php` enforces the description path.
- **Task checklist.** The checklist of a task (`TaskChecklistItem`, Admin-only through `DeniesPartners` and `AdminOnlyPolicy`) is filled in, edited, reordered and emptied only on the edit page, through the repeater bound to `Task::checklistItems()`. On the task page (`ViewTask`) the Admin can only tick or untick an item, and only through the `ToggleTaskChecklistItem` Action. The Action takes the target state, so a double click is harmless. It re-reads the task under a shared row lock and finds the item only among that task's items, so an unknown, malformed or foreign id is a 404. It checks the `update` ability on the item and refuses an archived task, whose checklist is read-only. The page method checks `TaskResource::canAccess()` itself, because the Livewire update endpoint `livewire-{hash}/update` is public. `tests/Feature/Tasks/TaskChecklistTest.php` enforces it.
- **Task billing.** A task's billing type, rate, fixed price and estimate are overrides in the Admin-only `task_billing` row, which exists only while something is overridden. The effective values are read only through `TaskBillingResolver` (task, parent task, project, client; the first level with a non-null value wins per field); a caller never repeats that order, and the resolver itself refuses anybody but the Admin or a system run. `tests/Feature/Tasks/TaskBillingResolverTest.php` enforces it.
- **Task notifications.** A task notification is sent only through `TaskNotifier`, which picks the recipients and builds the link of each audience (`/admin/tasks/KEY-N` for the Admin, `/admin/my-tasks/KEY-N` for a Partner). Notifications are queued after the commit and carry scalars only, so a worker reloads nothing and renders with no signed-in user. The preferences of a user (`NotificationPreferences`, edited on the profile page) can only narrow delivery. An internal comment never notifies a Partner, and that rule runs before any preference is read; it is also enforced in the notification constructor. Every value a task notification interpolates (title, display name, excerpt, change line) is escaped once, in `TaskNotification`, whose `toMail()` and `toDatabase()` are final: Markdown-escaped in the mail lines by `MailText::escapeMarkdown()` (the escape lives in `MailText`, not in `TaskNotification`; the mail renderer already HTML-encodes each line, so no `e()` there), HTML-escaped with `e()` in the bell, and left as plain text in the subject. A subclass only names its text group and supplies raw values, and never calls a translation helper. `tests/Isolation/NotificationMarkupTest.php` enforces that for every subclass and audience. A Partner's edit of a task description tells the Admin and the assignee through `TaskChangedNotification`, with one change line that names the Partner and no description text. `tests/Feature/Tasks/TaskNotificationsTest.php`, `tests/Feature/Notifications/NotificationPreferencesTest.php` and the canary proof `tests/Isolation/NotificationLeakTest.php` enforce it.
- **E-mail.** Every e-mail renders through the published `kokpit` theme: `config/mail.php` key `markdown` names it, `resources/views/vendor/mail` holds only the customised copies (layout, message, header, footer, the theme CSS, the text layout) and the framework copies stay the fallback for every other component, so do not publish a component you do not change. The supplier branding (name, address line, company ID, contacts, logo) is read only through `MailBrand`: one read per scope, in the system context, over a field whitelist, with a fallback to the application name on any failure; a view never reads `SupplierSettings`. The logo is an inline cid part embedded by `EmbedMailLogo` from the downscaled bytes of `MailLogo`, never a URL or a route, so no public route exists for mail assets. Every interpolated value in a Markdown line (a name, a title, a number, an amount, an Admin-typed word) is escaped with `MailText::escapeMarkdown()`, the text layout reverses exactly those escapes with `MailText::unescapeMarkdown()`, and the subject and URLs are not escaped. The document e-mail keeps its plain-text body: an Admin-typed body enters the HTML only through `PlainTextHtml::paragraphs()` (escaped, line breaks kept), and the card button and the plain-text block come from one call of `PayLinkBlock::forHtml()` under `PayLinkBlock::applies()`. - **Timer lock and clock.** Every timer decision takes the per-user advisory lock `TimerLock::lock()` first inside its transaction, before any row lock (the order is the timer lock, then task, project and client `FOR SHARE`, then the running entry `FOR UPDATE`); `ArchiveTask` and the board take their own locks and never the timer lock, so there is no cycle. The partial unique index is the authority behind it: a start that loses the race is translated into `TimerRaceLost`, after the rollback, and any other unique violation is rethrown unchanged. - **REST API.** Everything under `/api/v1` lives in `routes/api.php` in one route group per ability. Reads (GET) carry `auth:sanctum`, the ability `time:read` or `finance:read` and `throttle:api-read`; writes (POST, PATCH, DELETE) carry `auth:sanctum`, the ability `time:write` or `finance:write` and `throttle:api-write`. A controller is thin: it validates shape in a form request (`TimeEntryPayload` and `TransactionPayload` map the payload to the data of the domain Actions with an allow-list, so a smuggled `user_id`, `billing_state`, `czk_source` or `id` never gets through; `TransactionPayload` turns the minor-unit amounts of the wire into the major-unit strings of the Actions with `Money::ofMinor()->toMajor()` and renames the Action error keys `amount` and `czk_amount` to the API field names `amount_minor` and `czk_amount_minor` in one place, `remap()`), resolves references through `ReferenceResolver` (a UUID, a project key such as `DEMO` or a task reference such as `DEMO-1`; a name never identifies a record for a write) and writes only through the domain Actions. - **API lists and lookups.** A list endpoint is cursor paginated (default 50, at most 200, `per_page`), with a stable order (a timestamp, then the `id`). - **Idempotency.** The create endpoints (`POST /api/v1/time-entries`, `POST /api/v1/time-entries/batch`, `POST /api/v1/transactions` and `POST /api/v1/transactions/batch`) honour an optional `Idempotency-Key` header through the `EnsureIdempotency` middleware and the `IdempotencyStore` (table `api_idempotency_keys`): the same key and body replays the stored 2xx answer with `Idempotent-Replayed: true`, another body under the same key is 422 `idempotency_key_reused`, a retry while the first request still runs is 409 `idempotency_in_progress`, and a failed request releases its key. - **Finance.** A transaction is an income or an expense of the Admin, closed to Partners (`Transaction` and `TransactionCategory` are `DeniesPartners`). Categories form a two-level tree per type whose rules live in the database as composite keys, unique names and a frozen system row; the one system income category is reached only through `TransactionCategory::invoicePayments()` (Phase 10 books payments into it), may be renamed or reordered and never archived, deleted or retyped (`SaveTransactionCategory`, `MoveTransactionCategory`, `ArchiveTransactionCategory`, `DeleteTransactionCategory`). A transaction is written only through `RecordTransaction`, `UpdateTransaction` and `DeleteTransaction`, which authorize the Admin, take the row lock and validate the payload through `TransactionInput` (field errors keyed by the bare data key); the database refuses a nonsensical row on its own (CHECKs on the type, the amounts, the currency, the CZK source and the rate snapshot, and a composite key that ties the project to its client). The CZK figure is fixed once, when the row is written, by `TransactionCzk`: a CZK amount is its own figure (`CzkSource::Identity`), a foreign amount takes the figure the Admin typed (manual, and a manual figure stays manual on later edits) or the CNB list of the transaction date, looked up once with `ExchangeRateConverter::rateFor()` (the newest list not after the day) and converted with exactly that rate and unit amount, and the rate, unit amount and list date are stored with the row as the snapshot, so a list added later never moves a recorded figure. Without a figure and without a list the save is refused with a field error on `czk_amount`; it never waits for a rate and never stores a zero. The overview and its widgets read only through `FinanceOverview`, a hand-written reader that sums the stored `czk_minor` (nothing is converted again), refuses everybody but the Admin and a system run, and takes its period from `FinanceFilters`, which normalises the client-controlled filter state on the page and again in every widget. `tests/Feature/Finance/TransactionCzkTest.php`, `CategoryRulesTest.php`, `TransactionResourceTest.php`, `TransactionCategoryResourceTest.php`, `TransactionReceiptsTest.php`, `FinanceOverviewTest.php`, `tests/Feature/Schema/TransactionTablesTest.php` and `TransactionCategoriesTableTest.php` enforce it, and `tests/Isolation/DocumentFinanceLeakTest.php` proves that a Partner meets no Phase 9 surface (403 on every Admin route, page, widget and Soubory tab, and no archive, finance figure, hidden file name or other client's canary on any page or in the bell, each refusal paired with an Admin-side positive).
- **Card payments.** A document issued with its card switch on gets one single-use Stripe Payment Link; the switch is the global setting `online_payments_enabled` AND both Stripe secrets present AND the switch of the document, which starts from the flag of the client, is stored on the Admin-only row of the document, stays editable while an issued transfer document is open, is forced on for an online document and is frozen by the lock (Phase 14, OA-1; `CardPaymentSwitch`). The link is created by the queued `CreatePaymentLink` job after the issue transaction commits, so a Stripe failure never blocks issuing and only tells the Admin. The pay token is set once, with the first issue or, later, on an open issued document, and never changes, even when the switch is turned off and on again. The PDF, the e-mail and the Partner detail carry the stable `PayUrl` (`/pay/{token}`, route `pay.show`, `PayPageController`), never a Stripe address, and every printer goes through `PayUrl::forInvoice()`, which answers only while the switch is on, so a token alone never says that card payment is offered; the page redirects to the active link or says paid, cancelled or preparing. Stripe talks to `POST /webhooks/stripe` (route `webhooks.stripe`, `StripeWebhookController`): the signature is checked on the raw body, the event is stored once under its unique event id with the payer's personal data dropped, the answer is 200 at once and `ProcessStripeWebhook` does the work, handing `checkout.session.completed` and `checkout.session.async_payment_succeeded` to `RecordCardPayment` and `refund.created` to `RecordRefundEvent`. Processed events are deleted 90 days after processing by `PruneProcessedWebhookCalls`; the durable record is the `CardPayment`. Three mechanisms keep the books right. First, the reconcile invariant: a live link always offers exactly what its locked document still owes, so `PaymentLinks::reconcile()` runs inside every transaction that changes what is owed (`RecordPayment::recordLocked()`, `IssueCreditNote`, `DeletePayment`) and never outside one; do not deactivate a link any other way than through `PaymentLinks`, which has `PaymentLinks::deactivateLive()` beside `reconcile()` for the edits that change what is offered without changing what is owed: a change of the payment method deactivates the live link with the reason `replaced`, a switch-off with `manual`. Second, the system write core: a payment is written only into `invoice_payments` and its income only through the rules of `RecordPayment` (the system category, `TransactionCzk`, no `custom` source); a payment without a user is written only by `RecordPayment::recordLocked()` with the method card, inside one transaction with the document locked and a system run, and the database accepts a missing creator for no other method; a matched Stripe payment, its income and the paid state are one commit, and an assignment by the Admin (`AssignCardPayment`) uses the same core. Third, reserved Stripe references: `CardPayment::recordOnce()` writes the record with `INSERT ... ON CONFLICT DO NOTHING` against the unique event, session, payment intent and refund ids, so a repeat, a replay or a concurrent twin records nothing; a Stripe payment is deleted like any other, through `DeletePayment`, and the record keeps its references, so the same Stripe event can never book it again. A card payment is matched to a document by the invoice id of the link, and a later bank payment must match by variable symbol scoped by document kind, because an invoice and a proforma may share a symbol under custom number patterns (R-07-4; the docblock of `VariableSymbol` says so too). A payment that cannot be matched (another amount or currency, a cancelled document, no Kokpit metadata) and a second payment of a paid document are kept as an unmatched or duplicate record without an income, alert every Admin and wait in the overview `CardPaymentResource` and on the dashboard card `UnresolvedPayments` (in the reserved band of `Dashboard::getWidgets()`, next to `UnpaidInvoices`) until the Admin resolves them (`AssignCardPayment`, `ResolveCardPayment`, `RecordPaymentReturn`); a resolution is final. A Partner never meets any of it: `PaymentLink` and `CardPayment` deny Partners, and the only addition to a Partner surface is the pay button of `ViewPartnerInvoice` (`PartnerPayButton`). The tests never call Stripe: `StripeGateway` is bound to `FakeStripeGateway` (`tests/Support/FakeStripeGateway.php`), and webhook bodies are signed by hand with `StripeWebhookSigner`; every Stripe-shaped value is assembled at runtime. `tests/Feature/Payments/CardPaymentJourneyTest.php` is the end-to-end proof and `tests/Isolation/CardPaymentLeakTest.php` the Partner sweep.

### Hand-over notes for later phases

- **Phase 7 (REST API).** Built: time entries, the three lookups, tokens, limits, idempotent creates, the batch and the generated docs (see the REST API conventions above). The timer endpoints (start, stop, the running entry) are not part of it and moved to backlog phase 999.1 (API Timer). When they are built they write through `StartTimer` and `StopTimer`, never the model, and translate `TimerRaceLost` (a lost start) into a conflict answer instead of retrying; the unique running entry already makes a start safe per user. Time entries are written through `CreateTimeEntry`, `UpdateTimeEntry` and `DeleteTimeEntry`, the same Actions as the screens. Instants arrive as ISO 8601 text with an offset and go through `TimeEntryInput::instant()`; the Action truncates them to the whole second. A retried create is made safe by `EnsureIdempotency`, not by the endpoint. A task is addressed by `tasks.reference` (`KEY-N`, unique, stable), never by a title or a number alone; the board reads status and position only through `TaskBoard`. Only the token of an active Admin is valid, so deactivating an account stops its tokens without revoking them. Tracked time, rates and prices stay invisible to a Partner on every endpoint: a new column on a Partner-readable table needs the pinned-list edit of `PartnerSafeColumnsTest`.
- **Phase 9.1 (Transactions API).** Built: eight routes under `/api/v1` for transactions and their categories: `GET /transaction-categories` and `/transaction-categories/{category}` (a read-only tree), `GET /transactions` and `/transactions/{transaction}`, `POST /transactions`, `POST /transactions/batch`, `PATCH /transactions/{transaction}` and `DELETE /transactions/{transaction}`. A token carries one of four abilities, `time:read`, `time:write`, `finance:read` and `finance:write`; a time-only token gets 403 on a finance route and a finance-only token gets 403 on a time route, and a Partner token or no token gets 401 on every route. Writes go through `RecordTransaction`, `UpdateTransaction` and `DeleteTransaction`, the Actions of the Admin screens, so every rule of the screen (category type and archive, project of the client, CZK figure) holds over the API with the messages of the screen under API field names (`TransactionPayload::remap()`). Amounts travel in minor units (`amount_minor`, `czk_amount_minor`). The CZK figure has a fourth source, `custom` (`CzkSource::Custom`): the importer sends its own `exchange_rate` and optional `exchange_unit_amount`, and the row stores that rate as its snapshot. An own rate is sticky: editing the amount of a `custom` row recomputes the CZK figure at the stored rate, changing the currency returns the row to the CNB rate, sending `exchange_rate` and `czk_amount_minor` both as `null` returns a `custom` or `manual` row to the CNB rate of the transaction date, and the Admin screen recomputes at the CNB rate when amount, date or currency change. A batch takes at most `kokpit.api.transaction_batch_max_items` (500) items, saves each in its own transaction and answers 201, 207 or 422 like the time entry batch; a 500-item batch measured under one second locally. `TransactionController::CONFLICT_METHODS` lists the methods that can answer 409 (now `DELETE`, for a transaction the database refuses to delete), and the docs test requires a 409 only for those methods. The Idempotency-Key is honoured on both transaction creates; PATCH, DELETE and GET ignore it.

A draft is written only through `CreateDraft`, `UpdateDraft` (the whole draft in one transaction, lines matched by id, every amount computed on the server), `AddEntriesToDraft`, `AddFixedAmount`, `ReleaseEntries` and `DeleteDraft`; a document is issued only through `IssueDocument`, `ConvertProforma` and `IssueCreditNote`, which run the one pipeline of `DocumentIssuer` (with its `IssueContext`) in the caller's transaction under the row lock of the draft. The order of the pipeline is fixed: reads and the Admin-only rows first, the converted lines priced once with the CNB lists of the issue date, the number allocated late, the snapshots frozen (supplier, customer, lines, rates, CNB figures and the appearance), the PDF stored, and the flip of `state` to issued is the last write on the `invoices` row, because from then on the row is writable only while it is open and never again once a send has locked it (see **Editable invoices.**); a failure anywhere rolls the number and the stored object back. `EntryBilling` (`app/Domain/TimeTracking/Billing`) is the single writer of the billing and link columns of a time entry, `billing_state`, `billed_at`, `invoice_id` and the billed snapshot (rate, currency and amount): R-09-2 replaces the Phase 6 hand-over wording that invoicing bills through `MarkEntriesBilled`. `MarkEntriesBilled`, `CancelEntriesBilling` and every invoicing Action call it, on rows the caller locked FOR UPDATE in id order, and never write those columns themselves; its states are free, reserved by a draft, billed by a document and billed by hand, and `time_entries_frozen_guard` with its link guard stays the backstop for every writer. The billing terms of a task are read through `TaskBillingResolver` only and the rate of an entry through `TimeEntryRateResolver`, both of which refuse a Partner on purpose; invoice lines snapshot the effective values at issue, and the report, exports and dashboard take the amount of a billed entry from its snapshot (`EntryAmounts`). The work report attached to an e-mail is built through `WorkReportSource::fromEntryIds()` and `WorkReportPdf` and carries no money. The guards and their limits: a locked `invoices` row and its items and item sources accept no write, not even `updated_at` (R-04-4, R-04-6), and an issued document that is still open changes only through the write paths of the **Editable invoices.** bullet; the storno marker is the issued credit note with `cancels_invoice`, never a column on the invoice (R-04-5); the internal note, the CNB figures, the payments and the PDF link live in Admin-only side tables (`InvoiceAdmin` and `InvoicePayment`, R-06-1, R-06-6), so a Partner query never selects them, and any future column written after issue needs an owner decision amending D-13. The PDF reaches a browser only through the signed route `files.invoice` (`InvoicePdfController`, link from `InvoicePdfUrl::download()`), whose fixed order of checks answers a foreign invoice, a draft, an unknown id and a missing file with the same 404. E-mail goes through `QueueInvoiceEmail` and the idempotent job `SendInvoiceEmail`: every send, a resend included, is a new `invoice_emails` row and the latest row is the state of the document; a failure is a bell notice for the Admin only. A payment is written only by `RecordPayment` and is never edited; it is deleted only together with its income by `DeletePayment`, in one transaction under the transaction-local deletion flag (the only code that sets `kokpit.payment_deletion`, `tests/Arch/PaymentDeletionPathTest.php`), with the pair check of the database and the carried-payment rule: the copy of a proforma payment on the converted invoice is deleted with its own income and never touches the proforma, and a proforma payment that has a carried copy is refused (D-19 as amended on 2026-10-17, R-06-1, R-06-5, R-06-7, R-19-1, R-41-1 to R-41-5). - **Editable invoices.** An issued invoice or proforma stays open and editable until a successful e-mail send or the Admin's manual lock locks it, and only the Admin unlocks it again with a reason (Phase 10.1, Phase 16; D-01, D-03, D-12). The state is the column `invoices.lock_state` (`open` or `locked`) and the one database rule is `kokpit_guard_invoice_row()`: an open issued document is writable, a locked one is frozen, a credit note is locked from its issue, and the number and the kind never change. The code that locks is `SendInvoiceEmail`, which sets the lock in the same transaction as the sent mark, invoice row first, and the Admin's manual lock `LockInvoice` (Phase 16), which also takes the invoice row first and writes `invoice_locked_manually`; the only code that unlocks is `UnlockInvoice`, under the transaction-local setting `kokpit.invoice_unlock` (`tests/Arch/InvoiceUnlockPathTest.php` keeps that literal out of every other file). The single write path of an open issued document is `UpdateIssuedDocument` (lines, dates, parties, language, currency, notes, payment method, bank account and card switch), plus the issued paths of `AddEntriesToDraft`, `ReleaseEntries` and `AddFixedAmount` for linked time and fixed amounts; each of them ends in `IssuedEditFinisher`, which recomputes the CZK total, calls `PaymentLinks::reconcile()` so the card link offers the amount owed (a changed amount gives a new link), replaces the stored PDF through `ReplaceIssuedPdf` and writes the audit row through `InvoiceAudit`. `IssuedDocumentRules` is the one editability rule (it also refuses an edit while an e-mail is queued or sending and younger than the stale threshold of the System page, `InvoiceEmail::staleBefore()`, `email_in_flight`; an older row counts as failed, offers the resend, and `SendInvoiceEmail`, which claims a row under the invoice row lock, never sends it, class `stale`); no page or Action names the lock state itself. After the first successful send every edit leaves one Admin-only `invoice_edited` row with only the changed values, and the lock and the unlock leave `invoice_locked` (or `invoice_locked_manually`) and `invoice_unlocked`; the Partner reads none of them and sees only the current version of the document. The audited snapshot carries `bank_fingerprint`, a keyed fingerprint of the bank snapshot, so a change of the account is recorded with the fingerprints before and after, without the account itself (review WR-02; the owner accepted the fingerprint in place of the account values). The link between time entries and an invoice follows the same lock through `kokpit_invoice_accepts_time_changes()`, and `payment_links_invoice_fk` with the insert-time currency check keeps a link in the currency of its document. An old link keeps the currency it offered, so `RecordCardPayment` books a paid session only when the paid currency, the link's currency and the document's current currency agree (otherwise unmatched `currency`), and `kokpit_guard_card_payment_currency()` refuses in the database a card payment record that points at a payment in another currency (review CR-01). Later phases inherit this: a new e-mail kind (the payment confirmation of Phase 13 first) must not call the lock step, because only the document e-mail locks, and nothing but `SendInvoiceEmail` and `LockInvoice` may lock and nothing but `UnlockInvoice` may unlock. The enforcing tests are `InvoiceLockGuardTest`, `UnlockInvoiceTest`, `UpdateIssuedDocumentTest`, `UpdateIssuedDocumentPdfLinkTest`, `InvoiceEditAuditTest`, `IssuedEditorTest`, `IssuedTimeEditTest`, `PaymentClassificationTest`, `CardPaymentRecordTest`, `SendInvoiceEmailTest`, `EmailDialogTest`, `InvoiceEditSendConcurrencyTest` (an edit and the queueing of the e-mail in parallel processes) and `EditableInvoiceJourneyTest` (the whole rule in one test).
- **Payment method and bank accounts.** Every invoice and proforma carries its own payment method, `invoices.payment_method`: `transfer` or `online` (the enum `DocumentPaymentMethod`, not the `PaymentMethod` of a recorded payment, which says how money arrived). A credit note has none (NULL), every other row defaults to transfer through `kokpit_guard_invoice_row()`, and the column stays writable while the document is open; `invoices_payment_method_kind_check` ties the NULL to the credit note, and the amended `invoices_issued_fields_check` demands that an issued online document has no bank snapshot and an issued transfer document has one (owner answer OA-7, the online carve-out of Phase 10 D-12). The method decides what is printed (`InvoicePdfData`): a transfer document prints the bank box, the variable symbol and a QR code only where `Spayd::supports()` holds for its currency and account, an online document prints the online sentence and the card button and nothing about a bank. The method is independent of the currency and of the bank account (Phase 14, D-01, D-04). Bank accounts have a stable UUID v7 id, assigned in `BankAccountSettings::save()` and by the settings migration for the accounts that existed, and several accounts may share a currency; the one reader is `BankAccountSettings::find()`. A document points at its account by `invoice_admin.bank_account_id` (an Admin-only column), never by its currency, so a later change of the settings or of the currency cannot re-couple it to another account. `DocumentPayment` is the one rule of method, account and card switch, for a draft (`DocumentPayment::forDraft()`) and for an open issued document (`DocumentPayment::forIssued()`), and the creation, edit and issue paths call nothing else. On an open issued document card payment is offered only while it can work: a switch that a change from online derives, or that a save would turn on, needs card payment to be available, so a derived value falls back to off and an explicit request is refused as `card_payment_unavailable`; an online document whose switch is off, such as an invoice converted while card payment was unavailable, turns it on only once card payment is available to it again. The tie between the online method and the card switch is application-level only: no CHECK or trigger couples `invoices.payment_method` with `invoice_admin.card_payment_enabled`, so every writer goes through `DocumentPayment`. An invoice converted from a proforma inherits the proforma's method and stored account id; when that account is no longer configured, the issue copies the proforma's own bank snapshot, handed over through `IssueContext`, so a paid proforma always converts and never prints an account the proforma did not name. `DocumentPayment::preselect()` is the only currency-to-account rule and only suggests an account while the Admin prepares a document; `tests/Arch/BankAccountByIdTest.php` (`BankAccountByIdTest`) keeps it so: the old lookup by currency is deleted and the files that may call the preselection are an allowlist. `InvoiceCurrencies` is the one list of currencies an invoice can be billed in, for the create modal, the draft editor and the open issued editor. The card switch and the pay token follow the `Card payments.` rule above: the switch is editable while the document is open and frozen by the lock, the token is set once, every printer goes through `PayUrl::forInvoice()`, and a change of the method or a switch-off deactivates the live link through `PaymentLinks::deactivateLive()`. Phase 13 hand-over (owner answer OA-5), built: the invoice e-mail is an HTML message with a card button, and the button and the plain-text block both stand under `PayLinkBlock::applies()` as their one predicate, which holds only while the card switch is on AND a pay token exists, and never reads the token itself (see the `E-mail.` rule below). Phase 15 added `cash` as the third method: it prints no bank details, no QR code and no card button, and every cash payment gets a cash receipt (see the `Cash receipts.` rule below).
- **Cash receipts.** Phase 15 (P15-01 to P15-12) made `cash` the third value of `DocumentPaymentMethod`; the three predicates `printsBankDetails()`, `allowsCardChoice()` and `forcesCardPayment()` decide what a cash document prints and offers, so no caller compares the cases one by one, and the Admin detail keeps showing the stored variable symbol as an internal reference only (AS-13). Every cash payment gets a cash receipt (PPD, "příjmový pokladní doklad"), a row of `cash_receipts` that holds exactly what the receipt prints and is written by one place: `IssueCashReceipt`, called from `RecordPayment::recordLocked()` in the transaction of the payment, with the lock order invoice, payment, receipt. Its number comes from its own gap-free series (`DocumentKind::CashReceipt`, setting `cash_receipt_pattern`, default `PPD{YYYY}{NNNN}`, yearly reset, the year taken from the issue day), and the PDF is created by `StoreCashReceiptPdf` and linked to the receipt. `kokpit_guard_cash_receipt_row()` is the database rule for every writer: the number, the number of the paid document, the amount, the currency, the issue day, the language, the snapshots of appearance, the invoice and the client never change, a receipt is never deleted, only an open receipt accepts an edit (receipt date, purpose and the two party snapshots), `locked` goes back to `open` only under the sanctioned setting, and the cancel is set once. `SendPaymentConfirmation` attaches the PDF to the payment confirmation and locks the receipt on the successful send; a receipt cancelled before the mail leaves is neither attached nor locked, and the confirmation is still sent (AS-1); a confirmation that is skipped for lack of an invoice e-mail, or because the client's document e-mails are switched off, leaves the receipt open and the Platby tab shows it as not sent (AS-10). A cash payment of a proforma issues a receipt and the conversion issues no new one: the carried copy shows the receipt of the proforma payment by reference (D-07). The Actions are `CancelCashReceipt` (the storno with a reason of 10 to 500 characters: the number and the PDF stay, the PDF is rendered again with the cancelled band, and it is the only way to make the payment deletable, because `DeletePayment` refuses while the receipt is valid and the database clears the payment link of a cancelled receipt when the payment goes), `UpdateCashReceipt`, `LockCashReceipt` (the manual lock, Phase 16: the Admin closes an open receipt without a send), `UnlockCashReceipt` (the only code that sets `kokpit.cash_receipt_unlock`, kept so by `CashReceiptUnlockPathTest`) and `RegenerateCashReceiptPdf`; the reasons and the edited printed texts go only to the Admin-only activity log through `CashReceiptAudit` (AS-16), never to a row a Partner reads. The PDF reaches a browser only through the signed route `files.cash-receipt` (`CashReceiptPdfController`, link from `CashReceiptPdfUrl::download()` built at click time). ## What the checker flags

`scripts/check-sensitive.sh` reports the following categories. The rule name is what appears in a finding.

| Rule | What it flags |
|---|---|
| `key-prefix` | Secret-key and token prefixes with a body: Stripe, GitHub and AWS style keys (the AKIA and ASIA prefixes) |
| `email` | E-mail addresses outside `example.com`, `example.org`, `example.net`, `.test`, `.invalid`, `.localhost` |
| `company-id` | 8-digit company-ID-like numbers (the placeholders `12345678` and `00000000` are allowed). The number is also found after `-`, `_` or `/`, so write dates with separators (for example 2026-10-07) and not as one run of digits |
| `iban` | IBANs with a valid country length and checksum, also in groups of four and also in lower case |
| `cz-account` | Czech account numbers, with or without prefix, also with one space on either side of the slash |
| `public-ip` | Public IPv4 addresses, also after `-` or `_` (private, loopback, link-local, documentation and similar ranges are allowed) |
| `hosting-host` | Zerops and S3-provider endpoint hostnames, in any letter case |
| `home-path` | Personal absolute home paths: `/Users/<name>` and `/home/<name>` with or without a trailing slash, also quoted or at the end of a line, and the Windows form `C:\Users\<name>` (any slash style and letter case). Placeholder names are allowed: `example`, `user`, `username`, `name` and `you`, for the Unix form also `runner`, `vagrant`, `ubuntu`, `www-data`, `ddev` and `Shared`, and for the Windows form `Public`, `Default`, `All` and `runneradmin`. A `home` or `Users` segment inside a URL or a relative path is not a home path |
| `git-attributes` | A `-diff`, `binary` or `filter=` attribute in any `.gitattributes`. Such an attribute hides content from gitleaks in the hook, or stores something other than the file in git. The rule is checked in staged, `--all` and explicit-file mode, never in `--history`, so a removed line cannot keep CI red. A deliberate use (for example Git LFS) needs a reviewed path-scoped allowlist entry for this rule |
| `denylist` | Terms from your local denylist, see below |

Modes:

- no argument (or `--staged`): the added lines of the staged diff. This is what the hook runs.
- `--all`: every tracked file in the index, read in full. CI runs it.
- `--history`: every added line in `git log --all`; findings name the introducing commit as `path:line@sha`. It covers every commit, including content introduced by a merge commit (diffed against its first parent, `--diff-merges=first-parent`) and renamed files (shown in full). CI runs it over the full history.
- `FILE...`: explicit files (use `--` before a name that starts with a dash). Every non-empty operand is scanned; there is no binary skip.

Every mode reads the full content of every file, including files git treats as binary (NUL bytes, a `-diff` or `binary` attribute) and UTF-16 text. Diffs are forced to text, textconv drivers are ignored, and NUL bytes are read twice, once as a space and once removed. Each finding is printed once.

Exit codes: `0` clean, `1` findings, `2` usage error, not a git repository, an unreadable or in-repository denylist, or a scanner error. Matched values are always masked: a finding prints the rule, the file and the line, plus the first characters and the length of the value, never the value. The same is true for the denylist stage: the term and the line text are never printed. A file path that itself contains a denylist term is printed as the finding path, because the path is the finding.

## Exemptions

Reviewed exemptions live in two files, both covered by code owners and reviewed in pull requests:

- `scripts/sensitive-allowlist.txt`: one entry per line, `rule ;; path-ERE ;; matched-value-ERE`. Make each entry as narrow as possible: one rule, the smallest path scope, an anchored value pattern. The value pattern is tested against the matched value, not the whole line.
- `.gitleaks.toml`: the allowlists of the gitleaks configuration.

Exactly five files are exempt from the generic rules, by exact path: `scripts/check-sensitive.sh`, `scripts/lib/scan.awk`, `scripts/lib/diff2tsv.awk`, `scripts/sensitive-allowlist.txt` and `.gitleaks.toml`. The denylist still scans them. Binary assets (images, fonts, PDFs) are scanned too. A false positive in one gets a narrow, path-scoped allowlist entry.

There are no inline ignore comments, no environment variable and no flag that disables or redirects a rule. gitleaks runs with `--ignore-gitleaks-allow`, so a `gitleaks:allow` comment in a file has no effect.

## Local denylist

Terms specific to your own instance (client names, internal project names, company IDs) go into a denylist that never enters the repository:

    export KOKPIT_DENYLIST="$HOME/.config/kokpit/denylist.txt"

The file lives in your home configuration directory. The script refuses a path inside the repository.

Format: one term per line. Blank lines and lines starting with `#` are ignored. Terms are fixed strings. Use terms of at least 3 characters: very short terms match too much.

Term and text are folded the same way: ASCII letters and the accented Latin letters from U+00C0 to U+017F (Czech, Slovak, German, Polish and more) become lower-case base letters, and combining marks are removed. A term written with diacritics therefore matches the same text without them, the reverse also holds, and composed and decomposed spellings match. Matching is byte-wise after folding and does not depend on the system locale. Letters of other scripts are compared exactly as written. Accented letters in UTF-16 or in legacy single-byte encodings such as Windows-1250 are not folded; only their ASCII letters match.

A fictional example file:

    # fictional example terms
    Acme Fictional Ltd
    Project Bluebird

Behaviour:

- `KOKPIT_DENYLIST` unset, or the file does not exist: one notice on stderr, then only the generic rules run. The exit code is unaffected. This is also how CI runs.
- the file exists but is not readable: exit `2`.
- the file is inside the repository: exit `2`, so a real list can never be committed through this tool.

## Never bypass

`git commit --no-verify` and `LEFTHOOK=0` skip the hook. Do not use either: CI rescans the whole tree and the whole history and fails the pull request, so a bypass only moves the finding to a later and more public place.

A path-limited commit (`git commit -- <path>`) scans only the committed paths, not the whole index.

## If something leaks

If something sensitive was committed or pushed:

1. Rotate or revoke it first. A secret that was ever pushed is compromised, whatever happens to the history afterwards.
2. Remove it from history. Before the first push, a local history rewrite is enough. After a push, contact the owner: the organisation ruleset blocks force-pushes to `main`, so the repair needs a decision.
3. Notify the affected parties.

The same runbook, together with how to report a vulnerability privately, is in `SECURITY.md`.

## CI

The workflow `Hygiene` runs on pushes to `main` and on pull requests, never on `pull_request_target`. Its jobs:

- `scan`: the hygiene self-tests, `--all`, `--history` and gitleaks.
- `workflow-lint`: actionlint and zizmor.
- `tests`: Pest on PostgreSQL 18 and Redis services, after booting the application from `.env.example` alone (copy, `key:generate`, `migrate`, `kokpit:install`). Pest runs in four parallel shards of this job (`--shard`, by test class, balanced by the recorded class times in `tests/.pest/shards.json`, `fail-fast` off), and inside each shard the suites run from the cheapest to the most expensive: Unit and Arch, then Feature, then Isolation and Concurrency. The Partner audit runs in the first shard only. `tests/Feature/Repo/CiParityTest.php` keeps the shard matrix equal to the shard total and the steps equal to the suites of `phpunit.xml` except Audit; `composer test` and `composer ci` stay unsharded. After adding or removing many tests, refresh the class times with `ddev exec vendor/bin/pest --exclude-testsuite=Audit --update-shards` and commit `tests/.pest/shards.json`; a stale file only costs balance, never coverage.
- `static-analysis`: Pint and Larastan level 8.
- `dependencies`: `composer validate --strict`, `composer audit --locked` and the licence allowlist.
- `CI Passed`: the aggregator and the only status check the organisation ruleset requires. It waits for every other job, and `scripts/tests/test-workflow.sh` fails when a job is missing from its `needs` list.

Run the PHP gates locally inside DDEV with `ddev composer ci` (tests, formatting, static analysis and the licence check; `ddev composer check-licenses` runs the last one alone). The bash self-tests stay a host command: `bash scripts/tests/run.sh`.

The licence check passes a package when at least one of its declared licences is AGPL-3.0-compatible (a dual-licensed package lists its alternatives separately) and fails on `GPL-2.0-only`, on proprietary terms and on a package with no licence. A failure is a prompt to decide, not to extend the list in `scripts/check-licenses.php` silently; the change needs maintainer review.

The gitleaks step runs with `--log-opts="--all --diff-merges=first-parent --text --no-textconv"`, so it also reads merge commits and content git treats as binary. UTF-16 content stays invisible to gitleaks and is covered by the shell scan. In the pre-commit hook gitleaks cannot read binary-classified content; the `sensitive-content` job before it does.

Everything is pinned. Actions are pinned by full commit SHA and bumped by Dependabot. The tools gitleaks, actionlint and zizmor are downloaded as a release tarball by version and verified against a SHA-256 hard-coded in the workflow. Never trust a checksums file taken from the same release.

Manual bump procedure for a tool:

1. Read the new version and its asset digest: `gh api repos/<owner>/<repo>/releases/latest --jq '.assets[]|[.name,.digest]|@tsv'`.
2. Verify the digest against the upstream checksums.
3. Update the version and the digest in the workflow together, in one change, and update the tested versions in the Setup section.

Rules:

- Each deploy pushes the `kokpit` setup once (the version name is the tag, or `main` plus the short sha for a dispatch from `main`). Every container of the new version runs the `initCommands` in order, and Zerops ends the deploy at the first failing one, before traffic is switched, so the previous version keeps serving. The migration runs once per deploy through `zsc execOnce` keyed on the app version id; a failure is reported as failed on every container (a Zerops property), which stops the deploy. Directly after it `php artisan kokpit:deploy:verify` runs on every container, without `execOnce`, and exits non-zero on an unreachable database, a pending migration (package and settings paths included), a Redis connection (default, queue, cache, session) that fails or gives no valid answer, or a database server without the Czech ICU collation `cs-CZ-x-icu` (the remedy is an ICU-enabled PostgreSQL, which the official images are), which stops the deploy too. There is no `readinessCheck`. Rehearsal checks 8 and 9 confirm the behaviour on a real project (`.planning/phases/03-operations-foundation/03-ZEROPS-REHEARSAL.md`).
- Horizon starts at container start: `sudo supervisorctl start horizon` is the last `initCommands` step, so it runs on every container only after the migration and the verify passed, and supervisord (`autostart` in `supervisor-horizon.ini`) starts it again after a restart. `ZeropsConfigTest` keeps the command last, after the migration and the verify, and outside `execOnce`.
- The build base carries Node.js 24 (`alpine/nodejs@24`) next to PHP, but the repository has no `package.json` or lockfile, so the build installs PHP dependencies only, runs no Node or pnpm step and has no build environment, so `composer install` runs with `--no-scripts` (the `post-autoload-dump` scripts boot the application, where `ProductionConfigGuard` would refuse on the missing service-level variables). `package:discover` and `filament:upgrade` (the Filament assets are not committed) run at the start of `initCommands` instead, with the real environment; the maintainer adds a frontend build together with `ZeropsConfigTest` when one exists.
- Migrations stay backward compatible with the previous release (expand, deploy, contract): the previous version keeps serving during a deploy and after a failed one, so a column is added first and dropped only one release later.
- rollback is activating the previous version of the service in Zerops. It does not undo migrations, which is why they must stay backward compatible.
- The zcli version and its SHA-256 are hard-coded in `deploy.yml` and bumped by hand with the tool bump procedure of the CI section (read the digest of the asset `zcli-linux-amd64`, update version and digest together).
